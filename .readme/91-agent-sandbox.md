# Sandbox de agentes

Los clientes de agente ejecutan los comandos del modelo dentro de un sandbox del sistema operativo. Un comando que el sandbox deniega **no llegó a ejecutarse**: `04-validation-and-testing.md` prohíbe reportarlo como comprobación aprobada o fallida, y `13-agent-tooling.md` pide declarar la exención duradera en lugar de sortearla en cada corrida. Este archivo registra dónde se declara esa exención en cada cliente.

Declarar una exención mueve un límite de permisos, así que requiere la autorización explícita que exige `AGENTS.md`.

## Sistemas

El sandbox de Claude Code existe en macOS, donde usa Seatbelt, y en Linux y WSL2, donde usa bubblewrap. En Windows nativo y en WSL1 no hay sandbox: los comandos no se confinan y las exenciones no tienen efecto.

Codex confina los comandos con los ajustes de la sección de Codex. En Windows su sandbox se activa aparte, con `[windows] sandbox = "elevated"` o `"unelevated"` en el `config.toml`.

## Claude Code

El sandbox se activa con `sandbox.enabled` en `.claude/settings.json`; mientras esté apagado no confina nada y una exención no tiene efecto. En la plantilla ese archivo declara la configuración compartida; en un proyecto derivado queda sellado, como `.codex/hooks.json`: el hook del sello lo restaura si difiere del manifiesto y las herramientas de archivo no pueden editarlo, como explica [Adopción de versiones de la plantilla](96-template-adoption.md). Lo propio de cada proyecto o persona va en `.claude/settings.local.json`, que Claude Code aplica por encima del compartido y cuyas listas (`permissions.allow`, `sandbox.excludedCommands`, `sandbox.filesystem.denyWrite`) se suman a las del compartido ([ajustes](https://code.claude.com/docs/en/settings), secciones «Settings precedence» y «Lists merge instead of overriding»). Ese archivo no puede quitar entradas del compartido y es por persona: git lo ignora, con la regla del `.gitignore` de la plantilla, y las sesiones en la nube no lo leen. Un proyecto que necesita cambiar lo que comparte el equipo registra `.claude/settings.json` en la lista de excepciones, con la aprobación del usuario, y eso lo saca entero del sello. El hook de rutas protegidas lee la unión de los dos archivos. Exención y sandbox viven en la misma clave:

```json
{
  "sandbox": {
    "enabled": true,
    "excludedCommands": ["<invocación del script de E2E>*"]
  }
}
```

La exención de un runner propio de un derivado va en `.claude/settings.local.json`, con la misma forma. Los patrones son globs sobre la cadena del comando, y el `*` final cubre las variantes que cuelgan del mismo prefijo. Nombran el comando tal como lo publica el repositorio —`pnpm run test:e2e`, `npm run e2e`, `bun test:e2e`, `deno task e2e`, `make e2e`—, nunca una forma tomada de este documento: `03-code-authoring.md` establece cuál es el gestor propietario. Exceptúa el script, no el binario que invoca: el patrón alcanza también a los subprocesos que ese script lance. Un espacio antes del `*` exige que el nombre termine ahí, con o sin argumentos: `pnpm run test *` cubre `pnpm run test` y `pnpm run test <archivos>`, pero no `pnpm run test:e2e`.

Una exención solo saca del sandbox una llamada si cubre todos sus comandos, y algunas formas siguen confinadas aunque los cubra, entre otras: una llamada con `cd`, `pushd` o `popd`, una sustitución de comandos, un subshell o un bloque de control, una redirección que no se limite a duplicar un descriptor como `2>&1`, o un comando que empiece por `sudo`, `eval` o `xargs`. Así, una tubería hacia `tail` o una redirección a un log bajo `.temp/` mantienen el script de E2E dentro del sandbox, y falla igual que sin exención. Lo mismo hace una asignación de variable de entorno delante, como `FOO=1 pnpm run test:e2e`: Claude Code solo pasa por alto algunas variables que considera seguras. Un script que necesite una variable la fija en su propia definición, para que se invoque sin nada delante. La salida de un comando exento se lee del archivo de salida de la tarea en segundo plano que lo ejecuta o del log que escribe el propio script, nunca de una redirección ni de una tubería; el hook de comandos exentos de [Hooks de agentes](92-agent-hooks.md) lo impone: rechaza la llamada que lo confinaría y muestra la forma exacta que debe ejecutarse.

`excludedCommands` es una lista estática que salta el sandbox sin que el modelo intervenga, distinta del reintento fuera del sandbox que el modelo pide caso por caso y que depende de `sandbox.allowUnsandboxedCommands`. La sesión acepta `/sandbox exclude "<patrón>"` para añadir patrones sin editar el archivo.

### Configuración de la plantilla

`.claude/settings.json` activa el sandbox con estos ajustes:

- `enabled` y `autoAllowBashIfSandboxed`: cada comando corre confinado y se aprueba sin preguntar; solo escribe en el proyecto y en el temporal del sistema, que la sección [Escrituras en carpetas temporales](#escrituras-en-carpetas-temporales) trata aparte.
- `excludedCommands` con `node .scripts/run-checks.mjs *`, `node .scripts/browser.mjs *` y `node .scripts/release.mjs *`: los checks de la plantilla, las sesiones de navegador del agente y el release de la plantilla corren fuera del sandbox. Con el espacio antes del `*`, el nombre del script debe terminar ahí, con o sin argumentos, así que un archivo cuyo nombre solo empiece igual, con letras añadidas tras `.mjs`, no sale del sandbox. Las pruebas de los checks crean repositorios git desechables y copias de `.mcp.json` bajo `.temp/`, y el sandbox no deja escribir `.git/config`, `.git/hooks/` ni `.mcp.json` en ninguna carpeta, así que dentro fallan siempre. La exención de `run-checks.mjs` existe solo para los checks de la plantilla, la única que tiene ese script; la de `release.mjs`, que sí se adopta, porque no es `TEMPLATE_ONLY`, y queda sellado en los derivados, pero solo actúa en la plantilla mantenida, se explica al final de este punto. Dos reglas `permissions.allow`, para el lanzador solo y seguido de argumentos, con sus gemelas `PowerShell(...)`, dejan correr los checks sin pedir confirmación y existen, como la exención de `run-checks.mjs`, solo para los checks de la plantilla: esos scripts y pruebas de `.scripts/` corren así sin confinar y sin preguntar, y `filesystem.denyWrite` (más abajo) impide que un comando confinado los reescriba. Solo sale la invocación lanzada sola desde la raíz, sin las formas que la mantienen confinada, y las propias pruebas impiden que git salga de `.temp/` si no llega a crear un repositorio. Las cinco entradas se quedan en el `settings.json` sellado de un derivado, porque un archivo local no puede quitar entradas del compartido. Para que no sirvan de escape, el hook de alcance de escritura deniega, en un derivado, crear con las herramientas de archivo cualquier ruta solo de la plantilla (`TEMPLATE_ONLY`, en `.scripts/template-files.mjs`) y `.scripts` sigue en `denyWrite` para la shell, así que un derivado no puede crear un `run-checks.mjs` propio que heredara esas entradas. La exención del lanzador del navegador responde al caso conocido de la sección final, que explica su alcance, y se queda también en un derivado que no adopta la verificación en navegador operada por el agente, porque solo alcanza a una invocación de `node .scripts/browser.mjs`, que ese proyecto no hace; quitarla exige registrar `.claude/settings.json` como excepción. La exención de `node .scripts/release.mjs *` saca del sandbox el release de la plantilla, que ejecuta `git push` y `gh release create`: dentro del sandbox de macOS `gh` no verifica los certificados TLS, como explica el punto siguiente, y su espera del CI también lo necesita. A diferencia de la de los checks, no lleva regla `permissions.allow`: la confirmación la pide la regla `ask` del punto de `permissions.ask`, que compara el texto del comando, así que solo la forma documentada, `node .scripts/release.mjs …` lanzada sola desde la raíz, la activa y sale del sandbox. Otra grafía, como `node ./.scripts/release.mjs`, o la misma forma tras un `cd`, ni pide confirmación ni sale del sandbox y corre confinada: en macOS `gh` falla y el script termina sin etiquetar; donde `gh` funcione confinado, publicaría sin esa confirmación, aunque solo con el CI en verde. El script se niega, sin tocar nada, fuera de la plantilla mantenida, y `.scripts` sigue en `denyWrite` (más abajo), así que un comando confinado no puede reescribirlo. Riesgo residual en un derivado: un comando confinado podría editar el documento de adopción para que registre el `origin` del derivado y versionar un marcador de CI de la plantilla, con lo que el script lo trataría como plantilla mantenida y publicaría en el remoto del propio derivado; la barrera es la confirmación `ask`. El hook de [Hooks de agentes](92-agent-hooks.md) no ve el push ni el release que lanza el propio script, que espera al CI por sí mismo.
- `excludedCommands` y `permissions.allow` con los `gh` de solo lectura: `gh repo view` y `list`, `gh pr view`, `list`, `diff` y `checks`, `gh run list`, `view` y `watch`, `gh workflow list` y `view`, `gh issue view` y `list`, y `gh release list`, `view` y `verify`, que también cubre `verify-asset`. Dentro del sandbox de macOS, `gh`, como otras herramientas escritas en Go, no puede verificar los certificados TLS, así que esos comandos, lanzados solos, corren fuera del sandbox, con el acceso completo de la persona y sus credenciales de `gh`, y sin pedir confirmación. Cada regla `allow` tiene su gemela `PowerShell(...)`. Con `--web` o su forma corta `-w`, que abren el navegador, piden confirmación, porque una regla `ask` pesa más que una `allow`. `-w` la pide delante o detrás del argumento y agrupada con otras opciones cortas, como `gh pr view -cw`, con una regla por subcomando, salvo en `gh run list`, donde `-w` es `--workflow`, un filtro, y no la pide. Como esas reglas comparan el texto, también la pide un argumento que contenga `-w` tras un espacio, como `--search "x -wip"`. Los demás `gh` que usan la red fallan dentro del sandbox, y el modelo los repite fuera con la confirmación normal.
- `network.allowedDomains: ["*"]`: salida a cualquier dominio sin confirmación.
- `network.allowLocalBinding`: en macOS permite levantar servidores en `127.0.0.1`, como hacen los runners de pruebas.
- Sin `filesystem.denyRead`: por decisión del usuario, el sandbox puede leer las credenciales del equipo (`~/.ssh`, `~/.aws`, los tokens de `gh` o `wrangler`) por si una tarea las necesita.
- `filesystem.denyWrite` con `.scripts`, `.codex`, `.agents/skills`, `.agents/tool-versions.json` y `.temp/playwright-cli`: desde `.scripts/` corre código fuera del sandbox o sin preguntar —los hooks de ambos clientes, la línea de estado, `run-checks.mjs`, que ejecuta además sus pruebas y los scripts de la skill `prompt-plan`, en `.agents/skills/`, `browser.mjs` y, en un proyecto que declara el servidor `appium-mcp`, `mobile-server.mjs`, que el cliente arranca sin confinar y que ejecuta el paquete que instala en una caché por persona—, y `.codex/` define los hooks y la configuración de Codex; sin la protección, un comando confinado podría cambiarlos y su código correría sin confinar en el siguiente hook. `.agents/tool-versions.json` es el archivo de donde `browser.mjs` y `mobile-server.mjs` toman, sin confinar, la versión y el hash de integridad de `playwright` y de `appium-mcp`: protegido, un comando confinado no puede elegir qué versión se instala. `.temp/playwright-cli` es la carpeta de salida de la sesión de navegador, que corre sin confinar y sigue escribiendo en ella después de que el lanzador la comprueba; protegida, un comando confinado no puede escribir allí ni sustituirla, ni a `.temp`, por un enlace que redirija esas escrituras, aunque las capturas siguen siendo temporales y legibles. Las rutas relativas se resuelven contra la raíz del proyecto y el SO hace cumplir la denegación a los comandos confinados, subprocesos incluidos. Solo alcanza a esos comandos: las herramientas Edit y Write siguen editando esas rutas, porque se rigen por las reglas de permisos y no por el sandbox. Donde el comando no se confina, en Windows nativo y en Codex, o donde una regla `Edit` no llega, lo cubre en parte el hook de rutas protegidas de [Hooks de agentes](92-agent-hooks.md): lee la unión de esta lista y la de `.claude/settings.local.json`, donde un proyecto añade sus propias rutas, y pide confirmación en Claude Code, o rechaza en Codex, un comando de shell que escribe de forma evidente una de esas rutas, y tras cada comando avisa de las que cambiaron; es una heurística sobre el texto del comando, no una garantía. Los hooks que escriben fuera del sandbox (`check-file-length` en `.temp/check-file-length/`, `update-stack-doc` en `.docs/stack.md` y `check-template-seal` en `.temp/template-drift/` y en los archivos sellados que restaura) no siguen enlaces simbólicos, ni en el archivo ni en ninguna carpeta de su ruta, y solo borran o escriben archivos con la forma que esperan, así que un comando confinado no puede redirigir sus escrituras a rutas protegidas; `check-empty-dirs` solo elimina carpetas vacías. Lo que deja de funcionar dentro del sandbox debe ejecutarse fuera de él, con la confirmación normal: los formateadores sobre todo el repositorio; `git restore`, `checkout`/`switch`, `pull`, `merge`, `rebase` o `stash` que toquen esas rutas, porque fallan en esas rutas y el paso puede quedar a medias; aplicar o revertir con `prompt-plan` parches que las toquen; borrar con la skill `start` los archivos de `.scripts/` que son solo de la plantilla, que en Claude Code pide confirmar el hook de rutas protegidas y en Codex, donde ese hook corre con `--deny`, rechaza el comando escale o no el agente, así que `start` da al usuario el comando exacto para que lo ejecute él; borrar las capturas de `.temp/playwright-cli`; `node .scripts/tool-versions.mjs --refresh` y `--add`, que escriben `.agents/tool-versions.json` (dentro del sandbox llegan al registro por el proxy del entorno, pero no pueden escribir el archivo protegido y lo dicen); y los pasos de adopción de [Adopción de versiones de la plantilla](96-template-adoption.md). Por defecto el sandbox ya protege, además, los archivos de ajustes de `.claude` (`settings.json` y `settings.local.json`), `.claude/skills`, `.claude/agents`, las carpetas `commands` y `hooks` de `.claude`, `.mcp.json` y los `hooks` y `config` de `.git`.
- `permissions.deny` bloquea comandos de sistema que ninguna tarea necesita (`sudo`, `dd`, `mkfs`, `shutdown`…). Comparan prefijos de texto, así que no sustituyen al confinamiento.
- `permissions.ask` pide confirmación solo para las acciones remotas que pueden destruir algo o no se deshacen y para los `gh` que muestran credenciales, instalan o ejecutan código, o esconden otro comando: los `git push` que sobrescriben o borran en el remoto, con `--force` y sus variantes, `-f`, `--delete`, `-d`, `--mirror`, `--prune` o una referencia con `+`, también con opciones de git delante, como `git -C <carpeta> push --force`; fusionar o cerrar un PR (cerrarlo puede borrar su rama); los `gh` de releases que crean, también con su alias `new`, borran, editan, suben o descargan, este último porque escribe archivos en el equipo; los de ejecución de workflows y secretos; los de repositorios que crean, también con su alias `new`, borran, editan, renombran, archivan, desarchivan, bifurcan o sincronizan uno, o gestionan sus claves de despliegue y autolinks; los que borran issues, ejecuciones de workflows, cachés, etiquetas, gists, variables, proyectos, codespaces o claves SSH y GPG, o trasladan un issue, también con los alias `gh variable remove` y `gh cs`; `gh variable set` y `gh label clone`, que sobrescriben valores y etiquetas; todo `gh auth`, porque `gh auth token` y `gh auth status --show-token` muestran el token y `gh auth logout` corta el acceso; los que instalan, ejecutan, actualizan o quitan extensiones, con `gh extension`, `gh extensions` o `gh ext`; los que instalan, también con el alias `add`, actualizan o publican skills, con `gh skill` o `gh skills`, y todo `gh copilot`, que ejecuta su propio programa; todo `gh config`, porque `gh config get` puede mostrar el token si está guardado en el archivo de configuración y `set` cambia cómo se comporta `gh`; los de proyectos que borran elementos o campos, o cierran o desvinculan un proyecto; `gh codespace ssh` y `cp`, también con `gh cs`, que entran en un codespace o copian archivos entre él y el equipo; `gh alias set` e `import`, porque un alias puede esconder otro comando, aunque uno ya definido, como una extensión instalada, se invoca con su propio nombre y ninguna regla de texto lo alcanza; `gh api`, que llega a los mismos recursos; y `npm publish`, también con opciones delante. También la pide cualquier `gh` con opciones delante del grupo de comandos, como `gh -R <repo> pr merge`, o, en todos los grupos con reglas por subcomando (`pr`, `issue`, `release`, `run`, `cache`, `label`, `workflow`, `variable`, `repo`, `gist`, `project`, `codespace` y `cs`, `ssh-key`, `gpg-key` y `alias`), delante del subcomando, como `gh pr -R <repo> merge` o `gh repo --yes=true delete`, porque esas opciones no cambian el subcomando que se ejecuta y las reglas por subcomando no las alcanzarían; así la piden también los de solo lectura escritos de esa forma y `gh --version`. Las reglas de `git push` y `npm * publish*` comparan el texto del comando, así que también piden confirmación para comandos locales que lo contienen, como `npm run publish-docs` o un commit cuyo mensaje menciona `push --force`, y son solo una primera barrera: el hook de [Hooks de agentes](92-agent-hooks.md) cubre además los borrados con `:rama`, que ninguna regla de texto puede expresar porque Claude Code lee un `:*` final como su sintaxis de prefijo y no expande los demás `*` de la regla, las opciones cortas combinadas, como `git push -uf`, las referencias entrecomilladas, la configuración en línea y los remotos configurados como espejo o con una referencia forzada. Un `git push` normal, que solo añade al remoto, no la pide, aunque las reglas de aprobación siguen exigiendo autorización para hacerlo. Crear un PR no la pide, porque no destruye nada, aunque las reglas de aprobación siguen exigiendo autorización para abrirlo. Tampoco la piden las acciones locales: borrar archivos dentro del proyecto (`rm -r`), reescribir el historial (`git rebase`), borrar ramas ni descartar cambios sin commit (`git reset --hard`, `git clean`, `git checkout --`, `git restore`, `git stash drop`). Estas últimas pueden perder trabajo de otra sesión que git no recupera, así que las reglas de aprobación de las instrucciones siguen exigiendo autorización para ellas. También la pide `node .scripts/release.mjs`, con cualquier argumento, cuando se lanza sola desde la raíz: la regla compara el texto del comando, así que otra grafía (`node ./.scripts/release.mjs`) o un `cd` delante no la activa y la llamada corre confinada, con el efecto que describe el punto de `excludedCommands`. Publica una versión, con el push de la rama y del tag y el release, y como corre fuera del sandbox la confirmación es la única decisión de la persona antes de que empiece; el script no etiqueta hasta que el CI del commit pasa. Cada regla `deny` y `ask` tiene su gemela `PowerShell(...)`, porque en Windows Claude Code también ejecuta comandos con su herramienta PowerShell y una regla `Bash(...)` no la cubre.

Una exención de `excludedCommands` que un proyecto añada y que ejecute código del proyecto, como una suite E2E, un runner de pruebas, un script de paquete o `node .scripts/run-pinned.mjs` (npx con su caché en `.temp/npm-cache`), corre fuera del sandbox con el mismo riesgo, y esta protección no la cubre: un comando confinado puede reescribir ese código, que correrá sin confinar, y cambiar la versión de un paquete de Project Tooling, que `run-pinned.mjs` lee de `.docs/stack.md`. La exención de un runner de pruebas de extremo a extremo, con su riesgo y quién la declara, está en [Automatización de pruebas con agentes](98-agent-test-automation.md). Tampoco cubre al servidor de lenguaje de TypeScript, que corre fuera del sandbox y busca primero el `tsserver` del espacio de trabajo (`node_modules/typescript`), que los comandos confinados sí pueden escribir.

Las cachés de los gestores de paquetes viven bajo `.temp/` para no abrir escrituras fuera del proyecto. El `.npmrc` de la raíz fija `cache=.temp/npm-cache`, pero npm solo lee el `.npmrc` de su carpeta de proyecto, la más cercana hacia arriba con `package.json` o `node_modules`, o la actual si no hay ninguna, y resuelve esa ruta desde la carpeta en la que se ejecuta. Desde una subcarpeta, o con el repositorio dentro de otro proyecto de npm, usa otra caché: la de su configuración, fuera del proyecto, o `<subcarpeta>/.temp/npm-cache`. `node .scripts/run-pinned.mjs` no depende de eso: pasa a npm la ruta absoluta de `.temp/npm-cache` en la raíz, se ejecute desde donde se ejecute. Un proyecto con otro gestor apunta la caché de ese gestor a `.temp/<gestor>-cache` en su propio archivo de configuración; si no lo hace, el sandbox bloquea la escritura y el comando se repite fuera del sandbox con confirmación.

### Escrituras en carpetas temporales

`03-code-authoring.md` reserva `.temp/` para los temporales y pide confirmación para escribir fuera del proyecto. El sandbox de Claude Code deja escribir a los comandos confinados en la carpeta de trabajo, en un temporal por usuario y en los directorios añadidos, y fija `$TMPDIR` a ese temporal para ellos ([sandboxing](https://code.claude.com/docs/en/sandboxing#temporary-directories)). Las herramientas de archivo no pasan por el sandbox: el hook de alcance de escritura de [Hooks de agentes](92-agent-hooks.md) deniega sus escrituras en una carpeta temporal o en el scratchpad de la sesión, pide confirmación para las demás fuera del proyecto y, en la shell, deniega solo las escrituras evidentes en temporales.

`sandbox.filesystem` admite `allowWrite`, `denyWrite`, `denyRead`, `allowRead`, `allowManagedReadPathsOnly` y `disabled` ([ajustes](https://code.claude.com/docs/en/settings-reference#sandbox-filesystem)). Ninguna clave quita el temporal por usuario de las rutas escribibles ni lo redirige: `CLAUDE_CODE_TMPDIR`, que lo mueve, se ignora en el `env` de los ajustes de proyecto ([variables](https://code.claude.com/docs/en/env-vars)), y la documentación no dice si un `TMPDIR` en ese `env` prevalece sobre el que Claude Code fija a los comandos confinados. La única vía documentada sería un `denyWrite` sobre las carpetas temporales, que la plantilla no aplica porque no se ha probado y puede romper el propio Bash de Claude Code, Node, npm, pnpm o Playwright, que escriben ahí. Queda pendiente este experimento, en una copia desechable de un proyecto derivado y en una sesión nueva de Claude Code en cada sistema:

1. Añadir `"denyWrite": ["/tmp", "/private/tmp", "/var/folders", "/private/var/folders"]` (en Windows, el sandbox no existe) a `sandbox.filesystem` de `.claude/settings.local.json`.
2. Pedir al agente, uno por llamada: `pwd`, `cd .temp && pwd`, `node -e "console.log(require('os').tmpdir())"`, `node -e "require('fs').writeFileSync(require('os').tmpdir() + '/x', 'x')"`, `npm --version`, el gestor de paquetes del proyecto, la suite de pruebas y `node .scripts/browser.mjs` si el proyecto lo usa.
3. Repetirlo añadiendo `"env": { "TMPDIR": "<ruta absoluta del proyecto>/.temp/tmp" }`, con esa carpeta creada, y comprobar con `echo $TMPDIR` si los comandos confinados la reciben.
4. Adoptarlo solo si todos los pasos funcionan, o si fallan solo comandos que puedan repetirse fuera del sandbox con confirmación.

`permissions.blockWritesOutsideWorkingDirectories` hace que Write, Edit y NotebookEdit rechacen las rutas fuera de los directorios de trabajo ([ajustes](https://code.claude.com/docs/en/settings-reference#permissions-blockwritesoutsideworkingdirectories)), pero rechaza en lugar de pedir confirmación y deja escribible el scratchpad, así que la plantilla no la usa.

### Carpetas `.cc-writes` de Claude Code

Claude Code crea una carpeta vacía `.cc-writes`, dentro de una carpeta `.claude`, en cada carpeta a la que se mueve la shell de una sesión, también cuando un comando hace `cd` a una subcarpeta, y no la borra después. El sandbox protege contra escritura la de la carpeta en la que se abrió la sesión y `~/.claude/.cc-writes`. Git no muestra carpetas vacías, así que no aparecen en `git status`. El hook que borra directorios vacíos (`check-empty-dirs.mjs`, en [Hooks de agentes](92-agent-hooks.md)) las quita en cada mensaje, con la `.claude` que dejan vacía, aunque una regla de ignorado global las oculte; conserva la de la raíz y no entra en las carpetas que una regla de ignorado excluye, como `.temp/`, ni en las que no puede leer.

## Codex

No existe exención por comando. Las palancas son de sesión completa, en `.codex/config.toml` o por bandera de invocación:

| Ajuste | Efecto |
| --- | --- |
| `sandbox_mode` | `read-only`, `workspace-write` o `danger-full-access` |
| `[sandbox_workspace_write]` | `writable_roots`, `network_access`, `exclude_tmpdir_env_var`, `exclude_slash_tmp` |
| `approval_policy` | cómo escala a aprobación del usuario un comando denegado |
| `default_permissions` | perfil de permisos por omisión; `:danger-full-access` desactiva el confinamiento |

La plantilla no declara `sandbox_mode` en `.codex/config.toml`, así que Codex usa sus valores por omisión; se dejó fuera deliberadamente al configurar el sandbox de Claude Code. Por la misma razón, `node .scripts/run-checks.mjs` no tiene en Codex la exención que tiene en Claude Code.

Tampoco quita los temporales de las rutas escribibles. `exclude_tmpdir_env_var` y `exclude_slash_tmp` solo rigen cuando una capa fija `sandbox_mode` o se usa `--sandbox`; si no, Codex aplica perfiles de permisos, y el perfil `:workspace` deja escribir en los temporales del sistema ([permisos](https://learn.chatgpt.com/codex/permissions)). Un perfil que extiende `:workspace` con `":tmpdir" = "deny"` y `":slash_tmp" = "deny"` sí los bloquea: con `codex sandbox -P`, un `node` que escribe en `os.tmpdir()` o en `/tmp` recibe `EPERM` con ese perfil y escribe sin error con `:workspace`, aunque se le pasen `exclude_tmpdir_env_var` y `exclude_slash_tmp`; con ese perfil, además, `npx` se quedó sin responder. La plantilla no lo aplica, porque rompe herramientas que escriben en el temporal y la documentación no confirma que un `.codex/config.toml` de proyecto pueda fijar `default_permissions`. El hook de alcance de escritura deniega en Codex las escrituras evidentes en temporales, y las demás siguen las aprobaciones de Codex.

Codex sí evalúa reglas por comando, con las decisiones `allow`, que ejecuta el comando fuera del sandbox sin preguntar, `prompt` y `forbidden`, en archivos `.rules` dentro de una carpeta `rules/` de cada capa de configuración, como `~/.codex/rules/` o la carpeta `rules` de `.codex` en el proyecto, que solo se carga si la persona confía en la capa `.codex/` del proyecto. Su documentación las marca como experimentales, así que la plantilla no declara ninguna: no hay equivalentes de `permissions.deny`, `permissions.ask` ni `permissions.allow`, y en Codex esas confirmaciones dependen del `approval_policy` y del sandbox de cada persona.

El sandbox de Codex protege `.codex/` y `.git/`, pero deja escribir `.claude/settings.json`, `.mcp.json` y `.scripts/` (comprobado con `codex sandbox -P :workspace`) y, como no lo protege, también `.claude/settings.local.json`. Un comando que Codex ejecute sin preguntar puede cambiar los hooks y los permisos de Claude Code, que los ejecuta sin aprobación previa; al volver a Claude Code después de usar Codex, revisa `git diff .claude/settings.json`. El sello de un derivado restaura `.claude/settings.json`, pero no `.claude/settings.local.json`, donde van los ajustes propios del proyecto o de la persona: git lo ignora, así que `git diff` no lo muestra y tras usar Codex se revisa también ese archivo a mano. Esa brecha de Codex sigue abierta: la plantilla no aplica ningún perfil de permisos, porque solo los perfiles beta (`default_permissions` con `[permissions.<nombre>.filesystem.":workspace_roots"]`) permiten dejar una subcarpeta de solo lectura, la documentación no confirma que un `.codex/config.toml` de proyecto pueda fijar `default_permissions`, y ampliar `:workspace` ensancharía un valor por omisión de solo lectura. El hook de rutas protegidas de [Hooks de agentes](92-agent-hooks.md) la cierra solo en parte: en Codex rechaza las escrituras de shell evidentes sobre las rutas de `denyWrite` (`.scripts/`, `.agents/tool-versions.json`), pero no sobre `.claude/settings.json`, que `denyWrite` no lista, ni lo que escriba un programa; en un derivado, donde ese archivo está sellado, el hook del sello lo restaura en el mensaje siguiente, pero no impide que lo escriban antes. Una persona puede definir uno en su propia configuración de Codex; Codex lo ignora mientras haya un `sandbox_mode` fijado o se use `--sandbox`. A la inversa, el sandbox de Claude Code ya no deja escribir `.codex/`, y Codex vuelve a pedir la aprobación de un hook que cambió, como explica [Hooks de agentes](92-agent-hooks.md).

## Caso conocido: navegadores bajo macOS

Chromium registra un puerto Mach al arrancar su propio sandbox. Seatbelt —el sandbox de macOS sobre el que se apoyan estos clientes— lo deniega, y cualquier runner que lo controle falla con `Permission denied` antes de levantar la aplicación. Una aplicación Electron, que lleva Chromium dentro, falla igual (comprobado: `bootstrap_check_in …MachPortRendezvousServer…: Permission denied`).

El mensaje parece un arranque E2E roto y no lo es: ningún cambio en la configuración de pruebas, en los navegadores instalados ni en las rutas de caché lo corrige. Tampoco `sandbox.network.allowMachLookup`, que la documentación oficial cita para Playwright: permite buscar servicios Mach, no registrarlos, y Chromium falla al registrar el suyo con `bootstrap_check_in` (comprobado en macOS con `allowMachLookup: ["*"]`). La única salida es que el comando quede fuera del sandbox.

Para las sesiones de navegador del agente, `.claude/settings.json` exceptúa `node .scripts/browser.mjs *`, también en un derivado, donde el archivo está sellado, el lanzador que describe [Skills de agentes](90-agent-skills.md): ejecuta el `cli` de Playwright en la versión fijada y solo deja pasar los comandos que manejan la página, sin ejecutar código fuera del navegador. Sin `--filename`, lo que escribe la sesión queda en `.temp/playwright-cli`, que `filesystem.denyWrite` protege. Con `--filename`, o con el archivo de `state-load`, `state-save` o `video-start`, Playwright escribe en esa ruta relativa a la raíz, que el lanzador comprueba una sola vez antes de lanzar el comando: un proceso confinado que corra a la vez podría sustituir una carpeta de esa ruta por un enlace durante el comando y redirigir esa escritura, aunque solo crea o sobrescribe el archivo con el nombre que eligió el agente. Como corre sin confinar, sus propios scripts, `browser.mjs`, `browser-args.mjs`, los `browser-capture*.mjs` y `npm-cli.mjs`, viven en `.scripts/`, que `filesystem.denyWrite` protege, así que un comando confinado no puede reescribirlos. También lee de `.agents/tool-versions.json`, protegido por `filesystem.denyWrite`, la versión y el hash de integridad de `playwright` (`X.Y.Z`, del registro de npm, instalada con `--ignore-scripts`): un comando confinado ya no puede elegir qué versión instala y ejecuta el lanzador, que en cada arranque compara la versión y la integridad que npm dejó en `node_modules/.package-lock.json` para `playwright` y para cada dependencia exacta que el archivo registra en `dependencies` (`playwright-core`) con lo registrado, sin volver a calcular el hash del contenido, y falla si ese archivo lista una copia anidada de uno de esos paquetes, que Node cargaría en su lugar, y da por buena la carpeta porque un comando confinado no puede escribirla; si no coinciden, borra la carpeta y reinstala, y no ejecuta la CLI si la instalación nueva tampoco coincide. Queda abierto, con exactitud: las herramientas Edit y Write no pasan por el sandbox y pueden editar ese archivo, versión y hash incluidos, de modo que quien las controla sigue pudiendo elegir la versión, y solo el cambio visible en el diff, la revisión y la aprobación de edición del cliente lo detienen; `--check` valida la forma del archivo, no su contenido; el refresco comprueba la atestación que publica el registro, no su firma; el hash recoge `playwright` y las dependencias que este fija por versión exacta, no las transitivas ni las declaradas con rango, que npm resuelve del registro configurado sin comparación; y `run-pinned.mjs`, que ejecuta con `npx` los demás paquetes del archivo, toma de él la versión pero no comprueba el hash de lo que descarga. Playwright vive en una caché propia de cada persona fuera del repositorio y del temporal del sistema, que el sandbox no deja escribir, se instala lanzando npm desde esa carpeta, y la configuración de la CLI tiene que ser la esperada. El subcomando `capture`, que mide la página con los mismos comandos y las mismas comprobaciones, lee además sin confinar `capture.config.json` de `.playwright/`, que `denyWrite` no protege y un comando confinado puede escribir, así que lo valida de forma estricta y falla cerrado (claves, tipos, rangos, tamaño, sin enlaces simbólicos), y escribe solo bajo `.temp/playwright-cli/<etiqueta>/`, la carpeta de salida protegida ([Captura y medición del navegador](90-agent-skills.md#captura-y-medición-del-navegador)).

Como cualquier exención, solo sale la invocación lanzada sola desde la raíz; un navegador que abre otro script confinado, como los checks de un plan de `prompt-plan`, sigue confinado y necesita la aprobación puntual del cliente. El navegador que abre corre sin confinar y su sesión sigue viva entre comandos, pero un cliente confinado no la alcanza: en macOS, `node .scripts/run-pinned.mjs playwright cli -s=<sesión> …` lanzado dentro del sandbox responde que esa sesión no está abierta, así que un comando que el lanzador rechaza no le llega por otra vía sin aprobación. En Linux no está comprobado si Chromium arranca confinado, y la exención se aplica igual; en Codex no hay exención por comando, así que el lanzador pide la escalada de su sandbox como cualquier otro comando.

Sin exención, o lanzado en una forma que la deja confinada, como dentro de un comando compuesto, el lanzador falla dentro del sandbox: la caché por usuario donde instala Playwright no es escribible allí (`fs.accessSync` sobre ella lanza `EPERM` en macOS, y sin la comprobación `mkdir` falla con `EPERM` sin más pista). Por eso, después de comprobar los argumentos y la configuración y antes de instalar o ejecutar nada, comprueba que puede escribir esa carpeta, o el ancestro existente más cercano si aún no existe, y si no puede sale con código 1 y un mensaje en `stderr` que dice `cannot write its cache <ruta>`, que lo más probable es que corra dentro del sandbox del cliente y que debe lanzarse solo, desde la raíz del repositorio, para que aplique la exención, o con la aprobación del cliente. Ese mensaje no es un rechazo del comando: la solución es cómo se lanza, no el comando.

## Caso conocido: simuladores de iOS bajo macOS

Comprobado en macOS con Claude Code, dentro del sandbox: `xcrun simctl list` falla con `CoreSimulatorService connection became invalid` y `Failed to initialize simulator device set`, y una corrida de WebdriverIO con Appium responde `Unknown device or simulator UDID` para un simulador que existe y está arrancado; fuera del sandbox la misma corrida pasa. El servicio de simuladores no es alcanzable desde el sandbox, y ningún ajuste documentado del sandbox lo corrige, así que la única salida es que el comando quede fuera de él.

La plantilla trae `node .scripts/device.mjs`, el lanzador que describe [Skills de agentes](90-agent-skills.md#lanzador-de-dispositivos-móviles), pero no lo exceptúa: un proyecto que automatiza una aplicación móvil añade `node .scripts/device.mjs*` a su `sandbox.excludedCommands`, con la autorización explícita que exige `AGENTS.md`. Como cualquier exención, solo sale la invocación lanzada sola desde la raíz. El lanzador corre sin confinar, así que valida sus argumentos con una lista cerrada, y sus scripts están en `.scripts/`, que `filesystem.denyWrite` protege; el detalle de lo que garantiza y no garantiza está en su sección. Los emuladores de Android bajo el sandbox no están comprobados todavía: no se afirma aquí que arranquen ni que fallen allí, y la exención del lanzador se aplica igual a ese caso hasta que se compruebe.

## Caso conocido: vigilancia de carpetas bajo macOS

Node, a través de libuv, vigila una carpeta con FSEvents y un archivo suelto con kqueue. Seatbelt deniega la búsqueda del servicio `com.apple.FSEvents`, el flujo de eventos no arranca y libuv lo informa como `EMFILE: too many open files, watch` (`errno -24`) en el evento `error` del watcher, aunque no falte ningún descriptor: subir `ulimit -n` no cambia nada. Le pasa a cualquier servidor de desarrollo o modo `watch` que vigile carpetas, también al servidor web que levanta un runner E2E; vigilar un archivo suelto sigue funcionando. Comprobado en macOS: un `fs.watch` de carpeta falla dentro del sandbox de Claude Code y funciona fuera, y uno de archivo funciona dentro.

A diferencia del caso de los navegadores, aquí basta una búsqueda: añadir `com.apple.FSEvents` a `sandbox.network.allowMachLookup` es la corrección que adoptaron otros sandboxes basados en Seatbelt, aunque no está comprobada con Claude Code. Su coste es que el flujo de eventos puede informar de rutas, no de contenidos, de archivos cambiados fuera de lo que el sandbox deja leer. La plantilla no lo declara; un proyecto que lo necesite lo registra entre sus exenciones, o usa el modo de sondeo (polling) de su watcher, o ejecuta el comando fuera del sandbox. En Codex el sandbox deniega la misma búsqueda, según su incidencia abierta [openai/codex#15698](https://github.com/openai/codex/issues/15698), y no hay un ajuste equivalente.

## Caso conocido: inspección de procesos

Un comando confinado no puede listar procesos: `ps` falla con `operation not permitted` y `pgrep` con `Cannot get process list`, porque no alcanza el servicio `sysmond`; `lsof` omite sin error los procesos que no inició el propio comando, así que un resultado vacío no prueba que el puerto esté libre. Así, un script o una prueba que identifica procesos por nombre, por su línea de comandos o por su puerto, como el que detiene un servidor de desarrollo o detecta otra instancia, concluye que no existen. Comprobado en macOS con Claude Code. Para saber si una corrida está en curso no se inspeccionan procesos ni puertos: se usa el bloqueo de corridas de [Automatización de pruebas con agentes](98-agent-test-automation.md#bloqueo-de-corridas). Para `ps` no hay ajuste del sandbox, y no está comprobado si añadir `sysmond` a `allowMachLookup` bastaría para `pgrep`. La salida es exceptuar el comando que lo necesita, con el riesgo que describe la sección de Claude Code para las exenciones de un proyecto; en Codex, que tampoco deja ejecutar `ps` dentro de su sandbox, ese comando pide la escalada.
