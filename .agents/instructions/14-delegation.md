# Delegation

Read before planning a normal or risk change, before work that needs a search or more than two tool calls, and before delegating to a subagent.

- At every change level, and for questions, the session reasons, answers, decides, writes the specification, briefs subagents, checks what they return, handles approvals and questions to the user, and reports; it delegates execution.
- Run in the session only a task of at most two tool calls on a known target with short output, such as reading a known file, one command, or an edit to a file already read, counting the calls of the whole task, never of a step cut out of it, and hand the whole task to a subagent as soon as it needs a third call.
- Delegate everything else: searches without a known target, exploration, reads of long or several files, commands with long output, implementation, and any task of three or more tool calls; for a question that needs such reading, delegate the reading and reason over what returns.
- Beyond that limit, run in the session only edits or checks a subagent's environment cannot perform, such as agent permission files, and the work the tier rules below assign to it, name each with its reason in the report, and report any other direct execution as a deviation.
- Start every delegated task at the fast tier: creating or moving files and folders, searches, exploration, reads that confirm a claim, mechanical or fully specified edits with every change spelled out in the brief, single commands, documents updated from given facts, and authorized version-control operations.
- Raise a task above the fast tier only for a reason the session names: implementation or debugging that needs judgment against the fixed specification, risk changes included, takes the standard tier; implementation beyond the standard tier, reviews, difficult decisions, unresolved root causes, risk-area design, and independent verification take the strong tier; and a task moves one tier up when its result fails for lack of capability or a review rejects its fix again.
- When unsure which tier fits a task that changes behavior, take the higher; a task that only gathers facts or applies spelled-out edits stays at the fast tier.
- Split a task that spans tiers and send its mechanical part to the fast tier, unless that part is at most two tool calls for the subagent doing the rest.
- Use the agents the repository declares, as the agent-subagents `.readme/` document maps them to tiers; send the work of a tier the client does not map to the next tier up it maps, and run it in the session only when it maps none above.
- When the session runs on a model below a tier's, or on the same model at no higher effort, do that tier's work in the session instead of delegating it upward, except independent verification, which still needs a clean context.
- Launch each declared agent without the session's history when the client would pass it by default, except a copy of the session, so that it starts from fresh context.
- When the client offers a copy of the session that inherits its context and runs on its model, use it only for a parallel task that needs the context already gathered, that a brief cannot carry without losing it, and that justifies the session's model; never for searches or mechanical edits.
- Give the independent tasks of one tier that are ready at the same time a single brief, since each delegation costs the session a brief and a result to read, except independent verification and, once the session has fixed the contracts and shared files they build on, tasks that write disjoint files, which get a brief each.
- Continue a subagent that is still available, instead of launching another, when the next task of its tier builds on what it already read; never for independent verification.
- Run independent briefs in parallel, except those that start services or seed or mutate shared local state; briefs running in parallel in one working tree run only the checks scoped to their own files, and the session runs the full checks once all return.
- Run tasks at the same time in one working tree only when they write disjoint files, and give a task an isolated working tree only when it starts from the revision and the uncommitted changes the task needs.
- Keep each brief as short as the task allows: the complete task, what the session has already ruled out, its constraints, acceptance criteria, and paths, pointing to the files and lines that give context instead of copying them.
- Require in each brief a final message of a stated maximum length with concise findings, file paths, the path and line behind each conclusion, changes made, and open issues.
- Require in each brief that the subagent bounds and stops every background process it starts and lists in its final message any it started that still runs; stop each one listed before accepting the result.
- Delegating never widens authorization: a version-control write, a deploy, or a destructive operation a subagent runs needs the user's explicit authorization for it, stated in its brief.
- When the client does not let the session wait for a subagent, continue with work that does not depend on it, and neither report nor assume its result until it arrives.
- When relaying to the person an approval a subagent requests, ask for it only for that action and warn that a broader grant reaches the whole session.
- Check a subagent's result without redoing its work: read the diff of what it changed, sample the lines its findings cite when a decision or an edit depends on them, and return a result that lacks that evidence to the subagent instead of gathering it in the session.
- Summarize a subagent's result for the user instead of repeating it, and never delegate approvals, decisions owed to the user, or the final report.
- Close a change's report with the distribution: the tasks sent to each tier, one sentence of reason for each above the fast tier, and the tasks the session ran itself.
