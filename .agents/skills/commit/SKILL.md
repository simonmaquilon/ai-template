---
name: commit
description: Split staged changes grouped by commit.
---
 
Analyze the staged changes and group them by commit type (feat, fix, docs, style, refactor, perf, test, chore, ci, build, revert). For each group, produce exactly one commit message following this exact structure, with no deviations: FIRST, inspect the current branch name and attempt to extract a work item number by checking whether the branch name starts with the literal prefix feature/ followed immediately by one or more digit characters (0 through 9); the extracted work item is the sequence of digits that appears right after feature/ and stops at the first non-digit character or at the end of the branch name — for example, the branch feature/1234 yields 1234, the branch feature/5678-add-login yields 5678, and the branch feature/99 yields 99; ONLY IF the branch name starts with feature/ AND at least one digit appears immediately after that prefix, prepend a separate line in the literal format Related to WI- followed immediately by those extracted digits (for example, Related to WI-1234), then exactly one blank line, then the commit message; if the branch name does not start with feature/, or the character immediately after feature/ is not a digit, or is any other branch type such as bugfix, hotfix, release, main, develop, or master, you MUST completely skip and omit the entire Related to WI line — do not output it, do not output a blank line in its place, do not output Related to WI- with nothing after it, do not output Related to WI- followed by any placeholder token, do not output Related to WI-TBD, do not output Related to WI-0, do not output any placeholder text, angle brackets, template tokens, or guessed values under any circumstance, and proceed directly to the commit message as the first line of output; the literal characters less-than and greater-than (angle brackets) must NEVER appear in the final output; then include the commit message in the format type(module): imperative summary, followed by exactly one blank line and a short paragraph that states why the change was made, and then, when bullets apply, exactly one more blank line and a bulleted list where each bullet starts with a hyphen and a space and describes one concrete change. Rules: module must follow the scope that the repository's existing commit history uses for that kind of change; only when the history shows no such convention, use the lowercase name of the specific feature, domain, or directory most affected, written in kebab-case when it spans multiple words (for example, seed-demo-users, never seed_demo_users or seedDemoUsers); the summary must use imperative mood (for example, add, fix, remove, not added or fixes); each bullet must describe a concrete change made in this commit in imperative mood starting with a verb (for example, add, update, remove, rename), and every meaningful change must appear as its own bullet without generic phrasing such as various changes or misc updates; the Related to WI- line is strictly conditional on a successful extraction from a branch whose name starts with feature/ followed by at least one digit — never fabricate, infer, or default this value, and never output it as a template; when present, the Related to WI- line must contain only actual extracted digits after the hyphen, must appear alone on its own line, and must be followed by exactly one blank line before the first commit message; separate multiple commit messages with exactly two blank lines; include the bullet list only when the change has non-obvious context or covers multiple discrete edits, and skip the bullets for chore, style, docs, and build types when the summary and the why paragraph suffice; omit numbered lists, bullet nesting, git add commands, and any prose outside the format.
 
After that, execute the commands by yourself.
