# Execution

The rest of the Execution rules of [SKILL.md](../SKILL.md), whose first rule holds throughout: nothing here runs until the user asks. [plan-workspace.md](plan-workspace.md) defines the folders and scripts these rules use.

## Answers

- When the person an open decision names, or the user when it names none, answers it, or the user supplies a pending datum, record the answer before the fragments it governs run or resume: in each of them, and in `rules.md` when it governs every change, replace the options, or the placeholder, with the answer, naming who decided and the date, and write or update the checks that depend on it. A choice the prompt leaves to the executor is made the same way, by the first fragment it governs, before that fragment's tests: record the choice and its reason where an answer would go, naming the executor as the one who chose, and write the checks that depend on it, which the dry-run rule then runs.
- When the user revises an answer that a `done` fragment already carried out, the first fragment that is not `done` carries the revised criterion with its own identifier, or, when every fragment is `done`, a new fragment does, added as the rule on changes to `done` fragments says. Right after its `record NN before`, or first when the plan has no `patch/`, that fragment updates the checks and project tests of `done` fragments that assert the replaced answer, so they follow the revised answer's wording and threshold and are otherwise as strict as before. It records each correction to an `NN-check` script or `helpers` as `check/` does, with the revision as its evidence, and those updated lines and tests join its tests-before run. When that fragment is restored or dropped, its corrections are undone, and a retry makes them again. The report line of the replaced criterion keeps its last status and names the criterion that replaces it.

## Done fragments

- Edit only fragments that are not `done`, `rules.md`, and the index. A change to `rules.md` applies to the fragments not yet `done`; one that would change what a `done` fragment required is a change to that fragment.
- `done` fragments, their patches, and their states never change, and no record of theirs is taken again. A change to what a `done` fragment requires, including a file it missed, becomes a new fragment: placed before the one that holds the final run and the closure audit while that one has no `record NN before`, and otherwise after it, followed by a new fragment that repeats the final run and the closure audit. A large change becomes a new plan.
- Fragment numbers never change, with two exceptions: the fragment that holds the final run and the closure audit takes the next free number when fragments are added before it while it has no `record NN before`, and a `blocked` fragment passed over under the next section takes the next free number when it runs after a later fragment has a record. Its build file and scripts, the number each script passes to `lib`, the index, and the dependencies follow the new number, while evidence already saved keeps its name.
- A correction made while a later fragment runs, such as one the closure audit or its reviews ask for, stays in that fragment's patch even when it touches files a `done` fragment changed, since the patches still apply in order, unless it needs a comparison with the tree before the applied fragments, which goes to a new fragment as `check/` says.
- Any other change to a `done` fragment, its patch, or its state stops the execution: report it as a ⏸ line, with the running fragment, or else the next pending one, `blocked` until the user decides. `record NN before` refusing because files of earlier fragments match no recorded state, or stay on disk while the index no longer tracks them, is such a change.

## Order

- A stop these rules make until the user decides holds in every session, under a deferral as well: a deferral settles the prompt's questions, never what the execution finds, so report the stop as ⏸ and wait, and a session that cannot receive a reply ends its execution there with that report.
- Take fragments in order, and stop at the first `failed` one, and at the first `blocked` one that has its `record NN before` or that a later fragment depends on, other than the one that holds the final run and the closure audit, until the user resolves it.
- Pass over any other `blocked` fragment: it has no record, so `apply` and `revert` count around it. The plan places fragments that wait on a decision or a pending datum as late as their dependencies allow, before the one that holds the final run and the closure audit, as `build/` says.
- When only passed-over fragments remain before the one that holds the final run and the closure audit, that one runs, unless it is `blocked` itself, and its closing report carries each open decision, with the criteria that wait on it, as ⏸ pending, as the prompt's rule on open decisions lets the rest of the work proceed.
- A passed-over fragment runs once the user resolves what it waits on: in place while no later fragment has a record, and otherwise under the next free number, followed, when the fragment holding the final run and the closure audit already ran, by a new fragment that repeats them. While a fragment that stops the execution stays `blocked`, the ⏸ report, which names each open decision, stands in for the closing report.

## Running a fragment

- After any dry run or `--baseline` run that the dry-run rule or `check/` requires before it, first run `record NN before` when the plan has `patch/` and the fragment has none yet, before writing any of its tests or changes to project files, so its patch captures them; a fragment resumed after `blocked` or retried after `failed` keeps the one it already ran.
- `record NN before` lists the untracked files version control does not ignore. When one of them is a file this fragment's work already wrote, delete `NN.before` and `NN.untracked`, move the file to the prompt skill's temporary location, run `record NN before` again, and put the file back, so `record NN after` can adopt it. A tracked file this fragment's work changed before its `record NN before` cannot enter its patch: report it as ⚠️ outside every patch, which the reviews and the closure audit read with the patches.
- Then, with or without `patch/`, check whether the completed fragments already deliver part of its change. When they do, turn those tests and check lines into guards, editing this pending fragment, its tests, and its `NN-check` script while keeping each criterion's wording and threshold and never making a test or check more permissive, cite the evidence, such as a test, a check line, or a log of a completed fragment, and report it.
- Then add its tests, if it carries any, and run, under the limits `check/` scripts follow, those that test the behavior it changes, together with the guards it adds. Tests of behavior that already holds before it and that it keeps unchanged, written against an interface that exists before it, are guards, not tests of the change; a test of behavior it restores or extends, such as a regression the closure audit found, is a test of the change. Store that run in `review/` as `NN-tests-before-<UTC timestamp>`. A guard that fails only because the file holding the new tests cannot load before the change, as when it imports a name the change adds, is no failed guard: make that file load, for example by importing the module as a whole, keeping every test's wording and threshold, and run the tests again. When any test of the change already passes without such evidence, or a guard fails, stop without running `record NN after`, report it, and mark the fragment `blocked` until the user decides.
- A fragment whose changed behavior a check measures, alone or with tests, runs the lines of that check that measure it as part of its tests-before run, and that `NN-check` log, which the report cites next to the tests-before log as run before the implementation, is the evidence. A fragment that only measures a baseline, reruns validations, or closes the plan has no tests-before run: the first run of its check or measure script, other than the dry run, is its evidence. When it passes, the fragment changes nothing; when a line fails, the fragment corrects it like any other, within the same limits, except that a fragment that only measures a baseline changes no project file and corrects only its measure script or `helpers`, as `check/` allows.
- Only then implement it. Run the checks of this and every completed fragment with `all NN`, adding `--slow` when the fragment changes what a slow line of an earlier fragment measures, such as what the project renders, and in the fragment that closes the plan. Correct its implementation until they pass, without changing its criteria, tests, or checks except as `check/` allows for a script shown not to measure its criterion, within the stop conditions the improved prompt and the project's rules set. When neither limits the corrections to a fragment's implementation, the closure audit's own limit not counting, the limit is three correction cycles, each a correction followed by an `all NN` run.
- All of this happens between `record NN before` and `record NN after` when the plan has `patch/`, so `record NN after` runs only once the checks pass.
- A commit at the end of a fragment, which only the user can authorize, directly or through the prompt, never a project rule alone, is made once its other checks pass and before `record NN after`, which a commit does not affect; rerun the checks after it. On a file system that ignores case, such a commit never includes a rename that only changes case, which waits until after closing, once no fragment remains to run. Such commits stay in history when fragments are reverted later.

## Recording the fragment

- `record NN after` adopts, with `--include`, every file this fragment's work wrote, there or first elsewhere, such as a draft it wrote in the temporary location and moved in. A file it moved whose original the before snapshot holds, as a tracked file or one an earlier fragment adopted, is adopted under its new name, since `revert` brings the original back, unless `--include` refuses that name. When it lies inside a folder `NN.untracked` lists as one name, record without it: the patch carries only the deletion, which `revert` undoes, and report the new name as ⚠️ outside every patch. On a file system that ignores case, a rename that only changes case, of a file or of a folder, stays outside the plan, since `apply` and `revert` cannot replay it there: a plain `mv` records nothing of it, which `record NN after` reports as renamed only in case; `record NN after` refuses one `git mv` recorded, so move it back to the old spelling first. Report it as ⚠️ outside every patch; it is made after closing, once no fragment remains to run, by the user or through a commit the prompt authorizes then, and to run a fragment later, or to revert or apply, move the rename back to the recorded spelling first. A file of the user's it moved whose original the before snapshot does not hold, because it was untracked there or outside the working tree, takes `--leave` instead, since `revert` would delete the new copy without bringing back the original; `record NN after` lists as gone such a file the before record named by its own name. It leaves out, with `--leave`, each new untracked file that is no part of its change, such as a generated report version control does not ignore. It refuses until every such new file is one or the other. Report the files left out as ⚠️ outside every patch. Taking a file out of the index while it stays on disk, as `git rm --cached` or a commit that stops tracking it does, stays outside the plan, since no patch can carry it: `record NN after` refuses such a file until `git add -- <file>`, with `-f` for an ignored one, tracks it again; report it as ⚠️ outside every patch, and it is made after closing, once no fragment remains to run, by the user or through a commit the prompt authorizes then. A file deleted from disk as well, as by `git rm` or `git mv`, is recorded as deleted; one the fragment removed with `git rm` that a build or install, such as one its checks run, wrote again looks taken out of the index, so delete it again before `record NN after`. Later it counts for what it holds where some point of the fragment sequence fits the files that way, as when it is rebuilt with the bytes it held before the fragment removed it, which reads as that fragment reverted, so `apply` deletes it again; where none fits, it counts as absent, and `revert` refuses to write over it until it is moved aside.
- An untracked file the working tree held by its name at `record NN before` can be neither adopted nor carried by any patch, even when the prompt authorizes the fragment to start tracking it: report it as ⚠️, and version control tracks it once a commit the prompt authorizes adds it.
- Right after each `record NN after`, read what it reports. The files it lists as changed between the previous recorded fragment's `afterTree` and this fragment's `beforeTree` changed outside every fragment's work between the two records, unless this fragment's work changed them before its `record NN before`, as the second rule of the previous section handles. Report both as ⚠️ outside every patch, as well as the files it lists as gone since the before record or as staged although the before record held them, nested repositories' own uncommitted work, and files renamed only in case; a nested repository the fragment changed, which no patch carries, also makes `apply` and `revert` refuse it later, so set it by hand as their refusal says. Fragment `01` has no earlier record, so a file its work changed before `record 01 before` cannot be told apart from a change made before the plan.
- Then compare the files `NN.state` lists with those this fragment's work wrote: one it did not write, such as a file another session edited meanwhile, is reported as a ⏸ line, and the fragment is `blocked` until the user decides whether its patch keeps that change.
- When the prompt carries the concurrency rule, run `revert`, `apply`, or `record NN restore` only after confirming that no other session is editing the files their patches list or, for `restore`, the files this fragment's work changed.

## Failed and dropped fragments

- A fragment whose checks still fail at a stop condition is `failed` and gets no `record NN after`: its changes stay in the working tree for the user. A retry first restores, with the user's consent, the files to the tree `record NN before` captured, through `record NN restore` when the plan has `patch/`, or as the user directs otherwise. `record NN restore` refuses, before writing, a file of the before snapshot that stays on disk while the index no longer tracks it, until `git add -- <file>`, with `-f` for an ignored one, tracks it again; the restore then writes the before snapshot's contents over it, so keep first a copy of any such file that holds work that is not this fragment's. It leaves every untracked file the fragment did not adopt, and every file staged during the fragment that the before snapshot lacks, and lists the new ones, so delete those this fragment's work wrote and unstage with `git rm --cached -- <file>` those it staged. It also lists the files staged that the working tree held untracked by name, so unstage each and put back by hand any this fragment's work changed, and the files it writes back that the index no longer tracks, as after `git rm` or `git mv` during the fragment, so track each again with `git add -- <file>`, with `-f` for an ignored one.
- A fragment the user drops after its `record NN before` is restored the same way; then delete its `NN.before` and `NN.untracked` with its build file and scripts.

## Environment and evidence

- When the sandbox blocks a tool a check needs, keep that tool's home and caches in the plan's `.cache/` (the bundled `lib` offers it), and launch a browser through the client's one-off approval outside the sandbox, except in a dry run, which follows the prompt skill's `Sandbox` limit; never widen sandbox settings.
- Store the evidence in `review/`, applying the gates each fragment and `rules.md` carry and the closure audit at the end. A question a review asks is reported as a ⏸ line, in the chat and in `review/report.md`, and the execution goes on, unless a criterion cannot close without its answer, which makes the fragment `blocked`.
