# Execution

The rest of the Execution rules of [SKILL.md](../SKILL.md), whose first rule holds throughout: nothing here runs until the user asks. [plan-workspace.md](plan-workspace.md) defines the folders and scripts these rules use.

## Answers

- Ask what the execution must ask the user, such as an open decision's options or a stop these rules make, as the Questions rule of step 5 of [the prompt skill](../../prompt/SKILL.md) asks: through its question mechanism, in the language the user writes in the conversation, in one round, with the recommended option first whenever the evidence gathered so far gives a reason to prefer it. A statement in the plan that no option is favored yet describes the preparation, not the user's wish, and binds no later recommendation.
- Record decisions once in the numbered decision register in `build/rules.md`. Use one sentence per decision with its author and reason. The fragments and report refer to the ID; update dependent checks before execution. A choice explicitly delegated by the user is labeled delegated. A proposal to change the user's prior decision cites its ID and stays pending until the user confirms it explicitly. When the user supplies a pending datum, record it there, replace its placeholders in pending fragments, and update the checks those fragments depend on.
- A choice the prompt leaves to the executor is made by the first fragment it governs, before that fragment's tests: record the choice and its reason in the register, naming the executor as the one who chose, and update the checks that depend on it, which the dry-run rule then runs.
- When the user revises an answer a `done` fragment used, put the revision under a new linked decision ID. Carry it into the first eligible pending or new fragment and update checks with that fragment. Preserve the recorded fragment and its historical evidence.
- The fragment that carries a revised answer updates, right after its `record NN before`, the checks and tests of `done` fragments that assert the replaced answer, as strict as before, recording each correction of an `NN-check` script or `helpers` as `check/` does; restoring or dropping that fragment undoes the corrections, and a retry makes them again.

## Done fragments

- Edit only fragments that are not `done`, `rules.md`, the index, and `README.md`. A change to `rules.md` applies to the fragments not yet `done`; one that would change what a `done` fragment required is a change to that fragment.
- `done` fragments, their patches, and their states never change, and no record of theirs is taken again. A change to what a `done` fragment requires, including a file it missed, becomes a new fragment: placed before the one that holds the final run and the closure audit while that one has no `record NN before`, and otherwise after it, followed by a new fragment that repeats the final run and the closure audit. A large change becomes a new plan.
- Fragment numbers never change, with two exceptions: the fragment that holds the final run and the closure audit takes the next free number when fragments are added before it while it has no `record NN before`, and a `blocked` fragment passed over under the next section takes the next free number when it runs after a later fragment has a record. Its build file and scripts, the number each script passes to `lib`, the index, and the dependencies follow the new number, while evidence already saved keeps its name.
- A correction made while a later fragment runs, such as one the closure audit or its reviews ask for, stays in that fragment's patch even when it touches files a `done` fragment changed, since the patches still apply in order, unless it needs a comparison with the tree before the applied fragments, which goes to a new fragment as `check/` says.
- Any other change to a `done` fragment, its patch, or its state stops the execution: report it as a ⏳ line, with the running fragment, or else the next pending one, `blocked` until the user decides. `record NN before` refusing because files of earlier fragments match no recorded state, or stay on disk while the index no longer tracks them, is such a change.

## Order

- A stop these rules make until the user decides holds in every session, under a deferral as well: a deferral settles the prompt's questions, never what the execution finds, so report the stop as ⏳ and wait, and a session that cannot receive a reply ends its execution there with that report.
- Before opening a dependent plan's first record, compare the delivered predecessor with the successor's recorded assumptions about revision, routes, contracts, stored state and checks. Record each discrepancy, revise only pending fragments in scope, and dry-run affected checks against the delivered base. Stop at a decision outside the existing authorization.
- Size a fragment so one executor can deliver and verify a reversible result within its context. Split a large fragment before taking its before record. Put consecutive fragments that need an exclusive E2E resource, a protected-script edit, or a coordinator-only action in a block assigned to the coordinator. Keep fragment order and finish each record before opening the next.
- Fragments whose dependencies are `done` may be prepared at the same time outside the working tree, each in an isolated copy that holds the recorded state, by subagents of the tier their work needs, within the delegation rules on shared local resources and with no more at once than the session's usage allows; nothing a copy holds or runs counts as evidence. Each then enters the working tree in index order, through every step of the next section as if written there, reconciled first with what the fragments recorded before it changed.
- Take fragments in order, and stop at the first `failed` one, and at the first `blocked` one that has its `record NN before` or that a later fragment depends on, other than the one that holds the final run and the closure audit, until the user resolves it.
- Pass over any other `blocked` fragment: it has no record, so `apply` and `revert` count around it. The plan places fragments that wait on a decision or a pending datum as late as their dependencies allow, before the one that holds the final run and the closure audit, as `build/` says.
- When only passed-over fragments remain before the one that holds the final run and the closure audit, that one runs, unless it is `blocked` itself, and its closing report carries each open decision, with the criteria that wait on it, as ⏳ pending, as the prompt's rule on open decisions lets the rest of the work proceed.
- A passed-over fragment runs once the user resolves what it waits on: in place while no later fragment has a record, and otherwise under the next free number, followed, when the fragment holding the final run and the closure audit already ran, by a new fragment that repeats them. While a fragment that stops the execution stays `blocked`, the ⏳ report, which names each open decision, stands in for the closing report.

## Ending an execution

- Finish authorized and resolvable work first. Give each remaining risk, decision, or blocked step a stable ID such as `[P-01]` in the coordinator's report. In the final response, give each user question its own list item such as `- [P-01] Which environment should be checked?` Give the alternatives and recommendation. If several plans are in scope, qualify the ID with the plan directory, as in `- [P-01] [2026-11-16-example] Which environment should be checked?` A visible question allows the turn to end with the item open.
- Name each fragment that is not `done` at the end of an execution in a ⏳ line: one that asks how to go on with a `failed` or `blocked` fragment, such as retrying or dropping a `failed` one, and one that names the `pending` ones, as when the user asked to run only some of them or to stop.
- Never end while an item can still be resolved within what the user authorized, such as a fragment the user asked to run whose dependencies are `done`, a check that can run, or a correction within the cycle limit; never take on what the user did not authorize, such as a fragment beyond those the user asked to run, and ask instead; and never settle an item by assuming the user's answer. The stops the rules above make, at a `failed` or `blocked` fragment, are valid ends only in the second way.
- Before the closing report of an execution, triage its ⚠️ lines as [warning-triage.md](warning-triage.md) defines.
- At the end of an execution, list the ℹ️ lines of the triage that are risks of the delivered work, not the deferred measurements already run or the observations outside the scope, in one `⏳ [P-NN]` line with its own ID that asks for their acceptance; that line carries the one question, whose options are accept all, recommended, and review one by one.
- When the user chooses to review one by one, each listed risk moves to its own ⚠️ line with its own ID and its own question; each warning that blocks keeps its own question and its own ID.
- One subject, one ID: lines that repeat the same subject cite the same ID, and an ID is never reused for another subject.
- Put the ID at the start of the text of each question, whether it goes through the question mechanism or the final message, so that the receipt can name it.
- Mark an entry the user answered by adding `[answered YYYY-MM-DD P-01]` to its line, with the date of the answer and the entry's ID, once the answer is in the conversation. In a project with no hook that holds receipts, the mark closes the line by itself; with one, it closes nothing without the receipt that hook holds for that ID, so an entry marked without one stays open and visible, and the turn may yield with it. Treat legacy acceptance marks as history.
- Record partial results as `⏳ [partial] [P-01] Parcial`, with the demonstrated part and the remainder.
- A subagent returns a written handoff with the base revision, paths changed, decisions by ID, check commands and evidence, and the next exact check. For an unresolved item, use `- Handoff [P-01] Which environment should be checked?` or `- Handoff fragment 02 Which environment should be checked?` in the final response. The handoff is to the coordinator. The coordinator alone writes `review/report.md`, refreshing it after each handoff, before asking a question and at each fragment boundary.
- When a tool of the session refuses a stop and lists the items that keep the execution open, as a hook of the project may, take that list as the next step under these rules: resolve each item within what the user authorized, ask about the rest, and end only in one of the two ways above.

## Times

- Take times from `check/time.mjs`. Start or resume a fragment with `node check/time.mjs NN`, and use `node check/time.mjs work "<reason>"` for integration, review, reporting and coordination outside a named fragment. Use `wait "<reason>"` only when no plan work can advance. Use `end` at a finished execution and `table` to render the recorded segments. Keep historical tables from closed plans as written.
- Each line closes the open segment. Work by the coordinator or its delegates counts as work. Time between `end` and a later restart is outside the execution.

## Running a fragment

- A replacement executor reads the written handoff, confirms its base revision, paths, decisions, and recorded evidence against the current plan, then starts with the next check it names. Keep an existing before record and investigate any mismatch before resuming.
- After any dry run or `--baseline` run that the dry-run rule or `check/` requires before it, first run `record NN before` when the plan has `patch/` and the fragment has none yet, before writing any of its tests or changes to project files, so its patch captures them; a fragment resumed after `blocked` or retried after `failed` keeps the one it already ran.
- `record NN before` lists the untracked files version control does not ignore. When one of them is a file this fragment's work already wrote, delete `NN.before` and `NN.untracked`, move the file to the prompt skill's temporary location, run `record NN before` again, and put the file back, so `record NN after` can adopt it. A tracked file this fragment's work changed before its `record NN before` cannot enter its patch: report it as ⚠️ outside every patch, which the reviews and the closure audit read with the patches.
- Then, with or without `patch/`, check whether the completed fragments already deliver part of its change. When they do, turn those tests and check lines into guards, editing this pending fragment, its tests, and its `NN-check` script while keeping each criterion's wording and threshold and never making a test or check more permissive, cite the evidence, such as a test, a check line, or a log of a completed fragment, and report it.
- Then add the declared tests and run the red check before implementation. Declare each test-only path as `<!-- test-path: path -->`. Run `node check/evidence.mjs NN red --test-path <path> --expect <failure text> -- <command> <args>` with every declared test path and the actual command, and save its full redacted output and exit status. Its before and after states must match the `record NN before` snapshot apart from the declared test-only edits. Refuse missing, incomplete, wrong-cause, or stale red evidence. Tests of preserved behavior are guards and should pass before the change. If the plan has no patch records or an active legacy before record lacks the snapshot, mark red verification pending. Preserve the old record. For an authorized retry, restore and verify the baseline through the legacy procedure before taking a fresh record.
- `record NN after` refuses a fragment that declares `<!-- test-path: path -->` entries unless `review/` holds the `red` receipt `NN-tests-before-<UTC timestamp>.json` of its `record NN before`, whose log matches its hash and whose test paths are the declared ones, and names the `node check/evidence.mjs NN red` command that is missing; `check/evidence.mjs` never saves a manual `tests-before` or `final-output` log, whose names the red run and the final run keep for themselves.
- When a test of the change already passes before implementation without that red evidence, or a guard fails, stop without running `record NN after`, report it, and mark the fragment `blocked` until the user decides.
- A fragment whose changed behavior a check measures, alone or with tests, runs the lines of that check that measure it as part of its tests-before run, and that `NN-check` log, which the report cites next to the tests-before log as run before the implementation, is the evidence. A fragment that only measures a baseline, reruns validations, or closes the plan has no tests-before run: the first run of its check or measure script, other than the dry run, is its evidence. When it passes, the fragment changes nothing; when a line fails, the fragment corrects it like any other, within the same limits, except that a fragment that only measures a baseline changes no project file and corrects only its measure script or `helpers`, as `check/` allows.
- Only then implement it. Run `all NN`, adding `--slow` when a change affects an earlier slow check. At closure wait for all writers to finish, and run `node check/all.mjs --final` on the integrated tree. Record its revision, tree and check fingerprints with the report, and repeat the final run after relevant edits. Allow at most three correction cycles per fragment, or fewer when the project or prompt sets a tighter limit. Each cycle is one correction followed by its check. The closure audit has its own limit. If the fragment still fails at its limit, report the failure and preserve the authorized criteria.
- A correction of the implementation never changes the fragment's criteria, tests, or checks, except as `check/` allows for a script shown not to measure its criterion.
- All of this happens between `record NN before` and `record NN after` when the plan has `patch/`, so `record NN after` runs only once the checks pass.
- A commit at the end of a fragment, which only the user can authorize, directly or through the prompt, never a project rule alone, is made once its other checks pass and before `record NN after`, which a commit does not affect; rerun the checks after it. On a file system that ignores case, such a commit never includes a rename that only changes case, which waits until after closing, once no fragment remains to run. Such commits stay in history when fragments are reverted later.

## Recording the fragment

- Stop every process the fragment's execution started, its subagents' included, before `record NN after` or setting it `done`; a fragment is never `done` while one still runs.
- Before `record NN after`, run the fragment's `NN-check`, directly or through `all NN`, on the tree it leaves: when the plan has that script, `record NN after` refuses without a passing run of it after `record NN before`, and names the command to run, or the file of `check/` or `build/` over 1 MiB that keeps every run stale, as `node check/all.mjs --final` does. After it records, it sets the fragment's status in `build/00-index.md` to `done`; read its warning, and set the cell by hand when it could not. Set `failed` and `blocked` by hand.
- `record NN after` adopts, with `--include`, every file this fragment's work wrote, there or first elsewhere, such as a draft it wrote in the temporary location and moved in. A file it moved whose original the before snapshot holds, as a tracked file or one an earlier fragment adopted, is adopted under its new name, since `revert` brings the original back, unless `--include` refuses that name. When it lies inside a folder `NN.untracked` lists as one name, record without it: the patch carries only the deletion, which `revert` undoes, and report the new name as ⚠️ outside every patch. On a file system that ignores case, a rename that only changes case, of a file or of a folder, stays outside the plan, since `apply` and `revert` cannot replay it there: a plain `mv` records nothing of it, which `record NN after` reports as renamed only in case; `record NN after` refuses one `git mv` recorded, so move it back to the old spelling first. Report it as ⚠️ outside every patch; it is made after closing, once no fragment remains to run, by the user or through a commit the prompt authorizes then, and to run a fragment later, or to revert or apply, move the rename back to the recorded spelling first. A file of the user's it moved whose original the before snapshot does not hold, because it was untracked there or outside the working tree, takes `--leave` instead, since `revert` would delete the new copy without bringing back the original; `record NN after` lists as gone such a file the before record named by its own name. It leaves out, with `--leave`, each new untracked file that is no part of its change, such as a generated report version control does not ignore. It refuses until every such new file is one or the other. Report the files left out as ⚠️ outside every patch. Taking a file out of the index while it stays on disk, as `git rm --cached` or a commit that stops tracking it does, stays outside the plan, since no patch can carry it: `record NN after` refuses such a file until `git add -- <file>`, with `-f` for an ignored one, tracks it again; report it as ⚠️ outside every patch, and it is made after closing, once no fragment remains to run, by the user or through a commit the prompt authorizes then. A file deleted from disk as well, as by `git rm` or `git mv`, is recorded as deleted; one the fragment removed with `git rm` that a build or install, such as one its checks run, wrote again looks taken out of the index, so delete it again before `record NN after`. Later it counts for what it holds where some point of the fragment sequence fits the files that way, as when it is rebuilt with the bytes it held before the fragment removed it, which reads as that fragment reverted, so `apply` deletes it again; where none fits, it counts as absent, and `revert` refuses to write over it until it is moved aside.
- An untracked file the working tree held by its name at `record NN before` can be neither adopted nor carried by any patch, even when the prompt authorizes the fragment to start tracking it: report it as ⚠️, and version control tracks it once a commit the prompt authorizes adds it.
- Right after each `record NN after`, read what it reports. The files it lists as changed between the previous recorded fragment's `afterTree` and this fragment's `beforeTree` changed outside every fragment's work between the two records, unless this fragment's work changed them before its `record NN before`, as the second rule of the previous section handles. Report both as ⚠️ outside every patch, as well as the files it lists as gone since the before record or as staged although the before record held them, nested repositories' own uncommitted work, and files renamed only in case; a nested repository the fragment changed, which no patch carries, also makes `apply` and `revert` refuse it later, so set it by hand as their refusal says. Fragment `01` has no earlier record, so a file its work changed before `record 01 before` cannot be told apart from a change made before the plan.
- Before recording or restoring, compare the candidate paths with the fragment's declared `<!-- write-path: path -->` entries and the work it actually owns. Pass `--leave-tracked <path>` for each foreign modified tracked file the fragment identifies, and list those exclusions in its handoff; both phases refuse it, before writing, for a fragment that declares no `<!-- write-path: path -->`, since nothing then says which tracked files it owns. A conflict on an owned path or a rename requires reconciliation before recording.
- After recording, compare the files `NN.state` lists with those the fragment's work wrote: one it did not write, such as an edit of another session not left out with `--leave-tracked` before recording, is reported as a ⏳ line, and the fragment is `blocked` until the user decides whether its patch keeps that change.
- When the prompt carries the concurrency rule, run `revert`, `apply`, or `record NN restore` only after confirming that no other session is editing the files their patches list or, for `restore`, the files this fragment's work changed.

## Failed and dropped fragments

- A fragment whose checks still fail at a stop condition is `failed` and gets no `record NN after`: its changes stay in the working tree for the user. A retry first restores, with the user's consent, the files to the tree `record NN before` captured, through `record NN restore` when the plan has `patch/`, or as the user directs otherwise. `record NN restore` refuses, before writing, a file of the before snapshot that stays on disk while the index no longer tracks it, until `git add -- <file>`, with `-f` for an ignored one, tracks it again; the restore then writes the before snapshot's contents over it, so keep first a copy of any such file that holds work that is not this fragment's. It leaves every untracked file the fragment did not adopt, and every file staged during the fragment that the before snapshot lacks, and lists the new ones, so delete those this fragment's work wrote and unstage with `git rm --cached -- <file>` those it staged. It also lists the files staged that the working tree held untracked by name, so unstage each and put back by hand any this fragment's work changed, and the files it writes back that the index no longer tracks, as after `git rm` or `git mv` during the fragment, so track each again with `git add -- <file>`, with `-f` for an ignored one.
- A fragment the user drops after its `record NN before` is restored the same way; then delete its `NN.before` and `NN.untracked` with its build file and scripts.

## Environment and evidence

- When the sandbox blocks a tool a check needs, keep that tool's home and caches in the plan's `.cache/` (the bundled `lib` offers it), and launch a browser through the client's one-off approval outside the sandbox, except in a dry run, which follows the prompt skill's `Sandbox` limit; never widen sandbox settings.
- A question a review asks is reported as a ⏳ line with its ID, and the execution goes on, unless a criterion cannot close without its answer, which makes the fragment `blocked`.
- Save evidence in `review/` through the bundled commands. Quote counts from saved command output. Cite run evidence as `[[run:NN-check-UTC.log]]` or `[[run:final-run.json]]`; before reporting, run `node check/report.mjs --refresh` to return stale claims to pending. Rehearse migrations in isolated disposable state, review them independently, and apply to a persistent environment only after that review passes and the user has authorized it. Verify the applied state and invariants afterward.
