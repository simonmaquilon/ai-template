# Plan workspace: folders and scripts

The folders of the plan directory that the Plan workspace section of [SKILL.md](../SKILL.md) creates, and the rules for the scripts they hold.

- `build/`: `00-index.md` holds only a table of the fragments in execution order, with each one's link, objective, the identifiers of the criteria and decisions it closes, the fragments it depends on, and its status (`pending`, `done`, `failed`, or `blocked`), set when the plan is created and updated after each execution or answer; the plan keeps no copy of the complete improved prompt. `rules.md` holds, once, the requirements that govern every change, such as the prompt's gates and the project rules it cites, and every fragment links it. Fragments `NN-<slug>.md` are small, incremental, and self-contained together with `rules.md`: each adds one behavior or one preparatory step, small enough to be built and tested on its own, builds on the fragments before it, and leaves every check of the completed fragments passing. Prefer many small fragments over a few large ones; when a criterion covers more than one behavior, split it across fragments, each carrying and checking its own part, and close it in the last of them. Write each one briefly and precisely, carrying only what the prompt states that applies to it: its objective, the context and baseline it needs, the acceptance criteria, decisions, and other requirements it closes with their identifiers, and the files and commands the prompt names for them. A mandatory first step of the prompt, such as enumerating the surface or finding a cause and stopping, becomes fragment `01`, which holds no other step and ends where the prompt stops. A fragment that changes behavior carries the tests the prompt requires for that behavior and the checks that measure it on the tree it leaves, such as measurements in the running application, instead of leaving them to a later fragment, so the tests of what it changes fail before it and all pass after it; a measurement that needs a later fragment's work belongs to the first fragment that makes it measurable. Criteria and requirements that only the whole plan closes, such as a final full test run, and the closure audit, belong to the last fragment. Every part of the prompt is carried by at least one fragment or by `rules.md`.
- `patch/`: `common`, `record`, `apply`, and `revert`, copied unchanged from this skill's bundled scripts, which behave as follows. `record` takes a fragment number and `before` or `after`: each snapshots the working tree without touching the repository index, for example through a temporary index file, leaving the plan directory out, without naming it in an exclude pathspec when version control already ignores it or it lies outside the repository, because `git add` then fails; `restore` puts the working tree back to the `before` snapshot of a fragment not yet recorded after, such as a failed one about to be retried; `after` also writes `NN.patch`, the diff between both snapshots with new files, and `NN.state`, the hashes of each file it touches before and after the change. The `NN.patch` files, in order, are the task's diff, which the reviews and audits that the prompt and the project's rules require read and which leaves out changes made before the plan; `rules.md` asks for no other snapshot. `apply` and `revert` scripts take a fragment number or `all`, work out from the recorded hashes how many fragments are applied in order, skip those already in the state they would leave, refuse a fragment out of order or any touched file that matches no recorded state, run `git apply --check` first, and write only the paths their patch lists. When a fragment changes no file, `record NN after` writes an empty `NN.patch` and an `NN.state` that lists no file, and `apply` and `revert` pass over it when counting the fragments applied in order and skip it as already in the state they would leave, without running `git apply` on its patch. This needs a git working tree; when the project is not one, ask the user before planning without `patch/`.
- `check/`: `lib` and `all`, copied unchanged from this skill's bundled `check-lib` and `check-all` scripts, and one `NN-check` script, written with `lib`, per fragment that needs one; `all NN` runs the checks of every fragment up to NN; given NN, the checks of earlier fragments skip their slow lines, such as browser measurements, unless it is given `--slow`, and without NN every line runs. A script marks those lines with `lib`'s `slow` and skips the slow work when `lib`'s `skipSlow` is true; it runs a command several checks need, such as a build, through `lib`'s `runOnce`, whose result one `all` run reuses once it succeeds; and before starting a server or browser it checks the earlier evidence its slow lines read, so a line whose evidence is missing fails for that reason without starting them. A plan whose copied `lib` lacks `slow`, `skipSlow`, and `runOnce` runs every line, its scripts use none of them, and its `all` takes no `--slow`. The checks are idempotent, run the project commands the fragment's criteria name, and exit non-zero on any failure other than those the prompt's measured baseline records as failing before the change, matched by the same test or command. A check for a criterion that depends on an open decision covers its recommended option and says so in the output line and report line it produces, is reported as ⏸ pending while the decision stays open, and is updated to the chosen option once it is settled; when the decision recommends none, or the criterion waits on a pending datum, the check is left out and reported as pending. A fragment that changes no file and whose criteria name no command needs no check script. A fragment that only measures a baseline carries instead a script named exactly `NN-measure`, which `all` never runs, written with `lib` like a check: its run, which `lib` names `NN-measure-<UTC timestamp>`, is the measurement, and later checks read the evidence it saved through `lib`'s `latestEvidence`, which leaves out baseline and dry runs; evidence names never are or start with `baseline` or `dry-run`. Code that several scripts share goes in one `helpers` module beside them, which they import and `all` never runs. An `NN-check` or `NN-measure` script, or `helpers`, shown by evidence not to measure what a criterion states, such as a failure the criterion's own condition does not explain, may be corrected: store that evidence in `review/`, stating in its content which fragment made the correction, as `NN-check-fix-<UTC timestamp>` or `NN-measure-fix-<UTC timestamp>` with the corrected script's number, or, for `helpers`, as `NN-helpers-fix-<UTC timestamp>` with the running fragment's number, keep the criterion's wording and threshold, never make the check more permissive, rerun every `NN-check` script that imports a corrected `helpers`, never a `done` fragment's `NN-measure` script, whose measurement stays as saved and, when the correction changes what it measured, is handled as a change to that fragment, and report the correction. A new fragment that the rule on `done` fragments adds may carry a criterion compared with the tree before the applied fragments, such as the preservation of behavior a regression found by the closure audit broke, which the Regression Preservation Gate already requires; when the plan has `patch/`, measure that tree before the new fragment runs `record NN before`: revert the applied fragments with `revert all`, run that fragment's `NN-check` script directly with `--baseline`, which makes `lib` name the run's log `NN-baseline-<UTC timestamp>` and the evidence the script saves through `lib` `NN-baseline-<name>-<UTC timestamp>`, and apply them again with `apply all`. That run's exit status is evidence, not a check result, and the fragment cites it; without `patch/`, report that baseline as not measured unless the user directs otherwise. Each line that runs, a `condition`'s detail included, names the command it runs or the files, paths, or addresses it reads, and its label and a `condition`'s detail show as escapes the characters the prompt skill's step 9 writes as escapes, so a log, a dry run's included, shows what the line looked at. `NN-check` and `NN-measure` scripts name the evidence they save, such as screenshots, through `lib`, which also gives that path relative to the project root, where `lib` runs commands, for a tool that refuses absolute paths; that path stays inside the project only for a plan inside it, so a plan whose checks need such a tool goes in a folder of the project that version control ignores, that no tool manages, and that lies in no folder a tool manages, which the user names when the project's rules name none. The scripts leave tracked files unchanged, write only to ignored outputs, the plan's `.cache/`, a tool's own caches or logs outside the project, and `review/`, apply the prompt skill's rule on shared local resources, and stop every server and browser they start.
- `review/`: screenshots, logs, and command output from build, patch, and check, named `NN-<kind>-<UTC timestamp>`, and `report.md`.

Fragments and `rules.md` use the improved prompt's language. Copy the bundled scripts from [scripts/node/](../scripts/node/); when the project cannot run Node, port them to a cross-platform runtime it requires, keeping their behavior, and ask the user when it requires none. Never edit the copied or ported scripts. `NN-check` and `NN-measure` scripts and `helpers` use only their runtime's standard library, resolve the plan's paths from their own location and the project's from `lib`'s `root`, contain no secret, and follow the project's language rules for comments and messages, English when it sets none. Before delivering a new plan, and before a fragment added later runs, run each `NN-check` and `NN-measure` script that the plan, or that later fragment, adds with `--dry-run` on the current tree, which makes `lib` name the run's log `NN-dry-run-<UTC timestamp>` and the evidence it saves `NN-dry-run-<name>-<UTC timestamp>`. Every line runs: a line that measures a change, or that depends on an earlier fragment's work, fails for that reason; a guard of behavior that already holds passes; a line that cannot run, such as when its approval is refused or the session cannot receive a reply, is ⚠️ not measured. Correct a script that does not behave so, never making it more permissive, and dry-run it again. A line of a change that still passes because the current tree already shows that behavior is ⚠️, and its fragment records it as a guard citing that dry-run log, keeping the criterion's wording and threshold. Each script's report line cites its last dry-run log: ✅ when every line behaved so, ⚠️ naming the lines that could not run or that already pass. The dry run executes no fragment and changes no status; when fragments are renumbered later, the report lines name their new numbers and keep citing the evidence files as saved.
