# Plan workspace: folders and scripts

The folders of the plan directory that the Plan workspace section of [SKILL.md](../SKILL.md) creates, and the rules for the scripts they hold.

- `build/`: `00-index.md` holds only a table of the fragments in execution order, with each one's link, objective, the identifiers of the criteria and decisions it closes, the prompt's own for its criteria and, for each decision and requirement the prompt does not number, a stable one the plan gives it in `rules.md`, such as D1 or R1, the fragments it depends on, and its status (`pending`, `done`, `failed`, or `blocked`), set when the plan is created and updated after each execution or answer; the plan keeps no copy of the complete improved prompt. `build/rules.md` holds, once, the requirements that govern every change, such as the prompt's gates and the project rules it cites, and every fragment links it. Fragments `NN-<slug>.md` are small, incremental, and self-contained together with `rules.md`: each adds one behavior or one preparatory step, small enough to be built and tested on its own, builds on the fragments before it, and leaves every check of the completed fragments passing. Prefer many small fragments over a few large ones; the criteria and requirements that depend on an open decision or a pending datum go in a fragment of their own, with nothing that does not depend on it, placed as late as the dependencies allow, before the fragment that holds the final run and the closure audit, so that only that fragment is `blocked` while the others proceed; when a criterion covers more than one behavior, split it across fragments, each carrying and checking its own part, and close it in the last of them. Write each one briefly and precisely, carrying only what the prompt states that applies to it: its objective, the context and baseline it needs, the acceptance criteria, decisions, and other requirements it closes with their identifiers, and the files and commands the prompt names for them. A mandatory first step of the prompt, such as enumerating the surface or finding a cause and stopping, becomes fragment `01`, which holds no other step and ends where the prompt stops, and a second one, as when finding the cause comes before enumerating the surface, becomes fragment `02` in the order the prompt sets; when the prompt stops there for the user's approval, every later fragment is `blocked` until the user approves, and the approval is recorded as [execution.md](execution.md) records an answer. A fragment that changes behavior carries the tests the prompt requires for that behavior and the checks that measure it on the tree it leaves, such as measurements in the running application, instead of leaving them to a later fragment, so the tests of what it changes fail before it and all pass after it; a measurement that needs a later fragment's work belongs to the first fragment that makes it measurable. Criteria and requirements that only the whole plan closes, such as a final full test run, and the closure audit, belong to the last fragment. Every part of the prompt is carried by at least one fragment or by `rules.md`.
- `patch/`: `common`, `record`, `apply`, and `revert`, copied unchanged from this skill's bundled scripts. They need a git working tree, git 2.25 or later, and Node 18 or later, and refuse an older one or a git that cannot run; when the project is not a git working tree, ask the user before planning without `patch/`. They behave as follows:
  - Snapshots: `record` takes a fragment number and `before`, `after`, or `restore`, and each takes a snapshot of the working tree as a git tree. It never touches the repository's index or a nested repository's, working through a temporary index that each run keeps in a folder of its own, removed afterwards, or by a later run once a killed one's process is gone and the folder is ten minutes old. Assume-unchanged and skip-worktree marks on files on disk, sparse checkouts, and the pathspec variables `GIT_LITERAL_PATHSPECS`, `GIT_GLOB_PATHSPECS`, `GIT_NOGLOB_PATHSPECS`, and `GIT_ICASE_PATHSPECS` change nothing it captures.
  - What a snapshot holds: the files the repository's index tracks, as the working tree holds them, and the files fragments adopted, and nothing else. No other untracked file, ignored or not, is read, hashed, or stored, except that the snapshot that tells which fragments are applied, which stores nothing, also reads a file or link standing at a path a fragment recorded that the index tracks under no spelling and no fragment adopted, such as one `revert` wrote back after `git rm`, `git mv`, or a commit took it out of the index and off the disk, so it counts for what it holds, or as absent where no point of the fragment sequence fits the files that way; and the plan's own files never enter a snapshot, even when the index tracks them. A nested repository the index tracks counts at the commit it has checked out, also when `.gitmodules` sets `ignore = all` for it, which `git add` skips. A tracked or adopted file stays in every later snapshot whatever ignore rules say, as git keeps tracking it. Taking a file out of the index while it stays on disk, as `git rm --cached`, `git reset`, or a commit that stops tracking it does, stays outside the plan, since no patch can carry it: `before`, `after`, and `restore` refuse, before any snapshot, a file of the snapshot they build on that stays on disk while the index no longer tracks it, until `git add` tracks it again, with `-f` for an ignored one. A file the index starts tracking that the working tree held untracked at `before`, by its name or inside a folder `NN.untracked` lists as one name, stays out, so no patch deletes or adds a file the user keeps.
  - Objects: snapshots keep the objects they write in `patch/objects/`, which git gc never prunes, and read the repository's objects, and those of any alternate the environment names, as alternates. A snapshot that lost an object it shared with the repository, such as a file staged before it that gc pruned since, is refused with that reason, and one git cannot read with git's. `apply` and `revert` compare through transient snapshots that store no object, and where the file system ignores case `after` takes one first, so its refusal of a rename that only changes case stores nothing.
  - `before`: writes `NN.before`, the snapshot and, on its second line, the repository or worktree it was taken in, and `NN.untracked`, a compressed list of the names of the untracked files then, which `after` removes with `NN.before`, each by its name, ignored or not, except that git may list a folder it ignores whole as one name, and lists the untracked files version control does not ignore, other than those earlier fragments adopted, which no patch carries and none can adopt later. It is refused for a fragment that has a `before` record or an `NN.state`, while a later fragment has a record, while an earlier fragment has a `before` record and no `after`, and while the fragments recorded before it are not all applied as recorded, or a file of the previous `after` snapshot stays on disk while the index no longer tracks it.
  - `after`: `--include <path>`, repeated per file and written from the current folder, adopts a file or link the fragment's work wrote, as [execution.md](execution.md) says. It resolves the path through real folders, compares it without case where the file system ignores case, records it as git spells it, composed on macOS, and refuses one outside the repository, in the plan, or in `.git`, one the working tree held by that name at `before`, tracked or untracked, and one inside a folder `NN.untracked` lists as one name, which no patch can carry. `--leave <path>`, also repeated and resolved the same way, names an existing new untracked file, or a folder of them, that is no part of the fragment's change, and refuses a file the index tracks or an earlier fragment adopted, whose change the patch carries. `after` refuses a file of the `before` snapshot that stays on disk while the index no longer tracks it, until `git add` tracks it again or, for one the fragment removed with `git rm` that a build or install wrote again, until it is deleted again, and refuses until every new untracked file that version control does not ignore is adopted or left. It writes `NN.patch`, the diff between both snapshots with new files, which no diff configuration or environment of whoever runs it can turn into one `git apply` rejects, and `NN.state`, with the repository or worktree under `root`, the mode and hash of each file it touches before and after the change, the files adopted under `included`, and those left under `left`; a fragment that changes no file gets an empty patch and a state that lists no file. It then reports the files that changed between the previous recorded fragment's `after` snapshot and its own `before` snapshot, the files `NN.untracked` named that are gone, whose contents no patch carries and `revert` cannot bring back, the files staged since `before` that it held untracked then, or created inside a folder it held untracked whole, which no patch carries, the nested repositories the fragment changed and those with uncommitted work of their own, and, on a file system that ignores case, the files and folders renamed only in case, which git does not record. On a file system that ignores case, it refuses a patch that deletes one name and adds another that differs from it only in case, as a `git mv` that only changes the case of a file or a folder records, and one that adds or deletes a name an earlier fragment recorded in another case, since `apply` and `revert` cannot replay such a rename there. It is refused once a later fragment has a record.
  - `restore`: puts the tracked and adopted files back to the `before` snapshot of a fragment not yet recorded after, such as a failed one about to be retried. It refuses, before writing, a file of the `before` snapshot that stays on disk while the index no longer tracks it, until `git add` tracks it again, after which the restore writes that snapshot's contents over it. It leaves every other untracked file, and every file staged during the fragment that the before snapshot lacks, as it is, and lists the new ones, apart from them those staged inside a folder it held untracked whole and those staged that it held untracked by name, and the files it writes back that the index no longer tracks, as after `git rm` or `git mv` during the fragment, so that `git add` tracks each again, naming the git command that undoes what the fragment staged. It is refused for a recorded fragment and once a later fragment has a record.
  - `apply` and `revert`: take a fragment number or `all`, work out from the recorded modes and hashes how many fragments are applied in order, passing over those that change no file, and skip those already in the state they would leave. They refuse a fragment out of order, any touched file that matches no recorded state, a fragment that changes a nested repository, whose contents no patch carries, and any run while a fragment has a `before` record and no `after`. They run `git apply --check` first and write only the paths their patch lists: `revert` deletes the files a fragment adopted, and `apply` puts them back. No script writes the index, so a file the index stopped tracking during a fragment, as `git rm`, `git mv`, or a commit does, stays untracked when `revert` writes it back, which it lists, and `apply`, `revert`, and `record NN before` count it for what it holds where some point of the fragment sequence fits the files that way, and otherwise as absent, as for a file a fragment removed with `git rm` that a build or install wrote again with other bytes; `git apply --check` then refuses to write over it, with git's reason. A patch that deletes a file or link where it adds files under that name, and, where the file system ignores case, a way back that deletes one name and adds another that differs only in case, as `record NN restore` writes after a `git mv` that only changed case, are written in two passes: those deletions first, confirmed gone, so nothing is written through a link git could not remove; the deletions git did make are undone when it could not make them all, and the whole first pass when the rest fails `git apply --check`. A write that fails after its check passed, or that leaves a file it had to delete in place, as on a folder no one can write, is refused saying that the working tree may hold part of that fragment's patch. Where they can tell that the working tree's file system ignores case, from the working tree's `.git` entry, or the git directory where the working tree has none, the scripts fold case whatever `core.ignorecase` says, and `record`, `apply`, and `revert` refuse to run while it is false or unset there, which git reads as false, until `git config core.ignorecase true` sets it as git sets it on such a file system, since git and the disk then disagree about which names exist.
  - Refusals: every script refuses without a stack trace, and before writing anything, to go on in another repository or worktree than its records name, with two build files that share a fragment number, or with a record it cannot read. `record NN before`, `after`, and `restore` refuse, before any snapshot, an index entry in a second spelling of a name, one the file system takes for the same file, that neither the snapshot they build on nor the last commit holds, as `git update-index --add` of `NOTES.md` beside a tracked `notes.md` makes, until `git rm --cached` takes it out; spellings they hold already, as a history that tracks both `A.h` and `a.h` does, also when a commit between fragments brings the second one, stay, and `after` and `restore` refuse, before writing, a change to a file the index or the before snapshot holds in two spellings, the deletion of one spelling included, which no patch can replay. `apply`, `revert`, and `restore` refuse something a patch does not remove where it must put a file, such as a folder holding other files or a file where one of its folders should be, before that fragment's patch writes anything, the fragments an `all` run already took staying as they are; what the patch removes itself, under any spelling the file system takes for the same name, as when a fragment replaces a file by a folder or a link, stops nothing. They also refuse, before writing, a file whose bytes on disk the clean filter of a filter driver hides from git, so that it seems to match its recorded state although they would overwrite bytes no object holds; line-ending conversion and `ident` hide nothing a checkout does not rewrite anyway, which the scripts tell apart from a driver with git 2.31 or later; with an older git, they compare with its checkout every file whose driver git runs, so a file whose line endings a checkout would rewrite is refused even when its driver changes nothing. A patch that no longer applies is refused with git's reason.
  - The `NN.patch` files, in order, are the task's diff, which the reviews and audits that the prompt and the project's rules require read, and which leaves out changes made before the plan and files no fragment adopted; `rules.md` asks for no other snapshot.
- `check/`: `lib` and `all`, copied unchanged from this skill's bundled `check-lib` and `check-all` scripts, and one `NN-check` script, written with `lib`, per fragment that needs one; `all NN` runs the checks of every fragment up to NN; given NN, the checks of earlier fragments skip their slow lines, such as browser measurements, unless it is given `--slow`, and without NN every line runs. A script marks those lines with `lib`'s `slow` and skips the slow work when `lib`'s `skipSlow` is true; it runs a command several checks need, such as a build, through `lib`'s `runOnce`, whose result one `all` run reuses once it succeeds; and before starting a server or browser it checks the earlier evidence its slow lines read, so a line whose evidence is missing fails for that reason without starting them. A plan whose copied `lib` lacks `slow`, `skipSlow`, and `runOnce` runs every line, its scripts use none of them, and its `all` takes no `--slow`. The checks are idempotent, run the project commands the fragment's criteria name, and exit non-zero on any failure other than those the prompt's measured baseline records as failing before the change, matched by the same test or command; a command a signal stopped never passes. A check for a criterion that depends on an open decision covers its recommended option and says so in the output line and report line it produces, is reported as ⏸ pending while the decision stays open, and is updated to the chosen option once it is settled; when the decision recommends none, or the criterion waits on a pending datum, the check is left out and reported as pending. A fragment that changes no file and whose criteria name no command needs no check script. A fragment that only measures a baseline carries instead a script named exactly `NN-measure`, which `all` never runs, written with `lib` like a check: its run, which `lib` names `NN-measure-<UTC timestamp>`, is the measurement, and later checks read the evidence it saved through `lib`'s `latestEvidence`, which leaves out baseline and dry runs; evidence names are never `baseline`, `dry-run`, `check`, or `measure`, and never start with `baseline-` or `dry-run-`. Code that several scripts share goes in one `helpers` module beside them, which they import and `all` never runs. An `NN-check` or `NN-measure` script, or `helpers`, shown by evidence not to measure what a criterion states, such as a failure the criterion's own condition does not explain, may be corrected: store that evidence in `review/`, stating in its content which fragment made the correction, as `NN-check-fix-<UTC timestamp>` or `NN-measure-fix-<UTC timestamp>` with the corrected script's number, or, for `helpers`, as `NN-helpers-fix-<UTC timestamp>` with the running fragment's number, keep the criterion's wording and threshold, never make the check more permissive, rerun every `NN-check` script that imports a corrected `helpers`, never a `done` fragment's `NN-measure` script, whose measurement stays as saved and, when the correction changes what it measured, is handled as a change to that fragment, and report the correction. A new fragment that the rule on `done` fragments adds may carry a criterion compared with the tree before the applied fragments, such as the preservation of behavior a regression found by the closure audit broke, which the Regression Preservation Gate already requires; when the plan has `patch/`, measure that tree before the new fragment runs `record NN before`: revert the applied fragments with `revert all`, run that fragment's `NN-check` script directly with `--baseline`, which makes `lib` name the run's log `NN-baseline-<UTC timestamp>` and the evidence the script saves through `lib` `NN-baseline-<name>-<UTC timestamp>`, and apply them again with `apply all`. That run's exit status is evidence, not a check result, and the fragment cites it; without `patch/`, report that baseline as not measured unless the user directs otherwise. Each line that runs, a `condition`'s detail included, names the command it runs or the files, paths, or addresses it reads, and its label and a `condition`'s detail show as escapes the characters the prompt skill's step 9 writes as escapes, so a log, a dry run's included, shows what the line looked at. On Windows, `lib` starts each command through cmd.exe as one line with the command and every argument quoted, which its log shows, and fails, without running it, a line whose command or argument holds `"`, `%`, `!`, or a line break, which cmd.exe cannot pass literally. `NN-check` and `NN-measure` scripts name the evidence they save, such as screenshots, through `lib`, which also gives that path relative to the project root, where `lib` runs commands, for a tool that refuses absolute paths; that path stays inside the project only for a plan inside it, so a plan whose checks need such a tool goes in a folder of the project that version control ignores, that no tool manages, and that lies in no folder a tool manages, which the user names when the project's rules name none. The scripts leave tracked files unchanged, write only where the prompt skill's command limits allow, the plan's `review/` and `.cache/` included, apply the prompt skill's rule on shared local resources, and stop every server and browser they start.
- `review/`: screenshots, logs, and command output from build, patch, and check, named `NN-<kind>-<UTC timestamp>`, and `report.md`.

Fragments and `rules.md` use the improved prompt's language. Copy the bundled scripts from [scripts/node/](../scripts/node/); when the project cannot run Node, port them to a cross-platform runtime it requires, keeping their behavior, and ask the user when it requires none. Never edit the copied or ported scripts. `NN-check` and `NN-measure` scripts and `helpers` use only their runtime's standard library, resolve the plan's paths from their own location and the project's from `lib`'s `root`, contain no secret, and follow the project's language rules for comments and messages, English when it sets none. Before delivering a new plan, before a fragment added later runs, and before a fragment runs whose check lines were written or changed after the last dry run, as when a choice the prompt leaves to the executor is settled, run each `NN-check` and `NN-measure` script that the plan or that fragment adds or changes with `--dry-run` on the current tree, within the prompt skill's command limits and Sign-in rule, which govern the run as they govern its own measurements, the plan's `review/` and `.cache/` counting among the writes they allow and serving as the cache location they name, which makes `lib` name the run's log `NN-dry-run-<UTC timestamp>` and the evidence it saves `NN-dry-run-<name>-<UTC timestamp>`. Every line those limits allow runs: a line that measures a change, or that depends on an earlier fragment's work, fails for that reason; a guard of behavior that already holds passes; a line that cannot run, such as when its approval is refused, the session cannot receive a reply, the user's instruction not to run commands covers it, or those limits forbid it, as one that touches real data or a production service, is ⚠️ not measured and, when that instruction or those limits forbid it, does not run. Correct a script that does not behave so, never making it more permissive, and dry-run it again. A line of a change that still passes because the current tree already shows that behavior is ⚠️, and its fragment records it as a guard citing that dry-run log, keeping the criterion's wording and threshold; a line that reruns a whole validation the plan must keep passing, such as the project's full test run, and a PENDING line, behave as they should when they pass or report pending. Each script's report line cites its last dry-run log: ✅ when every line behaved so, ⚠️ naming the lines that could not run or that already pass. The dry run executes no fragment and changes no status; when fragments are renumbered later, the report lines name their new numbers and keep citing the evidence files as saved.
