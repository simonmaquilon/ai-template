# Prompt plan

Turn a change request into a plan that can be built, verified, and reverted in small steps. This skill extends the `prompt` skill and never relaxes it.

## Precedence

- Read [../prompt/SKILL.md](../prompt/SKILL.md) and apply it to the draft supplied with this invocation, with all its rules: questions, inspection, measured baseline, the independent review of its step 12, and its output. When this invocation creates a plan, the user's invocation of this skill is the requested format that replaces that output: the prompt is neither printed nor saved, the fragments and `rules.md` carry its content, and its corrections and findings lines go to the report.
- That skill's Boundaries govern its own run. Start the plan only once its answer is final, with every question answered and its review done, as a separate step the user requests by invoking this skill.
- Create a plan only for an implementation prompt, one that authorizes changes to a target project; for any other prompt, return the prompt skill's output and state that no plan applies.
- Before creating the plan, read the target project's agent instructions and documented policy that apply to it, such as `AGENTS.md`, `CLAUDE.md`, the files they route or import, and contributing guides. They govern every step here and win on a conflict, except that they never relax this skill's gates: asking where to put a plan version control does not ignore, never changing ignore rules unasked, executing nothing until the user asks, deleting a plan only when the user asks, and no commit, push, or deploy unless the user asks. Where they are silent, this skill's defaults apply.
- In a session that cannot receive a reply, as the prompt skill defines it, create no plan when this skill would have to ask where to put it or whether to plan without `patch/`; return the prompt skill's output and report that question instead.

## Plan workspace

Create the plan directory `<YYYY-MM-DD>-<slug>/`, with an English kebab-case slug for the task, where the target project's rules place change plans, or else under a `plans/` folder where they place temporary artifacts, and under `.temp/plans/` at the project root when they name neither. When the project is under version control, confirm before writing that version control ignores that location; when it is not ignored, ask the user where to put the plan, and never change ignore rules unasked. The plan directory holds only these four folders, plus `.cache/` when a check isolates a tool:

- `build/`: `00-index.md` holds only a table of the fragments in execution order, with each one's link, objective, the identifiers of the criteria and decisions it closes, the fragments it depends on, and its status (`pending`, `done`, `failed`, or `blocked`), set when the plan is created and updated after each execution or answer; the plan keeps no copy of the complete improved prompt. `rules.md` holds, once, the requirements that govern every change, such as the prompt's gates and the project rules it cites, and every fragment links it. Fragments `NN-<slug>.md` are small, incremental, and self-contained together with `rules.md`: each adds one behavior or one preparatory step, small enough to be built and tested on its own, builds on the fragments before it, and leaves every check of the completed fragments passing. Prefer many small fragments over a few large ones; when a criterion covers more than one behavior, split it across fragments, each carrying and checking its own part, and close it in the last of them. Write each one briefly and precisely, carrying only what the prompt states that applies to it: its objective, the context and baseline it needs, the acceptance criteria, decisions, and other requirements it closes with their identifiers, and the files and commands the prompt names for them. A mandatory first step of the prompt, such as enumerating the surface or finding a cause and stopping, becomes fragment `01`, which holds no other step and ends where the prompt stops. A fragment that changes behavior carries the tests the prompt requires for that behavior, so those that test what it changes fail before it and all pass after it; criteria and requirements that only the whole plan closes, such as a final full test run, and the closure audit, belong to the last fragment. Every part of the prompt is carried by at least one fragment or by `rules.md`.
- `patch/`: `common`, `record`, `apply`, and `revert`, copied unchanged from this skill's bundled scripts, which behave as follows. `record` takes a fragment number and `before` or `after`: each snapshots the working tree without touching the repository index, for example through a temporary index file, leaving the plan directory out, without naming it in an exclude pathspec when version control already ignores it, because `git add` then fails; `restore` puts the working tree back to the `before` snapshot of a fragment not yet recorded after, such as a failed one about to be retried; `after` also writes `NN.patch`, the diff between both snapshots with new files, and `NN.state`, the hashes of each file it touches before and after the change. `apply` and `revert` scripts take a fragment number or `all`, work out from the recorded hashes how many fragments are applied in order, skip those already in the state they would leave, refuse a fragment out of order or any touched file that matches no recorded state, run `git apply --check` first, and write only the paths their patch lists. When a fragment changes no file, `record NN after` writes an empty `NN.patch` and an `NN.state` that lists no file, and `apply` and `revert` pass over it when counting the fragments applied in order and skip it as already in the state they would leave, without running `git apply` on its patch. This needs a git working tree; when the project is not one, ask the user before planning without `patch/`.
- `check/`: `lib` and `all`, copied unchanged from this skill's bundled `check-lib` and `check-all` scripts (`check_lib` and `check_all` in Python), and one `NN-check` script, written with `lib`, per fragment that needs one; `all NN` runs the checks of every fragment up to NN. The checks are idempotent, run the project commands the fragment's criteria name, and exit non-zero on any failure other than those the prompt's measured baseline records as failing before the change, matched by the same test or command. A check for a criterion that depends on an open decision covers its recommended option and says so in the output line and report line it produces, is reported as ⏸ pending while the decision stays open, and is updated to the chosen option once it is settled; when the decision recommends none, or the criterion waits on a pending datum, the check is left out and reported as pending. A fragment that changes no file and whose criteria name no command needs no check script. An `NN-check` script shown by evidence not to measure what its criterion states, such as a failure the criterion's own condition does not explain, may be corrected: store that evidence in `review/` as `NN-check-fix-<UTC timestamp>`, keep the criterion's wording and threshold, never make the check more permissive, and report the correction. The scripts leave tracked files unchanged, write only to ignored outputs, the plan's `.cache/`, a tool's own caches or logs outside the project, and `review/`, apply the prompt skill's rule on shared local resources, and stop every server and browser they start.
- `review/`: screenshots, logs, and command output from build, patch, and check, named `NN-<kind>-<UTC timestamp>`, and `report.md`.

Fragments and `rules.md` use the improved prompt's language. Copy the bundled scripts for the project's runtime: [scripts/node/](scripts/node/) when it is Node or the project requires no other, [scripts/python/](scripts/python/) when it is Python, and the ones matching the project's own scripts when it requires both; for another cross-platform runtime the project requires, port them keeping their behavior. Never edit the copied scripts. `NN-check` scripts use only the runtime's standard library, resolve paths from their own location, contain no secret, and follow the project's language rules for comments and messages, English when it sets none.

## Execution

- Execute no fragment, and run no `record`, `apply`, or `revert` script, until the user asks.
- When the person an open decision names, or the user when it names none, answers it, or the user supplies a pending datum, record the answer in every fragment it governs, and in `rules.md` when it governs every change, before that fragment runs or resumes: replace the options, or the placeholder, with the answer, naming who decided and the date, and write or update the checks that depend on it. A fragment still waiting on a decision or a pending datum is `blocked`.
- Edit only fragments that are not `done`, `rules.md`, and the index; a change to `rules.md` applies to the fragments not yet `done`, and when it would change what a `done` fragment required, it is handled as a change to that fragment. `done` fragments, their patches, and their states never change: a change that affects them becomes a new fragment placed before the one holding the closure audit, or, when that one is `done`, a new fragment that repeats the final run and the closure audit; a large change becomes a new plan.
- Take fragments in order, and stop at the first `failed` or `blocked` one until the user resolves it, since `apply` and `revert` count fragments in order; a `blocked` fragment that has no `record NN before` and that no later fragment depends on is moved instead after the fragments that do not depend on it, renumbering it and the fragments after it, none of which has a record yet, so those fragments proceed. For each, add its tests first, if it carries any; run those that test the behavior it changes, if any, under the limits `check/` scripts follow, and store that run in `review/` as `NN-tests-before-<UTC timestamp>`; if any of them already passes, stop without running `record NN after`, report it, and mark the fragment `blocked` until the user decides. A fragment whose behavior a check verifies rather than tests runs the lines of that check that verify the changed behavior as its tests-before run, and that `NN-check` log is the evidence. Only then implement it, run the checks of this and every completed fragment, and correct its implementation, without changing its criteria, tests, or checks except as `check/` allows for an `NN-check` script shown not to measure its criterion, until they pass, within the stop conditions the improved prompt and the project's rules set. All of this happens between `record NN before` and `record NN after` when the plan has `patch/`, so `record NN after` runs only once the checks pass. A commit the prompt authorizes at the end of a fragment is made once its other checks pass and before `record NN after`, which a commit does not affect; rerun the checks after it. Such commits stay in history when fragments are reverted later. When the sandbox blocks a tool a check needs, keep that tool's home and caches in the plan's `.cache/` (the bundled `lib` offers it), and launch a browser through the client's one-off approval outside the sandbox; never widen sandbox settings. A fragment whose checks still fail at a stop condition is `failed` and gets no `record NN after`: its changes stay in the working tree for the user, and a retry first restores, with the user's consent, the files to the tree `record NN before` captured, through `record NN restore` when the plan has `patch/`, or as the user directs otherwise. Store the evidence in `review/`, applying the gates each fragment and `rules.md` carry and the closure audit at the end.

## Report

- After creating the plan and after each execution, report one line per criterion, decision, and requirement, with its fragment and the exact evidence file in `review/`, and keep the same lines in `review/report.md`: ✅ met · ❌ failed · ⏸ pending or open decision · ⚠️ risk. The unmet criteria of a `failed` fragment are ❌.
- The chat answer carries no copy of the prompt: it gives these lines and the prompt skill's corrections and findings lines, which `review/report.md` keeps as well, all in the user's language, with each findings line naming the fragment, or `rules.md`, that carries it instead of a section of the prompt, and complements the closing report the improved prompt requires instead of replacing it.

## Retention and limits

- Keep plans after closing and delete one only when the user asks; when the target project's rules require removing temporary artifacts at closing without exempting plans, ask the user whether to keep it, or, when the session cannot receive a reply, keep it and report that question.
- No commit, push, or deploy unless the user asks, directly or through the prompt the plan carries out.
