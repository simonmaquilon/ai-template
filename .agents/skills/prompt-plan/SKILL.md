# Prompt plan

Turn a change request into a plan that can be built, verified, and reverted in small steps. This skill extends the `prompt` skill and never relaxes it.

## Precedence

- Read [../prompt/SKILL.md](../prompt/SKILL.md) and apply it to the draft supplied with this invocation, with all its rules: questions, inspection, measured baseline, the independent review of its step 12, and its output. When this invocation creates a plan, the user's invocation of this skill is the requested format that replaces that output: the prompt is neither printed nor saved, apart from the temporary review file that skill's step 12 allows; the fragments and `rules.md` carry its content, and its corrections and findings lines go to the report.
- That skill's Boundaries govern its own run. Start the plan only once its answer is final, with every question answered and its review done, as a separate step the user requests by invoking this skill.
- Create a plan only for an implementation prompt, one that authorizes changes to a target project; for any other prompt, return the prompt skill's output and state that no plan applies.
- Before creating the plan, read the target project's agent instructions and documented policy that apply to it, such as `AGENTS.md`, `CLAUDE.md`, the files they route or import, and contributing guides. They govern every step here and win on a conflict, except that they never relax this skill's gates: asking where to put a plan inside the project that version control does not ignore or inside another repository, never changing ignore rules unasked, executing no fragment and running no `record`, `apply`, or `revert` script until the user asks, deleting a plan only when the user asks, and no commit, push, or deploy unless the user asks. Where they are silent, this skill's defaults apply.
- In a session that cannot receive a reply, as the prompt skill defines it, create no plan when this skill would have to ask where to put it or whether to plan without `patch/`; return the prompt skill's output and report that question instead.

## Plan workspace

Create the plan directory `<YYYY-MM-DD>-<slug>/`, with an English kebab-case slug for the task, where the target project's rules place change plans, or else under a `plans/` folder in the temporary location the prompt skill defines. When that location is inside a project under version control, confirm before writing that version control ignores it; when it is not ignored, ask the user where to put the plan, and never change ignore rules unasked. A folder inside a repository other than the target project's never holds a plan, whoever names it, because the scripts take the plan's repository as the project; ask the user for another. A plan outside the project runs its scripts from the project's root, and the report names its absolute path; one in the session's scratch folder or the operating system's temporary folder, which the client or the system may empty, is reported as a ⚠️ risk. The plan directory holds only these four folders, plus `.cache/` when a check isolates a tool:

- `build/`: `00-index.md` holds only a table of the fragments in execution order, with each one's link, objective, the identifiers of the criteria and decisions it closes, the fragments it depends on, and its status (`pending`, `done`, `failed`, or `blocked`), set when the plan is created and updated after each execution or answer; the plan keeps no copy of the complete improved prompt. `rules.md` holds, once, the requirements that govern every change, such as the prompt's gates and the project rules it cites, and every fragment links it. Fragments `NN-<slug>.md` are small, incremental, and self-contained together with `rules.md`: each adds one behavior or one preparatory step, small enough to be built and tested on its own, builds on the fragments before it, and leaves every check of the completed fragments passing. Prefer many small fragments over a few large ones; when a criterion covers more than one behavior, split it across fragments, each carrying and checking its own part, and close it in the last of them. Write each one briefly and precisely, carrying only what the prompt states that applies to it: its objective, the context and baseline it needs, the acceptance criteria, decisions, and other requirements it closes with their identifiers, and the files and commands the prompt names for them. A mandatory first step of the prompt, such as enumerating the surface or finding a cause and stopping, becomes fragment `01`, which holds no other step and ends where the prompt stops. A fragment that changes behavior carries the tests the prompt requires for that behavior and the checks that measure it on the tree it leaves, such as measurements in the running application, instead of leaving them to a later fragment, so the tests of what it changes fail before it and all pass after it; a measurement that needs a later fragment's work belongs to the first fragment that makes it measurable. Criteria and requirements that only the whole plan closes, such as a final full test run, and the closure audit, belong to the last fragment. Every part of the prompt is carried by at least one fragment or by `rules.md`.
- `patch/`: `common`, `record`, `apply`, and `revert`, copied unchanged from this skill's bundled scripts, which behave as follows. `record` takes a fragment number and `before` or `after`: each snapshots the working tree without touching the repository index, for example through a temporary index file, leaving the plan directory out, without naming it in an exclude pathspec when version control already ignores it or it lies outside the repository, because `git add` then fails; `restore` puts the working tree back to the `before` snapshot of a fragment not yet recorded after, such as a failed one about to be retried; `after` also writes `NN.patch`, the diff between both snapshots with new files, and `NN.state`, the hashes of each file it touches before and after the change. The `NN.patch` files, in order, are the task's diff, which the reviews and audits that the prompt and the project's rules require read and which leaves out changes made before the plan; `rules.md` asks for no other snapshot. `apply` and `revert` scripts take a fragment number or `all`, work out from the recorded hashes how many fragments are applied in order, skip those already in the state they would leave, refuse a fragment out of order or any touched file that matches no recorded state, run `git apply --check` first, and write only the paths their patch lists. When a fragment changes no file, `record NN after` writes an empty `NN.patch` and an `NN.state` that lists no file, and `apply` and `revert` pass over it when counting the fragments applied in order and skip it as already in the state they would leave, without running `git apply` on its patch. This needs a git working tree; when the project is not one, ask the user before planning without `patch/`.
- `check/`: `lib` and `all`, copied unchanged from this skill's bundled `check-lib` and `check-all` scripts, and one `NN-check` script, written with `lib`, per fragment that needs one; `all NN` runs the checks of every fragment up to NN. The checks are idempotent, run the project commands the fragment's criteria name, and exit non-zero on any failure other than those the prompt's measured baseline records as failing before the change, matched by the same test or command. A check for a criterion that depends on an open decision covers its recommended option and says so in the output line and report line it produces, is reported as ⏸ pending while the decision stays open, and is updated to the chosen option once it is settled; when the decision recommends none, or the criterion waits on a pending datum, the check is left out and reported as pending. A fragment that changes no file and whose criteria name no command needs no check script. A fragment that only measures a baseline carries instead a script named exactly `NN-measure`, which `all` never runs, written with `lib` like a check: its run, which `lib` names `NN-measure-<UTC timestamp>`, is the measurement, and later checks read the evidence it saved through `lib`'s `latestEvidence`, which leaves out baseline and dry runs; evidence names never are or start with `baseline` or `dry-run`. Code that several scripts share goes in one `helpers` module beside them, which they import and `all` never runs. An `NN-check` or `NN-measure` script, or `helpers`, shown by evidence not to measure what a criterion states, such as a failure the criterion's own condition does not explain, may be corrected: store that evidence in `review/` as `NN-check-fix-<UTC timestamp>` or `NN-measure-fix-<UTC timestamp>`, or, for `helpers`, as `NN-helpers-fix-<UTC timestamp>` with the running fragment's number, keep the criterion's wording and threshold, never make the check more permissive, rerun every `NN-check` script that imports a corrected `helpers`, never a `done` fragment's `NN-measure` script, whose measurement stays as saved and, when the correction changes what it measured, is handled as a change to that fragment, and report the correction. A new fragment that the rule on `done` fragments adds may carry a criterion compared with the tree before the applied fragments, such as the preservation of behavior a regression found by the closure audit broke, which the Regression Preservation Gate already requires; when the plan has `patch/`, measure that tree before the new fragment runs `record NN before`: revert the applied fragments with `revert all`, run that fragment's `NN-check` script directly with `--baseline`, which makes `lib` name the run's log `NN-baseline-<UTC timestamp>` and the evidence the script saves through `lib` `NN-baseline-<name>-<UTC timestamp>`, and apply them again with `apply all`. That run's exit status is evidence, not a check result, and the fragment cites it; without `patch/`, report that baseline as not measured unless the user directs otherwise. `NN-check` and `NN-measure` scripts name the evidence they save, such as screenshots, through `lib`, which also gives that path relative to the project root, where `lib` runs commands, for a tool that refuses absolute paths; that path stays inside the project only for a plan inside it, so a plan whose checks need such a tool goes in a folder of the project that version control ignores, which the user names when the project's rules name none. The scripts leave tracked files unchanged, write only to ignored outputs, the plan's `.cache/`, a tool's own caches or logs outside the project, and `review/`, apply the prompt skill's rule on shared local resources, and stop every server and browser they start.
- `review/`: screenshots, logs, and command output from build, patch, and check, named `NN-<kind>-<UTC timestamp>`, and `report.md`.

Fragments and `rules.md` use the improved prompt's language. Copy the bundled scripts from [scripts/node/](scripts/node/); when the project cannot run Node, port them to a cross-platform runtime it requires, keeping their behavior, and ask the user when it requires none. Never edit the copied or ported scripts. `NN-check` and `NN-measure` scripts and `helpers` use only their runtime's standard library, resolve the plan's paths from their own location and the project's from `lib`'s `root`, contain no secret, and follow the project's language rules for comments and messages, English when it sets none. Before delivering a new plan, and before a fragment added later runs, run each `NN-check` and `NN-measure` script that the plan, or that later fragment, adds with `--dry-run` on the current tree, which makes `lib` name the run's log `NN-dry-run-<UTC timestamp>` and the evidence it saves `NN-dry-run-<name>-<UTC timestamp>`. Every line runs: a line that measures a change, or that depends on an earlier fragment's work, fails for that reason; a guard of behavior that already holds passes; a line that cannot run, such as when its approval is refused or the session cannot receive a reply, is ⚠️ not measured. Correct a script that does not behave so, never making it more permissive, and dry-run it again. A line of a change that still passes because the current tree already shows that behavior is ⚠️, and its fragment records it as a guard citing that dry-run log, keeping the criterion's wording and threshold. Each script's report line cites its last dry-run log: ✅ when every line behaved so, ⚠️ naming the lines that could not run or that already pass. The dry run executes no fragment and changes no status; when fragments are renumbered later, the report lines name their new numbers and keep citing the evidence files as saved.

## Execution

- Execute no fragment, and run no `record`, `apply`, or `revert` script, until the user asks.
- When the person an open decision names, or the user when it names none, answers it, or the user supplies a pending datum, record the answer in every fragment it governs, and in `rules.md` when it governs every change, before that fragment runs or resumes: replace the options, or the placeholder, with the answer, naming who decided and the date, and write or update the checks that depend on it. A fragment still waiting on a decision or a pending datum is `blocked`.
- Edit only fragments that are not `done`, `rules.md`, and the index; a change to `rules.md` applies to the fragments not yet `done`, and when it would change what a `done` fragment required, it is handled as a change to that fragment. `done` fragments, their patches, and their states never change: a change to what they require becomes a new fragment placed before the one holding the closure audit, or, when that one is running or `done`, a new fragment after it that repeats the final run and the closure audit; a large change becomes a new plan. A correction made while a later fragment runs, such as one the closure audit or its reviews ask for, stays in that fragment's patch even when it touches files a `done` fragment changed, since the patches still apply in order, unless it needs a comparison with the tree before the applied fragments, which goes to a new fragment as `check/` says.
- Take fragments in order, and stop at the first `failed` or `blocked` one until the user resolves it, since `apply` and `revert` count fragments in order; a `blocked` fragment that has no `record NN before` and that no later fragment depends on is moved instead after the fragments that do not depend on it, renumbering it and the fragments after it, none of which has a record yet, so those fragments proceed. For each, first check whether the completed fragments already deliver part of its change; when they do, turn those tests and check lines into guards, editing this pending fragment, its tests, and its `NN-check` script while keeping each criterion's wording and threshold and never making a test or check more permissive, cite the evidence, such as a test, a check line, or a log of a completed fragment, and report it. Then add its tests, if it carries any; run, under the limits `check/` scripts follow, those that test the behavior it changes, if any, together with the guards it adds, tests of behavior that already holds before it and that it keeps unchanged, written against an interface that exists before it, which do not count as tests of the change, while a test of behavior it restores or extends, such as a regression the closure audit found, is a test of the change; store that run in `review/` as `NN-tests-before-<UTC timestamp>`; if any test of the change already passes without such evidence, or a guard fails, stop without running `record NN after`, report it, and mark the fragment `blocked` until the user decides. A fragment whose changed behavior a check measures, alone or with tests, runs the lines of that check that measure it as part of its tests-before run, and that `NN-check` log is the evidence. A fragment that only measures a baseline, reruns validations, or closes the plan has no tests-before run: the first run of its check or measure script, other than the dry run, is its evidence; when it passes, the fragment changes nothing, and when a line fails, the fragment corrects it like any other, within the same limits, except that a fragment that only measures a baseline changes no project file and corrects only its measure script or `helpers`, as `check/` allows. Only then implement it, run the checks of this and every completed fragment, and correct its implementation, without changing its criteria, tests, or checks except as `check/` allows for a script shown not to measure its criterion, until they pass, within the stop conditions the improved prompt and the project's rules set. All of this happens between `record NN before` and `record NN after` when the plan has `patch/`, so `record NN after` runs only once the checks pass. A commit the prompt authorizes at the end of a fragment is made once its other checks pass and before `record NN after`, which a commit does not affect; rerun the checks after it. Such commits stay in history when fragments are reverted later. When the sandbox blocks a tool a check needs, keep that tool's home and caches in the plan's `.cache/` (the bundled `lib` offers it), and launch a browser through the client's one-off approval outside the sandbox; never widen sandbox settings. A fragment whose checks still fail at a stop condition is `failed` and gets no `record NN after`: its changes stay in the working tree for the user, and a retry first restores, with the user's consent, the files to the tree `record NN before` captured, through `record NN restore` when the plan has `patch/`, or as the user directs otherwise. Store the evidence in `review/`, applying the gates each fragment and `rules.md` carry and the closure audit at the end. A question a review asks is reported as a ⏸ line, in the chat and in `review/report.md`, and the execution goes on, unless a criterion cannot close without its answer, which makes the fragment `blocked`.

## Report

- After creating the plan and after each execution, report one line per criterion, decision, and requirement, with its fragment and the exact evidence file in `review/`, plus one line per script a dry run ran, and keep the same lines in `review/report.md`: ✅ met · ❌ failed · ⏸ pending or open decision · ⚠️ risk. The unmet criteria of a `failed` fragment are ❌. In the chat, lines that share a status, fragment, and evidence file may be merged into one that lists their identifiers.
- The chat answer carries no copy of the prompt: it gives these lines and the prompt skill's corrections and findings lines, which `review/report.md` keeps as well, all in the user's language, with each findings line naming the fragment, or `rules.md`, that carries it instead of a section of the prompt, and complements the closing report the improved prompt requires instead of replacing it.

## Retention and limits

- Keep plans after closing and delete one only when the user asks; when the target project's rules, or the global configuration that set the plan's location, require removing temporary artifacts at closing without exempting plans, ask the user whether to keep it, or, when the session cannot receive a reply, keep it and report that question.
- No commit, push, or deploy unless the user asks, directly or through the prompt the plan carries out.
