# Start

Start from an empty folder or a new, empty repository, or prepare a project that already has the template: template cleanup, primary references, and agent tooling. Text the user passes with the invocation is the first evidence about the project.

## Precedence

- Where present, `AGENTS.md` and the instructions it routes govern every step. Before adoption follow the safety and approval rules here and the canonical adoption guide in the approved release. Load `01` and `10` at the start of the derived-project workflow, `03` before deleting files, `06` before stack.md, `11` before the first backlog.md entry, `06` and `13` before changing tooling, and `12` for staging or a commit, plus every other module `AGENTS.md` routes for the step at hand, such as `08` for secrets, `07` for design tokens, `04` and `16` for checks, and `15` for the CI workflow.
- The skeletons are the checklist: each section's heading and guide line say what it holds. [references/documents.md](references/documents.md) groups them into topics and lists the cross-document pitfalls; [references/tooling.md](references/tooling.md) covers the tooling step.
- Never rewrite a skeleton's headings, except the title placeholders that take the project name (the README H1 and design.md's `# Design System:`), its guide text, or design.md's frontmatter keys. The documents live in `.docs/`, and this skill writes them itself in their skeleton's structure.

## Boundaries

- Only the explicitly selected mockup build may generate the approved starter files and install its approved dependencies. The derived-project interview installs only pinned agent tooling through `node .scripts/run-pinned.mjs`, after the user consents, and adds no application, generator, or test files. Empty adoption ends with the template alone. Deployment and product implementation are outside `start`.
- No staging, commits, branches, or pushes unless the user explicitly asks. Apply `12` for staging and commits. With consent, both new paths can initialize Git if needed, add `plantilla`, and fetch the approved release ref. In the derived-project interview the only other Git write is `git remote add --no-tags plantilla <template URL>`, after consent. Delete files through the filesystem, never with `git rm`.
- Do not edit `.agents/instructions/`, the primary references or routing table of `AGENTS.md`, `.agents/template-version`, `.agents/tool-versions.json` (only its refresh command changes it, once approved), stack.md's Template Tooling, or `stack:generated` blocks other than their Notes column. Client settings, hooks, sandbox, permissions, `.gitignore`, and `.gitattributes` change only inside a tooling change the user approved. `.claude/settings.json` and `.codex/hooks.json` are sealed template files that this skill never edits: what the project or a person approves goes in `.claude/settings.local.json`, which is per person.
- Record a deviation only when the user decides to depart from a baseline rule after hearing what it protects; then follow `01`: an entry of `.agents/template-exceptions.json` keyed by the sealed path the project keeps, linking the routed project policy that replaces the rule.
- Never invent names, metrics, dates, versions, owners, evidence, or legal or regulatory claims. Content you derive from the user's answers, such as principles, terminology, journeys, phases, or acceptance rows, is a proposal written only once the user confirms it. Versions come from official sources consulted in the session (`03`, `06`), never from memory. No secret goes into any document.

## Template guard

First action, every run: identify the actual working directory and enclosing Git root with read-only checks. Apply the origin guard before any workflow, including when the working directory is below the Git root. Read the canonical template URL from `.readme/96-template-adoption.md` at the repository root when present and compare it with `git remote get-url origin`, ignoring protocol, the `git@host:` form, a trailing `.git`, and case. The canonical source for a user-installed copy before project files exist is `https://github.com/simonmaquilon/ai-template.git`. When the origin matches the template, change nothing, run nothing else, explain in the user's language that a project is created with `gh repo create <name> --template <owner>/<repo> --private --clone` (or `--public`), then `cd <name>`, opening the agent there, and invoking `/start` or `$start`, and that an existing project adopts it as `.readme/96-template-adoption.md` describes; then stop. Never bootstrap a subdirectory of another Git root. A project with the template and no Git or `origin` still uses the derived-project workflow; unless `plantilla` already exists, mark the remote step ⏳.

## Start from scratch

Begin adoption only in an empty working directory outside Git or at the root of the user's own newly initialized, empty repository. Inspect directory entries without following symlinks, including hidden and ignored entries, and verify the physical destination. Check that the physical parent is outside any Git worktree even when the destination has its own `.git/`. For a Git repository require a real local `.git/` directory, an unborn `HEAD`, no project history on other refs, an empty index, and no worktree entries besides `.git/`. When the user did not choose, offer two paths in the user's language: adopt the template only, or start from a mockup. Follow an explicit choice directly.

If the user explicitly resumes an interrupted extraction, apply only the recovery procedure below after verifying the same root, approved ref, and provenance of the extracted paths. For any other existing tree without the template, refer the user to the existing-project adoption procedure. At the root of a derivative, an explicit request to start from a mockup can continue from its adopted baseline before application code exists. An explicit request to resume the mockup build can also continue after starter files were written. Use the existing derived-project workflow in other derivatives.

### Adopt a published release

1. Reuse an explicitly approved bare `MAJOR.MINOR.PATCH` release tag, or check the canonical source's published tags read-only and ask for approval of a proposed release. Batch the adoption approval and needed Git writes: `git init` if absent, `git remote add --no-tags plantilla https://github.com/simonmaquilon/ai-template.git` if absent, and fetching the tag into `refs/plantilla/<version>`. The released `.readme/96-template-adoption.md` is available with `git show <ref>:.readme/96-template-adoption.md` before extraction. The maintained guide's sections «Empezar en una carpeta vacía» and «Localizar las versiones» describe this procedure.
2. Verify that `plantilla` resolves to the canonical source and get the exact object ID of the advertised tag. If the fixed ref exists, require it to hold that object. Otherwise fetch only the advertised object with `git fetch --no-tags --no-prune --no-write-fetch-head --refmap= plantilla "$template_oid"`. Resolve its commit and use `git show` and `git ls-tree` to verify that `.agents/template-version` and the parsed `.agents/template-manifest.json` declare the approved version and the manifest's file set and blob IDs match the tracked release tree excluding the manifest itself and the six template-only paths. Stop on any discrepancy. Create the fixed ref with `git update-ref --no-deref "refs/plantilla/$template_version" "$template_oid" ""`, which requires its absence even if another process adds it after inspection. Never replace a remote or an existing ref. Retain the fixed ref as the seal's local source.
3. Recheck the empty root immediately before extraction, allowing only `.git/` and the archive scratch files this step created under `.temp/`. Produce a complete temporary `git archive` of the verified commit before extracting with `tar -xkf`. Keep the released `.gitignore` and use the exact six adoption exclusions: `.github/workflows/template-checks.yml`, `.scripts/run-checks.mjs`, `.scripts/tests/`, `.scripts/check-security-skill.mjs`, `.scripts/security-skill-hash.mjs`, and `.readme/94-template-ci.md`. Verify the resulting symlinks, version, manifest, and files. Check that the six exclusions are absent and `.github/` has content if it exists. No adoption marker is needed in a new repository. On a partial extraction, inventory the written and missing paths against the fixed release, checking types and contents, including symlink targets without following them. Preserve all contents; if any path is foreign, changed, or ambiguous, stop. Otherwise archive and extract only the verified missing paths with the same no-overwrite protection. Follow Client bindings for protected writes.
4. Refresh the generated workflow inventory with `node .scripts/update-stack-doc.mjs` because the template CI workflow was excluded. Run the derived-project checks in «Después de adoptar». Before the first commit, run the file-length check without `--base` and verify symlinks on disk because the symlink check reads the index. Report check outcomes and gaps. For template-only adoption, finish here after any separately approved GitHub creation. Leave the skeletons unfilled and skip the product interview.

GitHub is optional in either path. Create a GitHub repository only after the user explicitly chooses the owner, repository name, and visibility and authorizes creation. Verify `gh repo create` against official help; check that the target is available and use `--source` and `--remote` only as needed without replacing an existing remote. A commit or push needs separate authorization. Keep the result local when the user chooses local.

### Start from a mockup

1. Open the mockup conversation before asking for template or Git approvals. If the mockup or a description is available, state what it shows, propose a scope limited to the evidence, and ask the first unresolved product or design question in the user's language. Otherwise ask the user to share or describe it. Confirm observed details and intended journeys separately, and let the user settle behavior, permissions, data, and stack. Continue the conversation while adoption is pending. If the project lacks the baseline, adopt it with the user's approval before writing project files. Use the derived-project cleanup and interview below, including its rules for deferred decisions.
2. Only generate a base when the user explicitly chooses to build and approves the stack and starter format. With no approved stack, continue the interview and leave generation pending. Check the official generator documentation and versions, and apply the existing approval rules to any generator, dependencies, and installs. Protect the adopted files, configuration, and permissions. If the generator could collide with any project path, run it in an isolated directory under `.temp/`, inspect its result, and transfer only approved files to unoccupied paths. Keep template settings and protections intact.
3. On resumption after generation began, reconcile the existing starter files with the approved base and commands using the project and the user's confirmed decisions. Continue from the first unfinished installation or verification step without regenerating or overwriting existing files. Ask only for evidence or approvals still needed. Run the applicable startup, build, or minimal test for the approved base using the project's documented command, with a bounded run and cleanup of any process it starts. Record only verified commands and results in their primary references. On failure, inspect the observed error, correct it within scope where possible, rerun the affected check, and report any remaining failure and its effect on readiness. Apply the derived-project tooling approval and reconciliation steps as applicable after the stack is known.

## Progress state

Recompute it on every run from the repository itself; keep no state file.

- Cleanup: which of these still exist: `.github/workflows/template-checks.yml`, `.scripts/run-checks.mjs`, `.scripts/tests/`, `.scripts/check-security-skill.mjs`, `.scripts/security-skill-hash.mjs`, `.readme/94-template-ci.md`. They are the template-only files that `.scripts/template-files.mjs` lists (`TEMPLATE_ONLY`) and `.readme/96-template-adoption.md` describes in its «Qué pertenece a la plantilla» section; when it describes a file this list lacks, or the reverse, report ⚠️ and delete only what both agree on. The 5 `.scripts/run-checks.mjs` entries and the `node .scripts/browser.mjs *` exemption of the sealed `.claude/settings.json` are not part of Cleanup: they stay, because a local file cannot remove entries of the shared one, and the write-scope hook denies creating a template-only path in a derived project.
- Remote: whether `git remote get-url plantilla` exists; when it points anywhere but the template, report ⚠️ and leave it.
- Existing code: a root manifest such as `package.json`, `pyproject.toml`, `go.mod`, or `Cargo.toml`, or source directories the template does not ship, mean the installed stack governs: propose deleting stack.md's Selected Stack, as its guide line says.
- Markers: `TODO`, or bracketed text that is not a Markdown link, link reference, or checkbox; ignore code spans, fenced blocks other than README's `text` blocks, frontmatter keys, `stack:generated` blocks, and Template Tooling.
- Each section is pending (has markers), deferred (has markers and a referenced entry in backlog.md), later (filled by later work, per documents.md), or done (no markers). Registered pending detail for every document lives only in backlog.md under `11`; the other documents retain the entry reference.
- Tooling is done when every installed skill is a baseline skill, is used by the Selected Stack, or with existing code by the installed stack, or carries in its stack.md Notes cell the user's decision to keep it.
- Resume at the first step with pending items. Do not ask again about done or deferred items unless the user wants to; mention the deferred ones once in the opening, together with any declined cleanup or remote and the state of tool servers and the language-server binary, which have no resumable marker.

## Conversation

- Talk in the user's language; write each document in the language `AGENTS.md` sets for it.
- Ask everything in the chat as plain text: never use a question tool such as `AskUserQuestion` or `request_user_input`. Give every question its context: what it decides, which document and section it fills, and a short example of an answer.
- Open with two to four lines: what `/start` does, what is already done, and what comes next; then ask the first question.
- One topic per turn, with at most three related questions. Use plain words and explain a term with an example, such as an invariant being "a rule that must never break". Never dump a questionnaire.
- Reuse what the user, the invocation text, and the repository already settle; confirm an inference instead of asking again. Offer options only when evidence supports them, and recommend one only with a stated reason.
- "No sé" or "después": keep the marker, add a backlog.md entry under `11` naming the section, what is missing, and the condition that resolves it, with who decides only when the user names someone, reference that entry from the section, and move on. This includes open items of security.md and README. "No aplica": write that it does not apply and why, in the document's language, and delete the section only when its guide line allows it and nothing links to it. Follow `11` for backlog.md; other empty registers keep their table header and get a single row saying there is none, in the document's language.
- Interview answers supply document content and are not the open decisions of `AGENTS.md`. Approvals are: batch each step's deletions, remote, tooling changes, installs, and deviations into one message with reason, impact, and alternatives, which is that step's single round under `AGENTS.md`, with plain chat as the question mechanism, and act only on an explicit yes.
- Write each section as soon as its topic is settled, so an interruption loses nothing. After each document, summarize what was recorded and what stays open, with a link to the file, and apply corrections before moving on. A settled fact that belongs to a later document is written there at once and not asked again.

## Workflow

1. Orient: run the guard, route to Start from scratch when applicable, or compute the derived-project progress state and open. In a session that cannot receive replies, report the state and stop, unless the request already gives the approvals and answers the next steps need; then continue with them and stop at the first decision they do not cover.
2. Cleanup: one approval message for the deletions and the remote. Remove `.github/` once empty; leave `.agents/template-version` and `.agents/template-manifest.json` as they are; the stack hook regenerates its workflows block, and when it did not run, `node .scripts/update-stack-doc.mjs` does.
   - Leave `.claude/settings.json` as it is, the template-only entries and the browser launcher exemption included ([references/tooling.md](references/tooling.md)).
3. product.md, by the topics in documents.md.
4. design.md: first ask whether the project has a user-facing surface. Write tokens only for brand values the user marks as binding; otherwise record one open decision leaving the visual direction to the UI design workflow when the first screen is built, or, with an existing interface, documenting that interface through it. Never ask about aesthetic styles or CSS values.
5. stack.md: apply the existing-code check. When the user delegates the choice, propose a stack with reason, impact, and alternatives, and record `delegated: …` only after the user accepts that proposal; delegating the choice does not accept it in advance. Approved Target Versions get exact stable versions verified in the session. Outside the declared and resolved versions of Platform Versions and Dependencies (`06`), never copy a value that a manifest pins.
6. plan.md, at decision level: no reproduced implementation identifiers or versions (`10`), only the path of the source that fixes a decision, while pending-item identifiers and links are allowed. The phase table takes only the delivered phases that documents.md lets existing code record; unfinished phases go to backlog.md (`11`). The end-to-end line and the agent-operated browser verification line are resolved as documents.md says; the end-to-end decision offers one of the template's two automation tools from project evidence, installs nothing, and creates no configuration or test files.
7. security.md's Status, then README.
8. Tooling, by references/tooling.md, with one approval message, which includes the sandbox exemption for the end-to-end runner when the project adopted end-to-end tests that start a browser, an Electron app, or a mobile emulator or simulator; every grant, exemption, and plugin in that message is written to `.claude/settings.local.json`, and the message warns that the file is per person (git ignores it, cloud sessions do not read it).
9. Reconcile: run the checklist in documents.md, then `node .scripts/check-doc-links.mjs` and `node .scripts/check-instructions.mjs`, which must print nothing; confirm stack.md's generated blocks reflect the deletions and removals, and rerun the checks after any fix.

## Report

In the user's language, one line per applicable item: adoption version and fixed ref, local or GitHub repository, cleanup, remote, each changed document, deferred decisions with their backlog.md identifiers, starter base and its verification, skills, tool servers, language-server binary, the Codex hook-trust notice, and the checks. Start each line with ✅, ❌, ⚠️, 🚫, ⏳, or ℹ️, grouping the lines in that order. For empty adoption report that the skeletons are ready with no application or selected stack. The ordinary derived-project report may name the first commit as the next step, made only if the user asks (`12`, or `/commit`). Scaffolding belongs only to the explicit mockup build.

## Client bindings

- Invocation: `/start` in Claude Code, `$start` in Codex. Before a project exists, a user can copy this entire skill directory to `~/.claude/skills/start` or `~/.agents/skills/start` respectively. Questions are plain chat text in every client.
- When a client's sandbox blocks a step, such as `git remote add` writing `.git/config` or `skills add` writing `.agents/skills/`, retry that one command through the client's approval or escalation prompt, or give the user the exact command; never widen sandbox settings. A blocked command never ran (`16`).
- Deleting the template-only files under `.scripts/` differs by client: in Claude Code the protected-paths hook asks for confirmation, so run the deletion once the user approves it; in Codex that hook runs with `--deny` and rejects the command whether or not the agent escalates, so give the user the exact command to run themselves and keep the step ⏳ until they say it ran.
- Non-interactive sessions, such as `claude -p` or `codex exec`, stop at the first missing answer or authorization and report the progress state.
