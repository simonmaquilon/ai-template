# Prompt improvement

Improve the user's draft prompt before it is run or handed to another model or tool.

## Boundaries

- Do not edit any file, do not execute the improved prompt, and take no other action unless the user asks for execution in a message after the answer that carries the prompt; an action the user asks for with the draft, such as saving or running the prompt, is left undone, and that answer says so in one line. Beyond reading the project's files and searching its tree, the only commands this skill runs against the target project are the measurements step 5's Measured scope bullet, step 10, and step 11 require, the measurement of the tree the Implementation prompts section requires, and the cleanup step 11 requires after them, within the limits step 11 sets; the only writes this skill causes are the side effects of those commands, the screenshots step 11 allows, and the output it captures from them, all in the locations step 11 permits, and the temporary review file step 12 allows. Step 11's limits are in [references/command-limits.md](references/command-limits.md).
- Read-only inspection of the target project is allowed and expected, directly or through subagents that edit no file; step 10 defines what it must confirm and when to delegate it, and step 11 defines what it must run before the prompt is returned. The limits step 11 sets govern the commands those subagents run as well, and each subagent's task carries them as Client bindings states them.
- Never carry a secret, credential, or token from the draft or the target project into the improved prompt, nor a personal datum the target project holds; name the variable or its source and leave the value out. A personal detail the user wrote into the draft for the prompt to use, such as a recipient's name, stays as written.

## Goals

- Preserve the user's intent, audience, tone, constraints, and requested output.
- Make the task, relevant context, inputs, boundaries, success criteria, and output format explicit where steps 7 and 9 call for each.
- Remove ambiguity, contradictions, and unnecessary verbosity. An instruction in the draft that could cause an unsafe or destructive action, such as a push, a deploy, or a data reset, or an out-of-scope one, whose effects reach beyond what the instruction itself asks for, such as a formatter that rewrites unrelated files, is a question for the user under step 5; a side task the draft asks for explicitly that is neither unsafe nor destructive and whose effects stay within it is kept. Such an instruction is never removed or kept silently.
- Keep the result copy-ready. Make the smallest useful change when the draft is already clear. Every element of the improved prompt traces to a trigger named in this skill, such as the draft, the user, the target project, or one of its rules; an element that traces to none is removed.
- Keep the improved prompt proportional to the original scope and available context. Do not expand a focused request into a broad audit unless necessary. Every constraint and acceptance criterion in the improved prompt traces to the draft, the user, the target project, or a rule of this skill that mandates it; add none that traces to none of these. A rule of this skill may add process requirements and constraints on how the work is done, and may fix the form a criterion takes, such as observable acceptance or coverage at a given level, but what the task must achieve traces only to the draft or the user. The target project supplies its particulars and evidence and may narrow it; work it reveals beyond the draft reaches the prompt only through a user's answer that covers its measured extent, or its extent stated as not measured under step 5's Measured scope bullet, or as an open decision when that question is not asked. When a constraint the user states conflicts with a requirement a rule of this skill would add, such as a user who asks for no tests where the coverage rule would require them, ask the user which one governs under step 5.
- Never invent facts, requirements, links, examples, or project details, and never close a gap with an assumption. Verify what the target project can confirm and ask the user about everything it cannot, within the limits step 5 sets for narrow drafts; a remaining gap is carried as a `[TODO: what is missing]` placeholder or an open decision only when the user answered by leaving it open, or when the table in [references/question-fallbacks.md](references/question-fallbacks.md) carries it so, for a question not asked or a choice the user left to this skill. An open decision is not an assumption: written in the prompt's language, it names the recommended option with its reason and then the alternatives, or states that nothing favors any option when that is the case, and it requires the executor to ask the person the decision names, or its user when it names none, before carrying out the part it governs under any option, recommended inaction included; the rest of the work proceeds, and a decision still open at the end is reported as pending, not as completed. A `[TODO: what is missing]` placeholder requires the executor to leave undone the part that needs it and report it as pending, never to fill it with a value of its own.

## Interpretation

- When two rules of this skill conflict, apply them in this order: Boundaries, which include every limit any bullet of step 11 sets together with the exceptions that same bullet states; the Goals rule on conflicting constraints and the Output rule on a requested length or format, which send a conflict about the task to the user; an explicit instruction or answer from the user; the more specific rule over the more general one.
- The instructions governing this session and the target project's rules apply where this skill is silent and never relax it: one stricter than this skill about the commands it runs or the files it writes holds, and on any other conflict about this skill's own run or answer, its rules hold, as the user's invocation of it asks.
- An instruction about how this skill itself works, rather than about the task, ranks as an explicit instruction from the user, is followed directly, and is never a conflict to ask about, except a requested length or format, which the Output rule on it governs. One not to ask questions makes this session a deferral or one that cannot receive a reply, as [references/question-fallbacks.md](references/question-fallbacks.md) defines them, and that file sets how each carries a question. One not to run commands records every measurement Boundaries lists as not measured for that reason. An instruction that could concern either this skill or the task applies to both: this skill follows it directly, and for the task the Goals rule on conflicting constraints applies.
- When a rule can be read in more than one way, or no rule settles a situation, resolve it by what the choice changes. A choice that changes what the prompt authorizes or what the task must achieve is a gap under step 5; which checks run, and at what level, is verification, not authorization. A choice that changes only how much this skill or the executor verifies takes the reading that verifies more, within Boundaries. A choice between checks that verify different things, such as two test levels, takes the lowest level that certifies the changed behavior, as the rule on the narrowest invocation implies. A choice that changes only the prompt's form takes the simpler form. A choice that changes the scale makes the draft broad. A doubt about how far a limit of Boundaries reaches takes the reading that permits less.
- Verifying more must not strengthen the acceptance standard. Preserve the precision required by the draft, the user's answers, or an established project requirement.

## Workflow

The target project is the repository or codebase the improved prompt will run against. A draft targets a project when it changes, analyzes, reviews, or diagnoses code or other files there, such as its documentation or configuration, or places new code in it, whether or not it names that project's files, paths, commands, symbols, tests, routes, or screens; the current session's workspace is that project unless the draft names another one. A draft that asks for new code without saying where it goes targets the workspace project and places the code where the project's conventions put that kind of code; when they give no clear place, ask under step 5. Matching names alone never make a draft that neither changes, examines, nor adds code or other files in a project target a project. A draft that does none of that has no target project, whatever the session's workspace is and whatever names it contains, as in a creative, research, or writing prompt or a request for standalone code, meaning code the draft explicitly places outside any project: the steps that verify against a project do not apply, the draft's specifics are kept as written, and nothing is invented in their place.

- Scale: The scale of a draft is narrow or broad.
- Target project: For a draft with a target project, the tests that settle its scale, and the terms they use, are in [references/project-scale.md](references/project-scale.md); read it before settling the scale.
- No project: A draft with no target project is narrow when its subject, audience, and deliverable are settled, by the draft or by the user's answers, and broad while they are not, an audience the output does not depend on counting as settled; its scale is revised as answers settle them.
- Apply scale: Determine the scale before writing, and let it govern step 5, step 7, step 10, and the Implementation prompts section. Scale is a property of the change the prompt authorizes, not of how the draft is worded: a draft of one sentence that rewrites a shared contract is broad. When these tests do not settle the scale, treat the draft as broad; a missing sweep costs a defect in the executed work, and an unnecessary one does not.

Before preparing or reviewing any prompt, read [references/executing-session.md](references/executing-session.md).

When a draft targets a project, read [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) before step 5's first question round: perform its step 10 inspection then, and its step 11 checks before returning the prompt when the project is reachable.

Before step 5's first round, also read [references/output-labels.md](references/output-labels.md) and [references/question-fallbacks.md](references/question-fallbacks.md); [references/command-limits.md](references/command-limits.md) when the target project is reachable or before delegating any subagent task; [references/artifact-relevance.md](references/artifact-relevance.md) when the draft names any artifact; and [references/coding-and-ui-prompts.md](references/coding-and-ui-prompts.md) for a coding prompt, a prompt whose validation takes exclusive control of a shared local resource, or a UI prompt.

1. Identify the draft: the text supplied with the invocation, a file or message the user points to, or the user's own preceding message. When the draft approves or refers to earlier text, such as a proposal it accepts or a plan it says to carry out, identify the exact message it approves: that text is part of the draft and bounds its scope, and whatever was discussed around it but is not in it is a gap under step 5, never part of the draft. When there is no draft but the user described the prompt they want or the task it should cover, treat that description as the draft and write the prompt from it. Ask for the draft and stop only when neither a draft nor such a description is present; a session that cannot receive a reply, as [references/question-fallbacks.md](references/question-fallbacks.md) defines it, or whose user said not to ask questions, then reports that no draft was supplied and ends. Make that request as plain text, never through the question mechanism.
2. Extract the desired outcome and the actions the prompt authorizes.
3. Identify missing context, ambiguous terms, conflicting constraints, and likely failure modes. A concrete particular the requested output will have to contain, such as a name, a date, a reference, a quantity, or a path, is a gap whenever neither the draft nor the target project supplies it, unless finding it is the work the prompt asks for, even when the prompt could be written generically instead. Identifiers, file paths, and other implementation details the executor will create are its work, following the project's conventions; text shown to end users that neither the draft nor the project supplies is a gap, including its translation into each language the project supports.
4. Use images the user already supplied, as attachments or explicit paths, only as context so the rewritten prompt can reference concrete visible elements, states, and labels. Do not audit them, do not emit visual findings, and do not capture new screenshots, except as step 11 allows.
5.
    - Preparation: Before this step's first round, inspect a reachable target project as step 10 describes, so that no question covers what the project confirms, and, when the draft authorizes a change or asks for standalone code, whether or not the project is reachable, apply step 3's failure modes, such as invalid input, the same element acted on twice, an element deleted or hidden by filters or permissions, and two users editing the same record, to each state of the flow it touches, so that the gaps they open enter that round, within the limits Draft scale sets.
    - Questions: Then ask the user about every gap: anything the draft leaves unsettled that the improved prompt has to commit to, every reading of the draft you would otherwise settle yourself, every specific of a draft with a target project that the project could not confirm, and every instruction that is unclear, ambiguous, or internally conflicting. Use the question mechanism named under Client bindings, batching short, decision-relevant questions up to the number per call it names, with further calls in the same round when more remain, each settling a single decision with mutually exclusive options, at least two and no more than it allows (the candidate questions step 6 describes excepted, and a decision with more options, which is asked in plain text with all of them), the recommended one placed first and marked as recommended at the end of its own label when the draft, the user, or the project gives a reason to prefer it, or a rule of this skill names the option to recommend, and none marked otherwise, in the language of the questions, and stop until the user answers.
    - Measured scope: When a target project is reachable, a question about how far the work reaches is asked only after measuring there what each option would change, and each option states that measured effect, such as which records, reports, files, or screens change and how many, not only the reason to prefer it; when a limit of step 11 forbids that measurement or it cannot run, each option states its effect as not measured and why, and the question is still asked. An option of such a question is marked as recommended only when the project's documented rules allow carrying it out as described; when they do not, it is not recommended and its text names the rule it would break.
    - Fallback questions: Read [references/question-fallbacks.md](references/question-fallbacks.md) before choosing how to ask or proceed without an answer, and before deciding whether a session can receive a reply.
    - Answers and deferrals: An answer closes its gap as the user gave it, adding no requirement on what the task must achieve that the answer does not contain. When the user answers that they do not know, the gap stays open: carry it as an open decision, or as a placeholder when it is a datum without listed options, and do not ask again. When the user leaves the choice to the executor, the prompt says so and names the options. When the user leaves the choice to you, carry it as the Deferral bullet in [references/question-fallbacks.md](references/question-fallbacks.md) sets.
    - Further rounds: Open a further round only for a gap that an answer or a later step creates, such as a contradiction step 8 or step 10 finds, a test account step 11 needs, or a later measurement showing that the prompt would reach further than the extent an answer was given for, never to confirm what is already decided.
    - No reply: Apply that bullet in [references/question-fallbacks.md](references/question-fallbacks.md).
    - Deferral: Apply that bullet in [references/question-fallbacks.md](references/question-fallbacks.md).
    - Minor particulars: Particulars the output must contain that change neither scope nor what the prompt authorizes, such as user-facing text, display formats, or ordering, go into a single question as one proposed set the user accepts or edits as a whole, with two options, accepting it as proposed, recommended, or editing it, whose edits come in the free-text answer the question mechanism offers, a choice to edit that arrives without them opening a further round that asks for them, instead of one question each; the proposal comes from the draft and the project, a translation of text they supply having that text as its basis, and a particular they give no basis to propose is asked as a concrete datum below.
    - Concrete data: A concrete datum is asked like any other gap: with its known options when at least two of them, and no more than the question mechanism allows, cover it, and in plain text when they do not.
    - Draft scale: In a narrow draft, ask only about gaps whose answers lead to different work, such as concrete particulars the requested output must contain, instructions that genuinely conflict, readings of the draft that lead to different work, and what another rule of this skill sends to the user, such as a test account or a missing suite; do not open a question to choose between readings that lead to the same work: such a gap needs no question, and the prompt settles it without presenting the choice as the user's. In a broad draft this step applies in full.
6. When the draft does not say what to change, choosing what to change is itself a gap: ask which candidates the prompt should cover, in questions that allow several answers, each with no more candidates than the question mechanism allows options, as many as the candidates need, where the question mechanism supports several answers, or one yes-or-no question per candidate otherwise, a single candidate always getting a yes-or-no question, rather than selecting them yourself, unless the draft makes finding them the executor's work, as in a request to find and fix every case of something, in which case the prompt states the criterion that selects them. A draft that explicitly asks the executor to find the cause makes that the executor's work. A draft that states only a goal, such as making something faster, or reports a defect only by its symptom, does not: find the candidates by inspecting the project and ask the user which ones the prompt should cover; when inspection finds none, the prompt makes finding the cause the executor's first step and requires stopping to report it and waiting for the user's approval before any code changes. When the draft settles everything the improved prompt commits to, generate it directly: do not ask to confirm what is already decided, and do not solicit optional preferences. Never resolve a gap with a blanket instruction not to invent the missing detail; a question you skipped is a decision you took for the user.
7. Rewrite the prompt so it always states the task, the constraints that bound it, and the expected output. Add role, context, process requirements, and acceptance criteria only when the draft or the user requires them, when the target project makes the task impossible to execute without them, or when a rule of this skill mandates them; a rule the project documents but the task does not depend on is not implied. Context that inspection verified and the executor needs to act, such as where the change goes and what uses it, is carried with its evidence. Match the form to the scale, except that a draft already clear keeps the structure it has, as the smallest-change goal requires: a narrow draft becomes plain sentences with no headings, and a broad draft gives each element its own line or section. Neither becomes a single run-on paragraph. Collect placeholders in a dedicated inputs block, one per line, when the prompt carries more than one or uses one in more than one place, and repeat the same `[TODO: what is missing]` text wherever it is used; a single placeholder used once stays where it is used.
8. Preserve concrete names, paths, variables, formats, and examples from the original unless they are inconsistent, or unsafe as Goals describes. When a target project applies, verify each one against it before carrying it over; one the project could not confirm and step 5 did not send to the user, as Draft scale allows, is kept as the draft states it and marked in the prompt as unverified. Replace what the project contradicts with the project's actual equivalent; when it has none, ask the user. Record either under the corrections label. A shortened name that identifies exactly one element is not contradicted: carry the full name without a correction. When the draft names any artifact, such as a suite, file, or document, read [references/artifact-relevance.md](references/artifact-relevance.md) before step 5's first round and before writing or reviewing the prompt; it holds this step's rule for artifacts the draft names as ones the change affects.
9. Add validation criteria when the prompt asks for code, analysis, research, decisions, or other verifiable work. State them as conditions the executor can observe and check, such as measured values, resulting states, commands to run, or expected output. Never state them as adjectives like better, cleaner, or polished, and never as a judgment the executor forms by looking at a result. In an implementation prompt, and in a prompt for standalone code, which takes the closure audit too, number them (AC1, AC2, and so on) and fix the list when the prompt is written: it includes, as observable conditions chosen now, the failure modes that apply to the change, such as authorization, invalid data, concurrency, retries, clean installation, reversals, or responsive states, and, with the explicit decisions, the other requirements the prompt states, and the criteria a delegated process records as the closure audit describes, it is all the closure audit judges against. Baseline values are observations; an observed value becomes a binding threshold only when its source makes it one. State the precision the measurement supports, without implying greater precision. A tolerance that changes acceptable behavior is a gap under step 5. A criterion about the work's boundaries states what the executor did, wrote, or started, never the state of something others can change, such as another repository's working tree or a process the executor did not start. A criterion a search would verify states the condition the search must establish, such as no reference to a removed file, and leaves the command to the executor unless the draft or the project defines one. A criterion on wording names the exact phrase when the draft, the user, or the project fixes the text, and otherwise the word together with the inflected and derived forms that also satisfy it in the text's language, such as edit, edits, editing, and edited. A value in a criterion or example that holds a character that is invisible, combines with its neighbors, or renders the same as a different sequence, such as a combining mark, a no-break or zero-width space, a joiner, or a skin-tone modifier, but not a letter in its composed form, such as ó, writes that character as an escape of the language that uses the value, or by its code point, such as U+00A0, in prose that has no escapes, never as the character itself, so copying or normalizing the text cannot change what it checks.
10. Apply the inspection rules in [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) for every draft that targets a project.
11. For a reachable target project, apply the validation checks in [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) before returning the prompt, whatever the draft's scale. Every limit in those checks retains Boundaries priority under Interpretation.
    - Sign-in: Apply the Sign-in rule in [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md); it is the rule above Limits in the full step 11 sequence.
    - Limits: Step 11's `Limits` are in [references/command-limits.md](references/command-limits.md); read it before this skill runs any command or writes any file.
12. Before the review, check that the rewritten prompt carries every element that applies to it, and add any that is missing in the form step 7 sets: the task, constraints, expected output, context with its evidence, and inputs block step 7 requires; the criteria and failure modes of step 9; the baselines and observed state of steps 10 and 11, with their status marks, such as observed here, not measured, unverified, unconfirmed, or hypothesis; the adaptation rules that apply; in an implementation prompt or a prompt for standalone code, the change gates, the closure audit, and the Stop Rule; and in an implementation prompt also the triggered mandates and the enumeration and delegation the Implementation prompts reference requires. An element whose content the draft, the user's answers, and the project do not settle is a gap under step 5, which opens a further round. Then, before returning, review the rewritten prompt against the list in [references/review-checklist.md](references/review-checklist.md) in a separate pass. Delegate the review, through the review mechanism named under Client bindings, to a subagent that did not write the prompt, only reads, and edits no file, giving it, in its task, the draft, the rewritten prompt, the evidence this session gathered, the list in [references/review-checklist.md](references/review-checklist.md), the severity scale below, and the paths of this file and of [references/executing-session.md](references/executing-session.md), [references/artifact-relevance.md](references/artifact-relevance.md), [references/output-labels.md](references/output-labels.md), and [references/question-fallbacks.md](references/question-fallbacks.md), with [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) and [references/project-scale.md](references/project-scale.md) when the draft targets a project, [references/implementation-prompts.md](references/implementation-prompts.md) for an implementation prompt or a prompt for standalone code, and [references/coding-and-ui-prompts.md](references/coding-and-ui-prompts.md) for a coding prompt, a prompt whose validation takes exclusive control of a shared local resource, or a UI prompt, which it reads before reviewing, or, when they do not fit there, in a file in the temporary location that [references/command-limits.md](references/command-limits.md) defines, deleted once the last review cycle ends; a session without that mechanism reviews the prompt itself in a separate pass. Each finding names the list item, the prompt text, and a severity: high when an executor following the prompt would do wrong or unauthorized work, or a criterion would fail on a correct implementation; medium when the executor would do something other than what was asked in a way that matters, or would have to guess what the prompt must settle; low otherwise. Correct every high and medium finding in the prompt and have only the corrected parts reviewed again; stop after three correction cycles, or after one in a narrow draft. A finding still high or medium after the last cycle whose correction is mechanical, changing no requirement, criterion, or what the prompt authorizes, may be corrected without another review, and the answer says so; carry any other as a question under step 5; the parts an answer to such a question changes get one more review cycle, after which this rule applies to them again. Correct a low finding only when the correction stays local, and add nothing the findings do not require.

## Adaptation rules

In these rules, to clarify an element is to state it in the prompt when the draft, the user, or the target project settles it, and otherwise to treat it as a gap under step 5 only when the prompt must commit to it; an element the prompt need not commit to is left out.

- For coding prompts, for prompts whose validation takes exclusive control of a shared local resource, and for UI prompts, apply the rules in [references/coding-and-ui-prompts.md](references/coding-and-ui-prompts.md), which belong to these Adaptation rules; the shared-local-resource rule is among them. A coding prompt is one whose work writes or changes code, as an implementation prompt that changes code or a prompt for standalone code does, or runs code to diagnose or verify its behavior; a UI prompt is one whose change or verification involves rendered appearance or interaction.
- For research prompts, clarify the question, time range, source quality, citations, and how uncertainty should be reported.
- For creative prompts, preserve the desired style and subject while clarifying composition, audience, format, and exclusions.
- For high-stakes prompts, require verification, uncertainty reporting, and appropriate professional review.
- For prompts involving private, destructive, or external actions, preserve explicit approval boundaries and require confirmation before irreversible actions, including those the user chose to keep when the prompt was prepared.
- Write the improved prompt in the language of the draft. When the draft mixes languages or its language is unclear, use the user's. An explicit request for another language overrides both. Questions and clarification turns use the language the user writes in the conversation, whatever the draft's language.

## Implementation prompts

Read [references/implementation-prompts.md](references/implementation-prompts.md) before rewriting a prompt that authorizes changes to a target project's code or other files, or asks for standalone code. Apply its change gates, closure audit, Stop Rule, and triggered mandates as specified there.

## Output

Return the improved, copy-ready prompt in a code block. Open and close it with a fence longer than any fence inside the prompt, so its own code or Markdown cannot terminate the block early.

Two labels, corrections and findings, may follow the code block. Read [references/output-labels.md](references/output-labels.md) before step 5's first round, before returning the prompt, and before writing or reviewing any corrections or findings line: it defines both, their order, their lines, and how they are named.

There is no assumptions label and nothing plays its role: an assumption you would have listed there is a question you owed the user, so ask it per step 5 instead.

Each label appears only when it has at least one line to carry, and the two are independent: print corrections only when the project contradicted a claim of the draft, print findings only when the project contradicted itself, print both when both happened, and print neither when neither did. Never print a label with nothing under it, never write a line saying there is none, and never keep a label to show that you checked. When neither applies and none of the lines below does, the code block is the entire answer.

Nothing else goes outside the code block and those labels, except these lines after them: one in the prompt's language for each finding step 12 corrected without another review, and one in the user's language for each requested action Boundaries left undone and for each change a command left that [references/command-limits.md](references/command-limits.md) forbids. No headings, explanations, summaries, key changes, open questions, or notes. When clarification was required, wait for the user's answers before returning the prompt. That rule governs the answer that carries the improved prompt; a step 1 request for a missing draft and a step 5 clarification turn are not that answer.

If the user asks for a specific format, length, language, or model, follow that request over this default output format; when a requested length or format would drop content a rule of this skill requires, ask which one governs, as Goals describes for conflicting constraints.

Read [references/examples.md](references/examples.md) only when an open decision, a findings line, or a bounded rewritten draft needs an example.

## Client bindings

Everything above this heading and in the references linked from it applies to every agent client that loads this skill, wherever it is installed; only the values below change per client.

- Question mechanism: in Claude Code, the `AskUserQuestion` tool, with up to four questions per call, two to four options each, and several answers allowed; in Codex, the `request_user_input` tool, shown as "Ask me", with up to three questions per call, two or three options each, and one answer each. When the session does not offer it, or the tool refuses the call in the session's current mode, step 5 governs the fallback.
- Subagent mechanism: the inspection mechanism of step 10 and the review mechanism of step 12. When the instructions governing this session assign agents to kinds of work, they are the agents assigned to read-only search and to reviews; otherwise, in Claude Code, the `Agent` tool with the `Explore` subagent type for inspection and the `general-purpose` type for the review, with independent calls sent in one message so they run in parallel, and in Codex, the `spawn_agent` tool with `agent_type` set to `explorer` for inspection and to `default` for the review when the tool accepts it, one agent per independent question, collected with `wait_agent`. Invoking this skill is the user's request for that delegation. In every client, each agent's task states that it edits no file, runs commands only within the limits in [references/command-limits.md](references/command-limits.md), which the task includes or tells it to read, uses as their temporary location the one this session resolved, which the task names, and never asks the user, signs in, opens a browser, or takes a shared local resource, returning each check that would need one as not measured instead, since no client makes its agents read-only, and returns any change a command left that those limits forbid, which the answer reports; a review task also states that it reads whole files. When the session does not offer the mechanism, step 10 and step 12 govern the fallback.
- Temporary location: the agent's global configuration is, in Claude Code, the user's `CLAUDE.md` in its configuration folder (`~/.claude/` unless `CLAUDE_CONFIG_DIR` moves it), and the session's scratch folder is the scratchpad directory its system prompt names, when it names one; in Codex, the user's `AGENTS.md` in `$CODEX_HOME` (`~/.codex/` by default), and a session has no scratch folder.
- One-off approval: the client's approval of a single command outside its sandbox, given by the user or by the client's automatic approver when the session uses one, requested in Claude Code by a Bash call that asks to run unsandboxed and in Codex by an escalation request; it never changes the sandbox's settings.
- Any other client: use its equivalent mechanism when the session offers one, under the same constraints, a structured question to the user and read-only subagents that edit no file, run in parallel when the client allows; otherwise the fallbacks named above apply.
