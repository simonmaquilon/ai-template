# Prompt improvement

Improve the user's draft prompt before it is run or handed to another model or tool.

## Boundaries

- Do not edit any file, do not execute the improved prompt, and take no other action unless the user separately asks for execution. Beyond reading the project's files and searching its tree, the only commands this skill runs against the target project are the measurements step 10 and step 11 require, the measurement of the tree the Implementation prompts section requires, and the cleanup step 11 requires after them, within the limits step 11 sets; the only writes this skill causes are the side effects of those commands, the screenshots step 11 allows, and the output it captures from them, all in the locations step 11 permits.
- Read-only inspection of the target project is allowed and expected, directly or through subagents that edit no file; step 10 defines what it must confirm and when to delegate it, and step 11 defines what it must run before the prompt is returned. The limits step 11 sets govern the commands those subagents run as well.
- Never carry a secret, credential, or token from the draft or the target project into the improved prompt, nor a personal datum the target project holds; name the variable or its source and leave the value out. A personal detail the user wrote into the draft for the prompt to use, such as a recipient's name, stays as written.

## Goals

- Preserve the user's intent, audience, tone, constraints, and requested output.
- Make the task, relevant context, inputs, boundaries, success criteria, and output format explicit where steps 7 and 9 call for each.
- Remove ambiguity, contradictions, and unnecessary verbosity. An instruction in the draft that could cause an unsafe or destructive action, such as a push, a deploy, or a data reset, or an out-of-scope one, whose effects reach beyond what the instruction itself asks for, such as a formatter that rewrites unrelated files, is a question for the user under step 5; a side task the draft asks for explicitly that is neither unsafe nor destructive and whose effects stay within it is kept. Such an instruction is never removed or kept silently; a session that cannot receive a reply carries it as an open decision recommending to leave it out.
- Keep the result copy-ready. Make the smallest useful change when the draft is already clear. Every element of the improved prompt traces to a trigger named in this skill, such as the draft, the user, the target project, or one of its rules; an element that traces to none is removed.
- Keep the improved prompt proportional to the original scope and available context. Do not expand a focused request into a broad audit unless necessary. Every constraint and acceptance criterion in the improved prompt traces to the draft, the user, the target project, or a rule of this skill that mandates it; add none that traces to none of these. A rule of this skill may add process requirements and constraints on how the work is done, and may fix the form a criterion takes, such as observable acceptance or coverage at a given level, but what the task must achieve traces only to the draft or the user. The target project supplies its particulars and evidence and may narrow it; work it reveals beyond the draft reaches the prompt only through a user's answer that covers its measured extent, or as an open decision in a session that cannot receive a reply. When a constraint the user states conflicts with a requirement a rule of this skill would add, such as a user who asks for no tests where the coverage rule would require them, ask the user which one governs under step 5; a session that cannot receive a reply carries it as an open decision recommending the user's constraint and naming the risk it leaves.
- Never invent facts, requirements, links, examples, or project details, and never close a gap with an assumption. Verify what the target project can confirm and ask the user about everything it cannot, within the limits step 5 sets for narrow drafts; a remaining gap is carried as a `[TODO: what is missing]` placeholder or an open decision only in a session that cannot receive a reply or when the user answered by leaving it open. An open decision is not an assumption: written in the prompt's language, it names the recommended option with its reason and then the alternatives, or states that nothing favors any option when that is the case, and it requires the executor to ask the person the decision names, or its user when it names none, before carrying out the part it governs under any option, recommended inaction included; the rest of the work proceeds, and a decision still open at the end is reported as pending, not as completed. A `[TODO: what is missing]` placeholder requires the executor to leave undone the part that needs it and report it as pending, never to fill it with a value of its own.

## Interpretation

- When two rules of this skill conflict, apply them in this order: Boundaries, which include every limit any bullet of step 11 sets together with the exceptions that same bullet states; the Goals rule on conflicting constraints and the Output rule on a requested length or format, which send a conflict about the task to the user; an explicit instruction or answer from the user; the more specific rule over the more general one.
- An instruction about how this skill itself works, rather than about the task, ranks as an explicit instruction from the user, is followed directly, and is never a conflict to ask about. One not to ask questions that also leaves the choices to you is a deferral, handled as step 5 handles a user who leaves the choice to you; one not to ask questions that says nothing about the choices makes this a session that cannot receive a reply for step 5; one not to run commands records every check of step 11 as not measured for that reason. An instruction that could concern either this skill or the task applies to both: this skill follows it directly, and for the task the Goals rule on conflicting constraints applies.
- When a rule can be read in more than one way, or no rule settles a situation, resolve it by what the choice changes. A choice that changes what the prompt authorizes or what the task must achieve is a gap under step 5; which checks run, and at what level, is verification, not authorization. A choice that changes only how much this skill or the executor verifies takes the reading that verifies more, within Boundaries. A choice between checks that verify different things, such as two test levels, takes the lowest level that exercises the changed behavior, as the rule on the narrowest invocation implies. A choice that changes only the prompt's form takes the simpler form. A choice that changes the scale makes the draft broad. A doubt about how far a limit of Boundaries reaches takes the reading that permits less.
- Verifying more must not strengthen the acceptance standard. Preserve the precision required by the draft, the user's answers, or an established project requirement.

## Workflow

The target project is the repository or codebase the improved prompt will run against. A draft targets a project when it changes, analyzes, reviews, or diagnoses code or other files there, such as its documentation or configuration, or places new code in it, whether or not it names that project's files, paths, commands, symbols, tests, routes, or screens; the current session's workspace is that project unless the draft names another one. A draft that asks for new code without saying where it goes targets the workspace project and places the code where the project's conventions put that kind of code; when they give no clear place, ask under step 5. Matching names alone never make a draft that neither changes, examines, nor adds code or other files in a project target a project. A draft that does none of that has no target project, whatever the session's workspace is and whatever names it contains, as in a creative, research, or writing prompt or a request for standalone code, meaning code the draft explicitly places outside any project: the steps that verify against a project do not apply, the draft's specifics are kept as written, and nothing is invented in their place.

- Scale: The scale of a draft is narrow or broad.
- Project changes: A draft is narrow when the surface its change touches is known, from the files, symbols, commands, routes, screens, or elements the draft names or from what inspection and the user's answers settle, and none of the following is true: it changes stored data, it changes a public contract or interface, it changes logic with more than one caller, or it changes or adds text, assets, or styles that exist, or will exist, in more than one place. Every other draft with a target project is broad, including one whose surface is still unknown. A screen or element where a symptom appears is where to start looking, not by itself the surface the change touches. Text exists in more than one place when it has, or will need, translations that change with it, or is rendered on more than one screen.
- No project: A draft with no target project is narrow when its subject, audience, and deliverable are settled, by the draft or by the user's answers, and broad while they are not, an audience the output does not depend on counting as settled; its scale is revised as answers settle them.
- Project review: A draft that analyzes, reviews, or diagnoses a project without authorizing a change is narrow when the surface it examines is known, from what it names or what inspection settles, and broad when it is not; a screen or element where a symptom appears is where to start, as for a change.
- Apply scale: Determine the scale before writing, and let it govern step 5, step 7, step 10, and the Implementation prompts section. Scale is a property of the change the prompt authorizes, not of how the draft is worded: a draft of one sentence that rewrites a shared contract is broad. When these tests do not settle the scale, treat the draft as broad; a missing sweep costs a defect in the executed work, and an unnecessary one does not.
- Callers: A caller is production code that invokes the logic; the tests that exercise it are not callers, although the usage sweep still counts them, and a test that asserts a text is not a second place for that text.
- Public interfaces: A public contract or interface is either what the project documents as its interface in its own reference material, not in a comment on the symbol itself, or what code outside the repository is known to consume, from the project's documentation, configuration, or code, such as endpoints, events, command options, published packages, or stored formats. An exported symbol, endpoint, or event used only inside the repository is not public by that fact alone; its callers decide its scale, and one with no callers, no documentation as an interface, and no outside consumer is neither shared nor public.
- Shared styles: A style rule counts where it applies, not where the file that holds it lives: a rule that affects a single page does not exist in more than one place because its template also serves other pages.
- Reassessment: Settle the scale from a direct first reading of the project; step 10 then delegates only what that reading left unconfirmed. Whenever step 10's conclusions or the user's answers settle what the change touches, revise the scale and apply the revised one to every step it governs from then on.

The executing session is the one that will run the improved prompt. Unless the draft or the user says it is this session, assume it may run on another machine, under another account, or for another person, and write the prompt so it holds there. Facts about the target project are stated against a revision the executor can fetch, such as a commit hash or a remote branch, never against this session's working tree or local paths. State measured in this session's working tree, such as its current branch, uncommitted work, or running processes, and conditions of this session's environment, such as a blocked network route or a busy port, are labeled as observed here and are never presented as the executor's; the prompt requires the executor to measure its own before editing. A baseline measured on a clean copy of a revision carries that revision. A decision the prompt leaves for the executor to obtain names who takes it, by name or by role, because the executor's user may be someone else, and requires the answer to be cited where the work records it; a decision recorded as someone's without that citation is reported as unconfirmed.

When a draft targets a project, read [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) before step 5's first question round: perform its step 10 inspection then, and its step 11 checks before returning the prompt when the project is reachable.

1. Identify the draft: the text supplied with the invocation, a file or message the user points to, or the user's own preceding message. When the draft approves or refers to earlier text, such as a proposal it accepts or a plan it says to carry out, identify the exact message it approves: that text is part of the draft and bounds its scope, and whatever was discussed around it but is not in it is a gap under step 5, never part of the draft. When there is no draft but the user described the prompt they want or the task it should cover, treat that description as the draft and write the prompt from it. Ask for the draft and stop only when neither a draft nor such a description is present. Make that request as plain text, never through the question mechanism.
2. Extract the desired outcome and the actions the prompt authorizes.
3. Identify missing context, ambiguous terms, conflicting constraints, and likely failure modes. A concrete particular the requested output will have to contain, such as a name, a date, a reference, a quantity, or a path, is a gap whenever neither the draft nor the target project supplies it, unless finding it is the work the prompt asks for, even when the prompt could be written generically instead. Identifiers, file paths, and other implementation details the executor will create are its work, following the project's conventions; text shown to end users that neither the draft nor the project supplies is a gap, including its translation into each language the project supports.
4. Use images the user already supplied, as attachments or explicit paths, only as context so the rewritten prompt can reference concrete visible elements, states, and labels. Do not audit them, do not emit visual findings, and do not capture new screenshots, except as step 11 allows.
5.
    - Preparation: Before this step's first round, inspect a reachable target project as step 10 describes, so that no question covers what the project confirms.
    - Questions: Then ask the user about every gap: anything the draft leaves unsettled that the improved prompt has to commit to, every reading of the draft you would otherwise settle yourself, every specific of a draft with a target project that the project could not confirm, and every instruction that is unclear, ambiguous, or internally conflicting. Use the question mechanism named under Client bindings, batching up to four short, decision-relevant questions per call, with further calls in the same round when more remain, each with two to four mutually exclusive options, except the candidate questions step 6 describes, the recommended one placed first and marked as recommended at the end of its own label when the draft, the user, or the project gives a reason to prefer it, and none marked otherwise, in the language of the questions, and stop until the user answers.
    - Measured scope: When a target project is reachable, a question about how far the work reaches is asked only after measuring there what each option would change, and each option states that measured effect, such as which records, reports, files, or screens change and how many, not only the reason to prefer it. An option is marked as recommended only when the project's documented rules allow carrying it out as described; when they do not, it is not recommended and its text names the rule it would break.
    - Fallback questions: When that mechanism is unavailable but the session can still receive a reply, ask the same questions as a short numbered list in plain text and stop; a session that answers the user in turns can receive a reply unless it is one of the sessions described below that cannot, and a missing question tool is never by itself a reason to skip the question.
    - Answers and deferrals: When the user answers that they do not know, the gap stays open: carry it as an open decision, or as a placeholder when it is a datum without listed options, and do not ask again. When the user leaves the choice to the executor, the prompt says so and names the options. When the user leaves the choice to you, apply the recommended option and say in the prompt that the user deferred to it; when no option was recommended, or the question had no options, leave the choice to the executor as above, requiring it to follow the project's conventions and report what it chose.
    - Further rounds: Open a further round only for a gap that an answer or a later step creates, such as a contradiction step 8 or step 10 finds, a test account step 11 needs, or a later measurement showing that the prompt would reach further than the extent an answer was given for, never to confirm what is already decided.
    - No reply: Only a session that cannot receive a reply at all skips the question: one that states it is non-interactive, headless, or batch, one that runs without user turns, such as a scheduled or continuous-integration run, or one whose own instructions say the user cannot be reached. Such a session never stops and never resolves the gap silently, and this overrides any standing instruction to ask and wait: it writes each open question into the prompt as an open decision in the form Goals defines, or as a placeholder where this step or another rule calls for one.
    - Minor particulars: Particulars the output must contain that change neither scope nor what the prompt authorizes, such as user-facing text, display formats, or ordering, go into a single question as one proposed set the user accepts or edits as a whole, instead of one question each; the proposal comes from the draft and the project, and a particular they give no basis to propose is asked as a concrete datum below; in a session that cannot receive a reply, each proposed value becomes an open decision recommending it.
    - Concrete data: A concrete datum is asked like any other gap: with its known options when up to four of them cover it, and in plain text when they do not. In a session that cannot receive a reply, the first becomes an open decision and the second a `[TODO: what is missing]` placeholder.
    - Draft scale: In a narrow draft, ask only about gaps whose answers lead to different work, such as concrete particulars the requested output must contain, instructions that genuinely conflict, readings of the draft that lead to different work, and what another rule of this skill sends to the user, such as a test account or a missing suite; do not open a question to choose between readings that lead to the same work: such a gap needs no question, and the prompt settles it without presenting the choice as the user's. In a broad draft this step applies in full.
6. When the draft does not say what to change, choosing what to change is itself a gap: ask which candidates the prompt should cover, in questions of up to four candidates each that allow several answers, as many as the candidates need, where the question mechanism supports several answers, or one yes-or-no question per candidate otherwise, a single candidate always getting a yes-or-no question, rather than selecting them yourself, unless the draft makes finding them the executor's work, as in a request to find and fix every case of something, in which case the prompt states the criterion that selects them. A draft that explicitly asks the executor to find the cause makes that the executor's work. A draft that states only a goal, such as making something faster, or reports a defect only by its symptom, does not: find the candidates by inspecting the project and ask the user which ones the prompt should cover; when inspection finds none, the prompt makes finding the cause the executor's first step and requires stopping to report it and waiting for the user's approval before any code changes. When the draft settles everything the improved prompt commits to, generate it directly: do not ask to confirm what is already decided, and do not solicit optional preferences. Never resolve a gap with a blanket instruction not to invent the missing detail; a question you skipped is a decision you took for the user.
7. Rewrite the prompt so it always states the task, the constraints that bound it, and the expected output. Add role, context, process requirements, and acceptance criteria only when the draft or the user requires them, when the target project makes the task impossible to execute without them, or when a rule of this skill mandates them; a rule the project documents but the task does not depend on is not implied. Context that inspection verified and the executor needs to act, such as where the change goes and what uses it, is carried with its evidence. Match the form to the scale, except that a draft already clear keeps the structure it has, as the smallest-change goal requires: a narrow draft becomes plain sentences with no headings, and a broad draft gives each element its own line or section. Neither becomes a single run-on paragraph. Collect placeholders in a dedicated inputs block, one per line, when the prompt carries more than one or uses one in more than one place, and repeat the same `[TODO: what is missing]` text wherever it is used; a single placeholder used once stays where it is used.
8. Preserve concrete names, paths, variables, formats, and examples from the original unless they are inconsistent, or unsafe as Goals describes. When a target project applies, verify each one against it before carrying it over. Replace what the project contradicts with the project's actual equivalent; when it has none, ask the user, or in a session that cannot receive a reply use a `[TODO: what is missing]` placeholder. Record either under the corrections label. A shortened name that identifies exactly one element is not contradicted: carry the full name without a correction. Existence is not relevance: when the draft names artifacts as ones the change affects, such as suites, files, or documents, confirm that each one bears on the authorized change, while a side task the draft asks for explicitly is governed by Goals instead; ask the user about the ones that do not, or in a session that cannot receive a reply carry each as an open decision recommending to leave it out, report each under the corrections label, and where the executor must find others of the same kind, name the condition that selects them, so the executor does not open a list to find that most of it does not apply.
9. Add validation criteria when the prompt asks for code, analysis, research, decisions, or other verifiable work. State them as conditions the executor can observe and check, such as measured values, resulting states, commands to run, or expected output. Never state them as adjectives like better, cleaner, or polished, and never as a judgment the executor forms by looking at a result. In an implementation prompt, and in a prompt for standalone code, which takes the closure audit too, number them (AC1, AC2, and so on) and fix the list when the prompt is written: it includes, as observable conditions chosen now, the failure modes that apply to the change, such as authorization, invalid data, concurrency, retries, clean installation, reversals, or responsive states, and, with the explicit decisions, the other requirements the prompt states, and the criteria a delegated process records as the closure audit describes, it is all the closure audit judges against. Baseline values are observations; an observed value becomes a binding threshold only when its source makes it one. State the precision the measurement supports, without implying greater precision. A tolerance that changes acceptable behavior is a gap under step 5. A criterion about the work's boundaries states what the executor did, wrote, or started, never the state of something others can change, such as another repository's working tree or a process the executor did not start. A criterion a search would verify states the condition the search must establish, such as no reference to a removed file, and leaves the command to the executor unless the draft or the project defines one.
10. Apply the inspection rules in [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) for every draft that targets a project.
11. For a reachable target project, apply the validation checks in [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md) before returning the prompt, whatever the draft's scale. Every limit in those checks retains Boundaries priority under Interpretation.
    - Sign-in: Apply the Sign-in rule in [references/project-inspection-and-validation.md](references/project-inspection-and-validation.md); it is the rule above Limits in the full step 11 sequence.
    - Limits:
        - Allowed writes: run only commands whose writes land in files the project ignores, such as caches, reports, or coverage output, in a tool's own caches or logs outside the project, in a temporary location outside the project, in the project's local development data, such as a local database, or, for a sign-in the rule above allows, in the session record it opens.
        - Project commands: The project's own commands are those its manifest, configuration, or documented policy defines, including a tool its configuration sets up to run, such as a test runner; any other tool that writes into its working directory runs from that temporary location, never from inside the project, while the project's own commands run where the project defines them, and their writes must still stay within these limits.
        - Prohibited actions: Never run one that modifies a file the project keeps under version control, applies a migration to anything other than a throwaway test database or the local development database, touches real data, deploys, or calls an external service other than a non-production service the application depends on, used only for checks that read, apart from the session record a sign-in opens.
        - External resources: Public resources the application loads on its own, such as fonts, icons, and scripts, are allowed; telemetry it sends is no part of any check, and signing in through a production identity provider is not allowed, so a check that needs it is recorded as not measured.
        - Shared resources: Before a command takes a shared local resource, apply the shared-local-resource rule under Adaptation rules to this session's own run, and start it only once no other session is using that resource; when it stays in use, record the check as not measured.
        - Existing servers: A server of the project that this session did not start is treated as the user's and is not contention: use it as it is, never stopping, restarting, or reconfiguring it.
        - Coverage: These limits govern every command this skill runs, including those step 10 uses to measure state and verify causal claims and those its subagents run.
        - Cleanup: Stop every server or other process this skill started, and close every browser session it opened, as soon as the measurements that need them end, and in any case before opening a further round of questions or returning the prompt; then confirm that each port they held is free and each browser session is closed.
12. Before returning, review the rewritten prompt against this list in a separate pass. Delegate the review, through the subagent mechanism named under Client bindings, to a subagent that did not write the prompt, only reads, and edits no file, giving it the draft, the rewritten prompt, the evidence this session gathered, and the severity scale below; a session without that mechanism reviews the prompt itself in a separate pass. Each finding names the list item, the prompt text, and a severity: high when an executor following the prompt would do wrong or unauthorized work, or a criterion would fail on a correct implementation; medium when the executor would do something other than what was asked in a way that matters, or would have to guess what the prompt must settle; low otherwise. Correct every high and medium finding in the prompt and have only the corrected parts reviewed again; stop after three correction cycles. A finding still high or medium after them whose correction is mechanical, changing no requirement, criterion, or what the prompt authorizes, may be corrected without another review, and the answer says so; carry any other as a question under step 5 or, in a session that cannot receive a reply, as an open decision. Correct a low finding only when the correction stays local, and add nothing the findings do not require.
    - every acceptance criterion is observable and, in an implementation prompt or a prompt for standalone code, numbered, with the failure modes that apply included in the list, and none makes a baseline observation binding unless its source makes it one;
    - every observable requirement of the task statement is covered by a numbered criterion, and the Spec Gate and the closure audit judge against every requirement the prompt states, not only its numbered criteria and decisions;
    - every constraint and acceptance criterion traces to the draft, the user, the target project, or a rule of this skill that mandates it, and everything the task must achieve is in the draft, including the exact text a draft approves, or in a user's answer that covers it at the extent the prompt gives it, or is carried as an open decision;
    - where a target project was reachable, every state claim, causal claim, reported defect, and validation command the prompt carries was measured, verified, or reproduced under steps 10 and 11, or is recorded as not measured, unconfirmed, or a hypothesis with its reason, and where it was not reachable, the user confirmed the claim or the prompt states it as unverified;
    - no gap was closed by an assumption and no detail was invented: every gap was asked about or, in a session that cannot receive a reply, carried as an open decision in the form Goals defines or as a placeholder, and a specific that neither step 5 nor step 10 sends to the user is kept as the draft states it and marked in the prompt as unverified;
    - every placeholder this skill adds uses the `[TODO: what is missing]` form, while variables the draft defines for its own use, such as template slots, stay as written;
    - every artifact the prompt names as one to change was confirmed to bear on the authorized change;
    - every run the prompt defers names who runs it;
    - no criterion fails on a correct implementation, such as one that keeps a baseline sequence the change extends or a search that reaches generated, ignored, dependency, or untracked tool output;
    - no criterion depends on state others can change or contradicts another part of the prompt, such as a choice the prompt leaves to the executor or the concurrency rule when the prompt carries it.

    This list is verified by reading the rewritten prompt and what this session did to prepare it; it never adds a section, label, or heading to it. A condition the prompt already satisfies implicitly needs no visible text to prove it.

## Adaptation rules

In these rules, to clarify an element is to state it in the prompt when the draft, the user, or the target project settles it, and otherwise to treat it as a gap under step 5 only when the prompt must commit to it; an element the prompt need not commit to is left out.

- For coding prompts, clarify repository scope, files or interfaces, constraints, tests, and acceptance criteria.
- For coding prompts, take build, test, and check commands from the project's own manifest, configuration, or documented policy, never from ecosystem convention, with the arguments that narrow one of those commands following the tool's own documented usage; a generic read-only command that searches, lists, or compares, or a one-off invocation step 11 ran as a reproduction or baseline, may also serve as a check. For standalone code with no target project, the check runs the code the prompt asks for through the interface the draft defines. When none of these covers a check, ask the user, and in a session that cannot receive a reply use a placeholder instead of a guess.
- For coding prompts, require coverage at the level that certifies the changed behavior, and name the file or suite that will hold it. When the project has no suite at that level, the observable check that certifies the behavior meets this requirement: name it and state that no suite at that level exists; adding one is a question for the user under step 5, in a narrow draft as well and even when that opens a further round, and in a session that cannot receive a reply it becomes an open decision whose recommended option is not adding one. Never present an existing unrelated suite as evidence that the change works; a suite that passes without exercising the change proves nothing.
- For coding prompts, prefer the narrowest invocation of the project's own commands that still covers the changed behavior, and name the broader run deliberately deferred, unless it executes exactly what the narrowest invocation does. A deferred run stays the executor's to run at its discretion. The prompt defers it to automation only when step 10 measured, within the limits of step 11, that the automation runs for the destination the work goes to, and then requires checking its result for the published revision before reporting validation; when that cannot be measured, the run is not deferred to automation. When the prompt authorizes an action that carries the work beyond the working tree, such as a push, merge, publish, or deploy, the broader run is not deferred: the prompt requires it, with its measured baseline, before that action.
- For prompts whose validation takes exclusive control of a shared local resource, such as a database, a fixed port, containers or a browser runner, say so in the prompt and require the executor to confirm no other session is using it before starting, to report contention as contention instead of reading it as a failure of the change, and to release the resource when done, stopping the servers and closing the browser sessions the executor started. A server of the project that the executor did not start is treated as the user's: it may be used as it is and is never stopped, restarted, or reconfigured. For a browser runner that names its sessions, require a session name that no other session holds, checked with the runner's own listing of every open session; sessions under other names do not make the runner unavailable. A runner without named sessions is covered by the checks on the ports and servers it uses.
- For UI prompts, those whose change or verification involves rendered appearance or interaction, require the executor to state the screen, route, viewport, and state where the result is verified, and to express acceptance as observable conditions: measured contrast, position, size, or spacing for appearance, and the resulting state for interaction. When the change adds, resizes, or moves rendered elements, also require checking, under the Regression Preservation Gate, that the layout still holds as it did before the change at a width just inside each side of every breakpoint in the project's styles that the change can affect, taken from those styles rather than from convention; the acceptance criteria still apply only at the viewports they name. Name a validation tool only if the user named it or the target project uses or documents it, except for the conditional visual verification below.
- For UI prompts that create, change, or audit rendered appearance, require screenshot-based verification through whatever screenshot-audit capability the executing session offers, detected from the skills and instructions that session will load, as far as this session can see them, from what the repository uses or documents, and from what the user named, rather than assumed by name. Do not require it for code-only UI questions, planning, copy changes, non-visual behavior, or narrow diagnoses whose cause and acceptance can be verified without screenshots. When one is used, require every finding to name the affected element, the property or token to change, and the condition that verifies it. Judge availability for the session that will run the improved prompt, not for this one. When none is detected, still require screenshot-based verification without naming a browser, runner, or capture tool: the executor obtains a capture or reports the change as visually unverified, and every finding keeps the same shape.
- For research prompts, clarify the question, time range, source quality, citations, and how uncertainty should be reported.
- For creative prompts, preserve the desired style and subject while clarifying composition, audience, format, and exclusions.
- For high-stakes prompts, require verification, uncertainty reporting, and appropriate professional review.
- For prompts involving private, destructive, or external actions, preserve explicit approval boundaries and require confirmation before irreversible actions, including those the user chose to keep when the prompt was prepared.
- Write the improved prompt in the language of the draft. When the draft mixes languages or its language is unclear, use the user's. An explicit request for another language overrides both. Questions and clarification turns use the language the user writes in the conversation, whatever the draft's language.

## Implementation prompts

## Output

Return the improved, copy-ready prompt in a code block. Open and close it with a fence longer than any fence inside the prompt, so its own code or Markdown cannot terminate the block early.

Two labels may follow the code block, in this order, each on its own line with its lines beneath it:

- a corrections label, when the target project contradicts a factual claim of the draft, such as a path that does not exist, a test that covers something else, or a command the project does not define, so the user learns what was wrong instead of seeing it silently rewritten;
- a findings label, when the target project contradicts itself in a way that bears on the work the prompt authorizes, such as documentation that describes behavior the code does not implement, a comment or reference that no longer matches what it names, or a stated rule the code applies differently.

One short line each. Each findings line ends by saying whether the prompt already carries it and where, such as a named decision or the context section, or that it does not, so the user can tell whether it still needs action. What the draft asserted belongs under corrections and never under findings; what the project asserts against itself belongs under findings and never under corrections. Both carry only what you verified by inspecting the project, and findings carry only what bears on the work the prompt authorizes. Neither label is a place for notes, advice, summaries, caveats, or a general audit of the project: context the executor needs belongs inside the prompt, and anything that would change what the prompt authorizes is a question you owed the user per step 5. A verified self-contradiction the executor needs appears in both places: as context inside the prompt and as a line under findings.

There is no assumptions label and nothing plays its role: an assumption you would have listed there is a question you owed the user, so ask it per step 5 instead.

Both labels are named here in English, but they are descriptions and not tokens: write each as the word the language of the improved prompt uses, followed by a colon, on its own line, and keep the same wording across the whole answer.

Each label appears only when it has at least one line to carry, and the two are independent: print corrections only when the project contradicted a claim of the draft, print findings only when the project contradicted itself, print both when both happened, and print neither when neither did. Never print a label with nothing under it, never write a line saying there is none, and never keep a label to show that you checked. When neither applies, the code block is the entire answer.

Nothing else goes outside the code block and those labels, except one line after them, in the prompt's language, for each finding step 12 corrected without another review: no headings, explanations, summaries, key changes, open questions, or notes. When clarification was required, wait for the user's answers before returning the prompt. That rule governs the answer that carries the improved prompt; a step 1 request for a missing draft and a step 5 clarification turn are not that answer.

If the user asks for a specific format, length, language, or model, follow that request over this default output format; when a requested length or format would drop content a rule of this skill requires, ask which one governs, as Goals describes for conflicting constraints.

Read [references/examples.md](references/examples.md) only when an open decision, a findings line, or a bounded rewritten draft needs an example.
