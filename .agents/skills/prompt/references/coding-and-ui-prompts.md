# Adaptation rules for coding and UI prompts

These rules belong to the Adaptation rules in [SKILL.md](../SKILL.md), and the meaning given there to clarifying an element applies to them. Those Adaptation rules define coding and UI prompts; the coverage rule below applies only to a coding prompt that changes behavior.

- For coding prompts, clarify repository scope, files or interfaces, constraints, tests, and acceptance criteria.
- For coding prompts, take build, test, and check commands from the project's own manifest, configuration, or documented policy, never from ecosystem convention, with the arguments that narrow one of those commands following the tool's own documented usage; a generic read-only command that searches, lists, or compares, or a one-off invocation step 11 ran as a reproduction or baseline, may also serve as a check. For standalone code with no target project, the check runs the code the prompt asks for through the interface the draft defines. When none of these covers a check, ask the user, never filling it with a guess.
- For coding prompts, require coverage at the level that certifies the changed behavior, and name the file or suite that will hold it. When the project has no suite at that level, the observable check that certifies the behavior meets this requirement: name it and state that no suite at that level exists; adding one is a question for the user under step 5, in a narrow draft as well and even when that opens a further round. Never present an existing unrelated suite as evidence that the change works; a suite that passes without exercising the change proves nothing.
- For coding prompts, prefer the narrowest invocation of the project's own commands that still covers the changed behavior, and name the broader run deliberately deferred, unless it executes exactly what the narrowest invocation does. A deferred run stays the executor's to run at its discretion. The prompt defers it to automation only when step 10 measured, within the limits of step 11, that the automation runs for the destination the work goes to, and then requires checking its result for the published revision before reporting validation; when that cannot be measured, the run is not deferred to automation. When the prompt authorizes an action that carries the work beyond the working tree, such as a push, merge, publish, or deploy, the broader run is not deferred: the prompt requires it, with its measured baseline, before that action.
- For prompts whose validation takes exclusive control of a shared local resource, such as a database, a fixed port, containers or a browser runner, say so in the prompt and require the executor to confirm no other session is using it before starting, to report contention as contention instead of reading it as a failure of the change, and to release the resource when done, stopping the servers and closing the browser sessions the executor started. A server of the project that the executor did not start is treated as the user's: it may be used as it is and is never stopped, restarted, or reconfigured. For a browser runner that names its sessions, require a session name that no other session holds, checked with the runner's own listing of every open session; sessions under other names do not make the runner unavailable. A runner without named sessions is covered by the checks on the ports and servers it uses.
- For UI prompts, those whose change or verification involves rendered appearance or interaction, require the executor to state the screen, route, viewport, and state where the result is verified, and to express acceptance as observable conditions: measured contrast, position, size, or spacing for appearance, and the resulting state for interaction. When the change adds, resizes, or moves rendered elements, also require checking, under the Regression Preservation Gate, that the layout still holds as it did before the change at a width just inside each side of every breakpoint in the project's styles that the change can affect, taken from those styles rather than from convention; the acceptance criteria still apply only at the viewports they name. Name a validation tool only if the user named it or the target project uses or documents it, except for the conditional visual verification below.
- For UI prompts that create, change, or audit rendered appearance, require screenshot-based verification through whatever screenshot-audit capability the executing session offers, detected from the skills and instructions that session will load, as far as this session can see them, from what the repository uses or documents, and from what the user named, rather than assumed by name. Do not require it for code-only UI questions, planning, copy changes, non-visual behavior, or narrow diagnoses whose cause and acceptance can be verified without screenshots. When one is used, require every finding to name the affected element, the property or token to change, and the condition that verifies it. Judge availability for the session that will run the improved prompt, not for this one. When none is detected, still require screenshot-based verification without naming a browser, runner, or capture tool: the executor obtains a capture or reports the change as visually unverified, and every finding keeps the same shape.
