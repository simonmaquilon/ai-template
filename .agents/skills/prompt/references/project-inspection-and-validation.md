# Project inspection and validation

Read this reference when a draft targets a project. The `Limits` bullet in [SKILL.md](../SKILL.md) step 11 governs every command here; every other limit in step 11 has the same Boundaries priority under Interpretation.

10.
    - Inspection: When a target project applies and is reachable in this session, inspect it read-only: open files, search the tree, and confirm that every path, symbol, command, and factual claim carried into the prompt exists and means what the draft says.
    - Broad drafts: In a broad draft, delegate to subagents that edit no file, through the subagent mechanism named under Client bindings, what the reading that settled the scale left unconfirmed: give each one a bounded question, the claims it must confirm, and the conclusions already established so it does not reread them, run independent ones in parallel, and require every conclusion to cite the file, line, or command output behind it. Keep their conclusions instead of rereading the same files, and inspect directly only what a conclusion leaves unresolved or uncited.
    - Direct inspection: A narrow draft, or a session without that mechanism, is inspected directly.
    - Evidence: A conclusion you draw from inspecting the project is not a fact the draft supplied: carry it with the evidence that supports it, never as something the user said and never in the user's voice.
    - Project state: A claim about the project's state rather than its contents, such as work left uncommitted, a migration still pending, or a check currently failing, is not settled by confirming that the files exist: measure it with commands that leave the project unchanged, the project's own or generic ones, and write what you observed, whether the draft asserted it or you inferred it. Record a contradicted state claim under the corrections label like any other. When it would change what the prompt authorizes, also ask about it.
    - Causal claims: A causal claim the draft carries as a finding, or one this skill infers, such as a cause, a redundancy, or a rule that does not apply, is verified before it becomes an instruction: a claim about what the code says, by reading it and citing file and line; a claim about how it behaves when run, by running or measuring it; when it cannot be verified, the prompt states it as a hypothesis the executor must confirm first, never as a fix to apply.
    - Unreachable projects: When a target project applies but is not reachable in this session, keep the draft's specifics, ask the user to confirm the ones you could not verify, in a narrow draft as well, and never replace one with a guess.

11. When a target project applies and is reachable in this session, test it before returning the prompt, whatever the draft's scale:
    - Baseline: run the narrowest invocation of each validation command the improved prompt will name, and write into the prompt each command with the result you observed, naming what passed and what failed, so the executor can tell a failure that predates the change from a regression it caused. Carry that result as measured evidence, never in the user's voice. Measure the broader run the prompt names as deliberately deferred as well, so the executor knows its baseline if it runs it. When the broader run executes exactly what the narrowest invocation does, the prompt names no deferred run. When a check asserts the behavior the change is meant to alter, the prompt says that it will fail until it is updated and that this failure is not a regression. A check that targets a file the executor will create has no baseline yet: record it as not measured because the file does not exist yet, not as a failure.
    - Reproduction: when the draft reports current behavior as wrong, try to trigger it with the commands, tests, or running application the project already has, or with a one-off invocation whose writes stay within the limits below, without writing or editing any file yourself; a one-off invocation whose only writes, if any, land in a tool's own caches or logs outside the project runs from the project root, and one that writes into its working directory runs from the temporary location, as the limits below require. Carry the reproducing invocations into the prompt as you ran them, except that a secret, credential, token, or personal datum the project holds becomes a named reference to its source, as Boundaries requires, a path into this session's temporary location becomes a description of that location, and an identifier that exists only in this session, such as a session name or an element reference, becomes a description of what it identifies. When it reproduces, the prompt carries the steps and the output you observed. When it does not, the prompt states the defect as unconfirmed and requires the executor to reproduce it before changing any code. A cause the draft attributes to the defect remains governed by the causal-claim rule of step 10. A draft reports a defect when it says the current behavior is wrong, broken, or different from what it should be; one that only states what the behavior must become asks for new behavior. A draft that asks for new behavior is not reproduced: measure the current behavior the change will alter by the same means, and carry the result into the prompt as its baseline; a pure addition alters nothing, so its baseline is only the confirmation that what it adds does not exist yet.
    - Visual defects: when the draft reports a defect in the rendered interface or asks to change what it shows, text included, observe the current state through whatever screenshot capability this session offers, detected from its available skills, from what the project uses or documents, and from what the user named, even when the code also shows it. Open only the screen, route, viewport, and state the draft names, the project confirms, or this bullet lets you choose, and take only the steps that reaching that state requires, such as signing in; none of those steps may change data beyond what the limits below allow. When the change does not depend on the viewport, observe at a common desktop viewport without asking. When neither the draft nor the project settles the screen, route, state, or a viewport the change depends on, ask for what is missing under step 5; a session that cannot receive a reply observes at choices it makes and carries each as an open decision recommending that choice. Save screenshots to a temporary location outside the project, and look only at what the draft asks to fix or change: no other visual observation enters the prompt. Describe what you observed in words, naming the screen, viewport, element, and what is wrong, because the executor will not have the screenshot.
    - Sign-in: when reaching that state requires signing in, use only a test account whose credentials are not secret, against a local application or a non-production environment, including hosted services such an application depends on; its steps may write only to the local application and its local development data, and to anything remote only the session record that signing in opens; production is never allowed. Take it first from the accounts the project documents; when the project documents none, ask the user which test account to use through the question mechanism of step 5, even when that opens a further round. A credential that appears only in source code is not a documented account: offer it as an option when you ask, and never use it unasked. Never create or seed an account to sign in with; exercising a sign-up flow the draft reports as defective against the local application is a reproduction whose writes stay in local development data. Never sign in with a real, production, or secret-bearing credential; when such a credential is the only way in, or the project documents no test account and the session cannot receive a reply, record the check as not measured. The prompt names the account by its role and source, never by its password.
    - Limits: Apply the `Limits` bullet in [SKILL.md](../SKILL.md) step 11 to every command and browser action described above.
    - A command you could not run, because its resource was in use, a limit forbade it, the sandbox still blocked it as the `Sandbox` limit describes, its environment was missing, or the user asked that nothing be run, never receives an invented result: the prompt records it as not measured and states why.
