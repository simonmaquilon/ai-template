# Command limits

The `Limits` bullet of step 11 in [SKILL.md](../SKILL.md). Interpretation gives every limit here Boundaries priority.

- Limits:
    - Allowed writes: run only commands whose writes land in files the project ignores, such as caches, reports, or coverage output, in a tool's own caches or logs outside the project, in the temporary location, in the project's local development data, such as a local database, or, for a sign-in the Sign-in rule in [project-inspection-and-validation.md](project-inspection-and-validation.md) allows, in the session record it opens.
    - Temporary location: the folder the target project's rules set for temporary artifacts; when they set none, the one the agent's global configuration sets; when it sets none, the session's own scratch folder, as Client bindings names them; and only when none of them is set, the operating system's temporary folder. One inside a project under version control counts only when version control ignores it, and one inside a repository other than the target project's never counts; in either case ask the user where to write.
    - Project commands: The project's own commands are those its manifest, configuration, or documented policy defines, including a tool its configuration sets up to run, such as a test runner; any other tool that writes into its working directory runs from the temporary location, never from elsewhere in the project, while the project's own commands run where the project defines them, and their writes must still stay within these limits. Before running a project command, read its definition, such as the script body and the documented defaults of the tool it calls, and run it only when they show its writes stay within these limits, as a test runner that writes new snapshot files or a script that fixes lint does not. Around each command this skill runs against the target project, compare its files before and after: under version control, the working tree's status, read without optional locks and listing untracked files one by one, such as through `git --no-optional-locks status --porcelain --untracked-files=all --ignore-submodules=none`, together with the contents of every file not ignored that it lists as changed or untracked and of every tracked file an index flag, such as assume-unchanged or skip-worktree, hides from it, read without writing any object, and the same inside each nested repository it lists and each submodule the index records; without version control, a listing of every file with its size and modification time, leaving out only the files whose writes Allowed writes permits. When a run leaves a change these limits forbid, leave that change as it is, run that command no further, record the checks that needed it as not measured, and report the change in the one line Output allows for it.
    - Prohibited actions: Never run one that modifies a file the project keeps under version control, applies a migration to anything other than a throwaway test database or the local development database, touches real data, deploys, or calls an external service other than a non-production service the application depends on or a non-production environment of the application, reached only as the Visual defects and Sign-in rules allow, either used only for checks that read, apart from the session record a sign-in opens.
    - External resources: Public resources the application loads on its own, such as fonts, icons, and scripts, are allowed; telemetry it sends is no part of any check, and signing in through a production identity provider is not allowed, so a check that needs it is recorded as not measured.
    - Shared resources: Before a command takes a shared local resource, apply the shared-local-resource rule under Adaptation rules to this session's own run, and start it only once no other session is using that resource; when it stays in use, record the check as not measured.
    - Existing servers: A server of the project that this session did not start is treated as the user's and is not contention: use it as it is, never stopping, restarting, or reconfiguring it.
    - Sandbox: When the client's sandbox blocks a measurement, first set the tool's home directory and cache locations, such as through its environment variables, to the temporary location, and carry that setting with the result. When it is still blocked, retry it once through the client's one-off approval outside the sandbox, never widening the sandbox's settings, and only when what the sandbox blocked is a write or connection these limits allow, such as a tool's own cache outside the project or a public resource the application loads, and the rest of what the command does, as its documented behavior shows, also stays within these limits; a block on anything else is a limit at work. When the retry is not allowed, or the approval is unavailable or refused, record the check as not measured.
    - Coverage: These limits govern every command this skill runs, including those step 10 uses to measure state and verify causal claims and those its subagents run.
    - Cleanup: Stop every server or other process this skill started, and close every browser session it opened, as soon as the measurements that need them end, and in any case before opening a further round of questions or returning the prompt; then confirm that each port they held is free and each browser session is closed.
