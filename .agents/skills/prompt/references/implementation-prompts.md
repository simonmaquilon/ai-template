# Implementation prompts

These rules apply to implementation prompts, those that authorize changes to a target project's code or other files. A prompt for standalone code with no target project takes only the three change gates, the closure audit with the bullets that follow it up to the Stop Rule (Delegated criteria, Review method, Severity and precision, Corrections, Stop conditions, Blockers, and Closing report), and the Stop Rule below, reading the code it produces in place of a diff, and the naming limit below does not bind it; the adaptation rules for coding prompts still apply to it, with the code the prompt asks for in place of the project, except that running that code through the interface the draft defines is its check and no question about adding a suite is asked. These rules are stack agnostic. Express them in terms the target project already uses, and never name a technology, layer, or artifact that the user did not mention and the target project neither uses nor documents, except where another rule of this skill allows naming it, such as a one-off invocation step 11 carries as evidence, a generic read-only command that searches, lists, or compares, or a validation tool the adaptation rules allow.

- Spec Gate: Before each change, require the executor to trace it to a concrete requirement authorized by the draft or the user's answer, to a requirement the prompt states under a rule of this skill or of the project in service of one, such as the coverage, usage-sweep, or documentation it requires, or to a verified in-scope defect that prevents meeting one. A project finding alone does not authorize extra work. For a project defect, require the executor to verify an unconfirmed report before editing, as step 11 requires; for standalone code, require confirmation against the supplied code before correcting it. An unconfirmed defect remains a hypothesis or blocker while independently authorized work proceeds.
- Fix-guided Verification: For a defect, require comparable before-and-after evidence showing the reported failure and then the corrected behavior. For new behavior, require an observable check of the requested result against the measured baseline, or through the requested interface for standalone code. An unrelated passing check is not evidence that the change works.
- Reference match: When a criterion says the behavior is the same as a reference X, such as a tool, a specification, or a prior version, require the prompt to name X, with its version and source, and the corpus the comparison runs on, a fixed set plus inputs generated from a fixed seed, with zero divergences as the criterion and every accepted divergence listed with its reason.
- Regression Preservation Gate: Require the executor to identify affected behavior that already works and prior accepted decisions or fixes from the draft, the user's answers, and project evidence, including the principles and acceptance conditions the project's reference material sets for the affected surface, such as an element that must stay in view, and the code comments that state the intent protecting those principles and conditions. When a criterion exempts part of the preserved behavior, such as an element's vertical position, it names the principles and conditions that exemption was checked against and keeps the ones it does not replace. Require post-change checks showing that what this gate identified still holds unless the current specification explicitly replaces it; treat any other breakage as a regression. For a pure addition with no prior behavior, record that there is nothing to preserve rather than inventing a baseline. When the change extends or reorders preserved behavior, such as a sequence it adds a step to, state the expected result after the change instead of requiring the baseline to hold unchanged.

- When the concurrency mandate applies, state that other agent sessions may be modifying the same working tree. Require treating pre-existing and concurrent changes as user-owned, re-reading each target file immediately before editing, limiting writes and formatting to the requested scope, never reverting or overwriting unrelated work, and stopping to report a true overlap when safe integration is uncertain.
- Require sweeping every usage of the touched name, symbol, key, or contract before closing, including the artifacts that must change with it, such as parallel translations, styles, generated files, fixtures, tests that assert the previous source, and documentation of the changed behavior.
- Require deleting whatever the change leaves dead.
- Role visibility: When the change adds, removes, or alters the data a view, response, export, or message gives to a role, in a project with two or more roles or parties, such as buyers, sellers, administrators, or tenants, carry a visibility matrix with one row for each pair of a role and a view, response, export, or message whose data the change adds, removes, or alters, including one the change does not edit that returns data the change stores, each naming the data that role receives there and the data it must not receive, as the draft, the user's answers, the project's reference material, and, for data a role already receives there, the access the project already enforces settle it; a cell none of them settles is an open decision, never a guess. Make each row a numbered acceptance criterion whose check reads what the role receives there, such as the response, payload, export file, or message body, not only what a screen renders, a row with an open cell waiting on that decision, pending and never failed until the user takes it, and list each other role the project defines with the reason the change does not reach it.
- Consolidate repeated implementation requirements into numbered acceptance criteria and reference their identifiers elsewhere instead of restating them; keep baseline evidence separate from those criteria.
- Closure audit: For every implementation prompt, require a distinct closure audit after implementation and the requested validations, run as a gate against the numbered acceptance criteria, the explicit decisions, and the other requirements the prompt states.
- Delegated criteria: When the prompt delegates part of the work to a process that writes or updates its own acceptance criteria while it runs, such as a workflow that drafts the requirements it then implements, the audit also judges against the criteria that process recorded, and one it left unmet is reported as a pending risk even when every numbered criterion passes.
- Review method: The executor re-reads the complete task-owned diff, traces changed contracts through relevant producers and consumers, and marks each criterion, explicit decision, and stated requirement as met or failed, rating a failure high when the behavior it covers is wrong, medium when it is partly met, and low when only its wording or form is off. Passing tests and checks are evidence, not proof of coherence.
- Severity and precision: Judge severity against the authorized requirement at the precision the measurement supports. Distinguish measurement uncertainty from a verified behavioral violation; uncertainty alone does not establish one. Preserve explicit numerical requirements, including exact equality when the draft, the user, or an established project requirement requires it.
- Corrections: Each failure is recorded with the correction that makes it pass; after applying the corrections, the executor re-verifies only what failed and the criteria whose files the corrections touched, not the whole task again.
- Stop conditions: The audit stops when no high or medium failure remains, or after three correction cycles, whichever comes first; what still fails is reported as a pending risk with the criterion, decision, or requirement it fails, and anything noticed outside all three is reported as an observation and not corrected.
- Blockers: When a correction needs new authority or information, require reporting the blocker instead of declaring completion.
- Closing report: Require the closing report to open with one sentence that starts with a plain yes or no to whether the work is done, such as "Yes, it is done." or "No, it is not done yet:" in an English report, worded in the language the report is written in, before anything it reports as done and without the names of its own process, such as gates, cycles, or statuses; after a no, the sentence says what keeps the work incomplete, named by what is left to do, such as a decision the user must take or a behavior that still does not work, and, after either answer, when a step below is pending, that the change is not in effect until it, and then to list each criterion with its final state, the corrections made in each cycle, the pending risks and observations, what was deliberately left untouched, and, as pending, each step the change still needs to take effect that was not taken, such as a commit, push, deploy, or someone's approval, with what it waits on, such as an authorization or a pending risk to resolve first, so the user never has to request a separate implementation review or ask what remains; such a step alone never makes the work incomplete, so when only such steps remain the sentence starts with yes. Require that sentence in the closing report only, never in a later message such as a confirmation or the answer to a follow-up, and require the report to end, where the session can ask, with a question that itself says, with the same plain yes or no, whether the work is done and what is left, and whose options are the open decisions and the pending steps, so the user chooses what happens next instead of writing it.
- Stop Rule: Require the executor to stop when the requested outcome is met and no material verified defect in the authorized scope remains. Do not add optional refactors or speculative changes; cleanup of dead work directly caused by the change remains required under the rule above where that rule applies. If the closure audit reaches three correction cycles with a high or medium failure, stop and report the work as incomplete with its pending risks. If required verification remains blocked at closure, report the work as incomplete while preserving independent authorized progress. Report observations outside the authorized scope without correcting them.
- The concurrency, usage-sweep, dead-code, and role-visibility mandates are triggered, not automatic; the closure audit above applies to every implementation prompt. In a broad draft the usage-sweep mandate applies. In a narrow draft, carry the usage sweep only when the touched name has more than one usage, counting every reference outside its definition, tests and documentation included. In any draft, carry the role-visibility rule when its own condition holds, and the dead-code rule only when the change leaves code, files, keys, text, styles, or assets without any use; replacing something in place does not by itself set it off. Measure the tree in every draft that authorizes changes. In any draft, carry the concurrency rule when the user says others are working on that surface, when that measurement shows uncommitted work there, or when the tree could not be measured. Whenever the prompt carries the concurrency rule, it names the state you observed instead of repeating the claim, labeled as observed in this session when the executing session may differ. When the target project documents one of these rules already, cite its own policy in a clause instead of restating the rule; the visibility matrix is still carried, each cell that policy settles citing it.
- When a broad draft adds or changes a capability instead of adjusting one known behavior, open the prompt with a mandatory first step: enumerate the surface the change will touch, mark each item as applies or discarded with a one-line reason, show that list, and only then edit. Require stopping to report anything in it that contradicts what the draft, the user's answers, and the prompt settle, and continuing only once that is resolved. When step 6 also makes finding the cause the first step, finding the cause comes first and the enumeration second, once the user approves the cause. When the prompt already carries an inventory you verified, require the executor to confirm and extend that one rather than build it again. When it is unclear whether a broad draft adds or changes a capability or adjusts one known behavior, require the enumeration.
- Build that enumeration from categories that survive any stack: stored data and its reversal path, public contracts and interfaces, shared logic with more than one caller, the user-facing surface, duplicated or localized text and assets, configuration and access rules, automated tests at the level that certifies the behavior, and reference material that documents it. Keep only the categories the target project actually has.
- The enumeration belongs to broad drafts only. A narrow draft skips it even when it adds a capability. It is a scale rule, not a default for every draft.
- For a broad draft, require the executor to delegate to subagents the parts of the work that split into independent pieces when the executing session offers them, and to do that work itself in sequence when it does not. Delegate reading, searching, and reviewing: building the enumeration, the usage sweep, independent checks, and, within the closure audit, a review of the final diff against the numbered criteria, the explicit decisions, and the other requirements the prompt states by a subagent that did not write it. Give each subagent a bounded question, the conclusion it must return, and the requirement to cite the file, line, or command output behind it; run independent ones in parallel, and keep their conclusions instead of rereading the same files. Keep edits in the main session; the one exception is a subagent editing files no other agent is touching, or an isolated copy of the tree, whose result the main session then integrates and revalidates. The shared-local-resource rule applies between subagents as it does between sessions. Like the enumeration, this mandate belongs to broad drafts only.
